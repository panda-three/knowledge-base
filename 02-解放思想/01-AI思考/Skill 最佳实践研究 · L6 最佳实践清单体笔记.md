## 三、阶段一：快速认识——锁定最佳学习素材（约 30min）

> 这是整件事的**方向锚定**。不是闷头开始学，而是先搞清楚「在这个领域，什么才是真正值得学的东西」。

### 3.1 第一步：人问 AI，快速扫盲

Truman 没有先去 Google、没有先去社区翻帖子、没有先去 GitHub 搜项目。他做的第一件事是：

```
Truman → AI：
「我想学 Skill，给我一些教程和最佳实践参考，开源的、得到过验证的。」
```

这一个问题看起来很普通，但里面有三个关键约束：

| 约束 | 含义 | 排除的内容 |
|---|---|---|
| **教程** | 系统的、结构化的学习材料，不是碎片帖子 | GitHub README、社区短文、零散技巧 |
| **开源** | 代码和文档可以拿到本地深度研究 | 付费课程、闭源产品文档 |
| **得到过验证的** | 有社区认可度、有实际使用案例，不是个人实验品 | 刚发布、没有人用过的实验性项目 |

### 3.2 AI 的反馈与 Truman 的判断

AI 给了一堆参考和例子。Truman 在其中**识别出了最关键的东西**：

```
Claude 官方开源的一组教程
  └── 其中「skill-creator」作为元技能（Meta-Skill），是当之无愧的第一名
      └── 官方的很多审美和最佳实践，都藏在这个元技能里面
```

> 🔑 **L6 洞察**：不是「找最好的教程」，而是「找最接近源头的东西」。
>
> - 社区教程 = 二手解读，可能走样
> - 官方教程 = 一手源头，代表了设计者自己的审美和意图
> - **元技能（skill-creator）= 源头中的源头**——它是用来「写 Skill 的 Skill」，里面藏着官方对「什么是一个好 Skill」的全部判断标准

### 3.3 为什么不直接用 skill-creator 自动生成？

Truman 专门指出了一个致命短板：

| skill-creator 的优点 | skill-creator 的致命短板 |
|---|---|
| 官方出品，审美正 | **纯英文工具**——中文语境下理解和执行都会打折 |
| 可以自动生成 Skill | **太黑盒了**——你不知道它内部怎么判断、怎么取舍 |
| 省时间 | **完全不可控**——出来的东西你没法精细调整 |

> 🔑 **L6 决策逻辑**：当一个工具是「黑盒」的时候，它省掉的「时间」将来会以「质量不可控」的形式加倍还回来。L6 的选择不是「哪个更快」，而是「哪个能让我对最终质量有完整控制权」。

## 四、阶段二：AI 翻译和解读——双工具交叉工作（约 1-1.5h）

> 这是整件事**最具架构巧思的一步**。不是用一个工具翻译，而是用两个工具**同时、交叉、分工**工作。

### 4.1 为什么是双工具并行？

```
Trae  +  Antigravity
  ↓          ↓
翻译        解读精华和亮点
（保真）    （提炼）
  ↓          ↓
  └────┬────┘
    交叉验证
  翻译的准确性和解读的深度互相补充
```

| 单一工具模式 | 双工具交叉模式 |
|---|---|
| 一个工具既翻译又解读 → 两个任务互相干扰 | Trae 专注翻译，Antigravity 专注解读 → 各做最擅长的事 |
| 翻译错了解读必然偏 → 没有纠错机制 | 两个工具独立工作 → 人对两份输出做交叉验证 |
| 速度：先翻译，再解读（串行） | 速度：翻译和解读同时进行（并行） |

### 4.2 翻译的核心要求：「执行 100% 有效」

这不是普通的「把英文变中文」。Truman 对翻译提出了一个极其苛刻的标准：

```
不是语言翻译，而是要保持「执行 100% 有效」的情况下做翻译。
```

什么叫「执行 100% 有效」？

| 普通翻译 | 「执行 100% 有效」的翻译 |
|---|---|
| 把英文意思讲清楚就行 | 翻译后的文本，作为 Skill 的配置文件或提示词，**能直接跑通，不出错** |
| 允许意译、省略、调整语序 | 代码块、参数名、文件路径、格式标记**必须原样保留或精确对应** |
| 人可以读懂 | 人**和机器**都能完全按翻译后的版本操作 |
| 用翻译工具（DeepL、Google Translate） | 用 **AI 编程工具（Trae）**——因为编程工具理解「代码不能乱改」 |

> 🔑 **L6 洞察**：这是 Truman 对工具本质的理解——**翻译 Skill 教程不是「翻译任务」，而是「编程任务」**。因为 Skill 教程里充满了代码、配置、文件结构和精确指令，用翻译工具会把这些关键信息「美化」掉，用编程工具才会保持原始精度。

### 4.3 双工具的具体分工与协作

| 维度 | Trae 做什么 | Antigravity 做什么 |
|---|---|---|
| **核心任务** | 逐文件翻译 Claude 官方 Skill 教程 | 通读全组教程，提取设计原则、审美偏好、关键模式 |
| **关注点** | 每个文件、每个代码块、每个参数说明的精确翻译 | 官方为什么这么设计？哪些是「必须遵守」的？哪些是「建议参考」的？ |
| **产出物** | 中文版官方教程（可执行版） | 官方设计哲学解读 + 精华亮点清单 + 关键模式总结 |
| **质量标准** | 执行 100% 有效——翻译后的配置能直接跑 | 不是复述内容，而是**提炼出官方没有明说的审美和设计原则** |

### 4.4 双工具交叉之后，人做什么

两份产出到手后，Truman 不是直接合并。他做了三件事：

| 动作 | 内容 | 为什么 AI 做不了 |
|---|---|---|
| **交叉验证** | 对比 Trae 的翻译和 Antigravity 的解读——某一处的解读是否真的符合原文意图？ | AI 不会主动对比两个工具的输出 |
| **识别遗漏** | Antigravity 提了一个设计原则，但 Trae 的翻译里有没有对应的原文支撑？如果有矛盾，回去查原文 | AI 不容易发现自己「过度解读」了 |
| **形成初步判断** | 官方的审美到底是什么？哪些是核心原则（不遵守 Skill 就不对），哪些是风格偏好（可以有自己的选择）？ | 这是建模判断，AI 只能给信息，不能替人做判断 |

## 五、阶段三：自建最佳实践教程——先萃取，再合并（约 1-1.5h）

> 这是整件事的**核心方法论文火点**。Truman 在这里揭示了一个极其关键的技巧。

### 5.1 一个关键技巧：先萃取，再合并

Truman 给 Claude 的指令是：

```
我想做一个最佳实践级别的教程。
你帮我把所有官方教程的精华、参考、案例合并，
给我写一篇 Top 的教程，要 Topdown，要实操。
```

然后他揭示了一个关键洞察：

```
一个技巧：基于原始案例建模，通常显著差于先做一次萃取，再二次合并萃取。
```

### 5.2 「先萃取再合并」到底是什么？为什么显著更好？

**错误做法（基于原始案例直接建模）**：

```
教程A ──┐
教程B ──┼──→ 直接丢给 AI：「把这些合并成一篇教程」
教程C ──┘
  ↓
结果：AI 面对一堆原始材料，不知道重点在哪
 → 容易变成「缩写」而不是「萃取」
 → 每个教程的重要程度被平均化
 → 丢失了隐藏在细节里的设计原则
```

**正确做法（先萃取再合并）**：

```
教程A → 萃取A（精华、原则、模式、案例）
教程B → 萃取B（精华、原则、模式、案例）
教程C → 萃取C（精华、原则、模式、案例）
      ↓
萃取A + 萃取B + 萃取C → 合并萃取 → 最佳实践教程
      ↓
结果：AI 面对的是已经提炼过的「精华层」
 → 不会被原始材料的篇幅干扰
 → 能专注于「跨教程的模式识别」
 → 更容易发现官方在不同教程里反复强调的核心原则
```

### 5.3 「萃取」到底萃什么？

| 萃取维度 | 具体内容 | 为什么这层重要 |
|---|---|---|
| **核心原则** | 官方反复强调的「必须做/禁止做」 | 这些是 Skill 的「宪法」，不可违背 |
| **设计模式** | 官方在处理某类问题时反复使用的结构 | 这些是可复用的「建筑模板」 |
| **审美偏好** | 官方推荐但不强制的风格选择 | 这些决定了 Skill 的「品味」 |
| **典型案例** | 官方用来示范的完整 Skill 实例 | 这些是「原则如何落地」的活样本 |
| **踩坑警告** | 官方明确指出容易出错的地方 | 这些是帮你避开已知陷阱 |
| **边界说明** | 官方说「这个 Skill 不适合做什么」 | 这些防止你用错场景 |

### 5.4 初版教程的生成要求

Truman 对 Claude 的输出有三个硬要求：

| 要求 | 含义 | 如果没有会怎样 |
|---|---|---|
| **Topdown** | 从顶层设计原则讲起，再逐步下钻到具体实现 | 读者看了很多细节，但不知道「为什么这么设计」 |
| **实操** | 每一步都有可执行的代码、配置、命令行 | 变成了「道理都对，但做不出来」 |
| **最佳实践级别** | 不是入门教程，而是「如果只读一篇，这篇就是标准」 | 和社区那些「太碎」的 Skill 没有本质区别 |

## 六、阶段四：逐步打磨——逐模块 2-5 轮「不够好」（约 2-3h，核心环节）

> 初版教程到手后，进入密度最高的打磨环节。这和官网研究的 VibeCoding 有相同的魂——**逐模块、多轮次、审美式反馈**。

### 6.1 打磨的模块化策略

Truman 不是对整篇教程说「改好一点」。他把教程拆成了几个重点实操模块，**逐个深挖**：

```
自建最佳实践教程
├── 模块1：Skill 的顶层结构设计
├── 模块2：系统提示词的编写原则
├── 模块3：数据资产包的组织方式
├── 模块4：搜索调研的工作流设计
├── 模块5：报告输出的格式与质量标准
└── 模块6：调试与测试策略
```

### 6.2 每个模块的打磨动作链

Truman 对每个模块都做了五种标准动作：

| 动作 | 对 AI 说什么 | 目的 |
|---|---|---|
| **让它解读** | 「这个模块的设计逻辑是什么？为什么官方选择这样做而不是那样？」 | 逼 AI 暴露理解深度，不满足于表面复述 |
| **交叉验证** | 「你刚说的这个原则，在官方教程的另外几个地方有没有一致的表述？找出来对照」 | 防止 AI 的「幻觉解读」——把一次性的举例当成核心原则 |
| **让 MECE** | 「这个模块下的子原则是否互相独立、完全穷尽？有没有重叠的？有没有遗漏的？」 | 提升教程的结构严谨性 |
| **排优先级** | 「这些原则里，哪些是不遵守 Skill 就废了的？哪些是锦上添花？」 | 帮读者区分「必须」和「建议」 |
| **补底层逻辑** | 「这个设计选择背后的第一性原理是什么？不要只说『官方推荐』，要讲清楚为什么。」 | 从「照做」升级为「理解后做」 |

### 6.3 「不够好」的逐轮推进（以模块 2「系统提示词编写原则」为例）

| 轮次 | AI 的输出 | Truman 的反馈（「不够好」的艺术） | 反馈类型 |
|---|---|---|---|
| V1 | 列出几条编写原则 | 「太表面了，这些都是社区帖子也会说的东西。我要的是官方教程里**藏着的**审美——那些不是明说，但从他们的示例里能看出来的东西。」 | **深度不够** |
| V2 | 补充了一些从示例里提取的隐性模式 | 「好一些。但你漏了一类关键原则——错误示范。官方教程里有没有明确说『不要这样做』的例子？把这些反面案例也加进去」 | **MECE 不全** |
| V3 | 加入了反面案例 | 「正面原则和反面案例现在有了。但这堆信息的优先级不对——读者看完不知道先抓哪一条。你重新排：最核心的 3 条放到最前面，剩下的按『不遵守的后果严重程度』排序」 | **优先级不清** |
| V4 | 重新排序 | 「可以了。但现在你把原则讲清楚了，读者还是不知道怎么检查自己的 Skill 是否符合这些原则。加一个自查清单——每条原则对应 1-2 个可检查的问题」 | **实操锚点缺失** |
| V5 | 加入自查清单 | 「通过。记下这个模块的最终结构：原则→反面案例→优先级排序→自查清单。后面其他模块也按这个结构来」 | **通过 + 沉淀模板** |

### 6.4 「一个技巧」的深层解读

> 「基于原始案例建模，通常显著差于先做一次萃取，再二次合并萃取。」

这个技巧在打磨环节是如何发挥威力的：

```
假设没有先萃取：
  每个模块打磨时，AI 需要反复回到原始英文教程里去找依据
  → 每次都要在长篇英文里定位
  → 容易遗漏、容易串义
  → 2-5 轮反馈下来，已经偏离原文

实际用了先萃取：
  每个模块打磨时，AI 回到的是中文萃取层
  → 定位快速、精准
  → 不会因为反复「翻译」而累积误差
  → 2-5 轮反馈始终在精华层上叠加，不跑偏
```

> 🔑 **L6 洞察**：「先萃取再合并」不只是初稿生成的技巧，它在打磨阶段的价值甚至更大——**它创建了一个「高信噪比的中间层」**，让后续所有迭代都发生在这个干净层上，而不是在原始噪音里反复搅动。

## 七、阶段五：交叉验证吸收——把外部知识吞进来（约 1h）

> 自建教程打磨到高水准之后，Truman 做了一件很多人会忽略的事：**不满足于单一信息源**。

### 7.1 两份外部教程的引入

| 外部教程 | 来源 | 独特价值 |
|---|---|---|
| **Claude 官方的培训教程** | Anthropic 官方 | 与开源教程互补——培训教程通常有更系统的教学结构，可能包含开源教程里没有的「为什么」 |
| **花总分享的 Feature 思考** | 一堂内部高手（花总） | 代表了一个有深度实践经验的**中文语境使用者**的独特视角——不是翻译，而是实战后的提炼 |

### 7.2 交叉验证的四步动作链

Truman 不是把两份外部教程「附录」进去就完了。他设计了一套严格的吸收流程：

```
Step 1: 交叉测评
  ├── 把自建教程 + Claude 官方培训教程 + 花总 Feature 思考
  └── 一起丢给 AI，让它对比三份材料：
      ├── 各自的核心观点是什么？
      ├── 哪里一致？（高置信度共识）
      ├── 哪里矛盾？（需要人判断）
      └── 哪里互补？（各方有独特的视角）

Step 2: 打分
  ├── 让 AI 对三份材料在「实操性」「体系性」「深度」「覆盖面」四个维度上打分
  └── 不是让 AI 决定谁好，而是暴露各自的强弱项

Step 3: 吸收
  ├── 把外部教程中自建教程遗漏的精华点提取出来
  └── 把外部教程中比自建教程讲得更好的部分替换进去

Step 4: 合并
  ├── 经过吸收后的自建教程，再做一次「合并萃取」
  └── 最终版教程 = 官方开源精华 + 官方培训教程补充 + 花总实战视角 + Truman 的打磨
```

### 7.3 为什么交叉验证这一步不能省

| 没有交叉验证 | 有交叉验证 |
|---|---|
| 自建教程 = 官方开源教程的提炼版，只有一个视角 | 自建教程 = 三个独立来源的精华合并，视角更完整 |
| 不知道自己的教程有什么盲区 | 打分表暴露了每个维度的强弱 |
| 可能被官方开源教程的「权威感」镇住，不敢质疑 | 有了两份外部参照，更容易看出官方开源教程也有没说清楚的地方 |
| 教程的「魂儿」是官方的 | 教程的「魂儿」是 Truman 自己判断后形成的 |

> 🔑 **L6 洞察**：交叉验证的本质，是**防止自己被单一信息源「洗脑」**。越是权威的来源，越需要多一份参照——因为权威感会让人不自觉地降低审辨力。

## 八、阶段六：生成系统提示词——工业化的原子封装（约 30min）

> 教程写好了。但 Truman 不只是要一篇教程。他要的是一个**可以跑起来的 Agent**。

### 8.1 「教程 → Partner」的转化逻辑

Truman 让 AI 把教程转化为一个 Partner。这个 Partner 由两个部分组成：

```
Partner = 系统提示词 + 数据资产包

系统提示词（逻辑、工作流和审美）
  ├── 这个 Agent 是什么角色
  ├── 它的工作流是什么（从接收指令到交付报告的完整流程）
  ├── 它的审美标准是什么（什么算好报告、什么算不合格）
  └── 它的边界是什么（什么能做、什么不能做）

数据资产包（数据、案例、细节）
  ├── 最佳实践案例库
  ├── 搜索策略模板
  ├── 报告格式模板
  ├── 常见搜索场景的预设参数
  └── 踩坑记录和修正策略
```

### 8.2 为什么拆成「提示词 + 数据包」而不是一个大提示词

| 一个大提示词 | 系统提示词 + 数据资产包 |
|---|---|
| 逻辑和数据混在一起，改一个案例要动整个提示词 | 逻辑稳定（提示词），数据可换（数据包）——改案例只需更新数据包 |
| 换一个业务场景（比如从「搜索调研」换成「竞品分析」），整份重写 | 系统提示词（工作流框架）可以复用，只换数据包 |
| 难以维护——越长越容易出 bug | 两部分各自维护，职责清晰 |

> 🔑 **L6 洞察**：Truman 的原话是——**「系统提示词和数据资产包，未来会是一堂课程最小的 AI 交付原子单元。可以自由在各个平台，拼接各种产品、服务、业务流出来。」**
>
> 这不只是一个技术选择。这是一种**AI 产品化思维**——把知识和能力封装成可以自由拼装的「原子」，而不是每次都从矿石开始冶炼。

### 8.3 系统提示词的生成要求

| 要求 | 含义 |
|---|---|
| **角色定义清晰** | 不是「你是一个搜索助手」，而是「你是 Stella，一堂云端团队的产品设计研究员，你的工作是在正式设计前完成深度调研」 |
| **工作流完整** | 从接收调研课题 → 确认目标和边界 → 设计搜索策略 → 多轮搜索 → 交叉验证 → 撰写报告 → 保存到 Obsidian，每一步都有明确指令 |
| **审美注入** | 教程里提炼出的所有设计原则和审美标准，都转化为提示词里的质量判断条件 |
| **边界明确** | 什么情况下停止搜索、什么情况下请示人、什么信息源不可用 |

## 九、阶段七：YAI 封装——2min 从教程到产品（约 2min）

### 9.1 封装的极简流程

```
Truman 的动作：

  → 不是聊天记录，而是结构化的研究报告文件
```

### 9.2 2min 背后的 5-7 小时

很多人看到「2min 发布」会觉得「好快」。但 2min 只是冰山浮在水面上的部分：

```
水面以上：2min YAI 封装
─────────────────────────
水面以下：
  30min 快速认识 + 锁定素材
  1-1.5h 双工具翻译和解读
  1-1.5h 自建最佳实践教程（先萃取再合并）
  2-3h 逐模块打磨（每模块 2-5 轮「不够好」）
  1h 交叉验证吸收（两份外部教程交叉测评）
  30min 生成系统提示词 + 数据资产包
  = 5-7h
```

> 🔑 **L6 洞察**：2min 的发布速度，是用 5-7 小时的「慢功夫」换来的。不是 YAI 快，而是前六步已经把该踩的坑踩完了，该验证的原则验证完了，该打磨的细节打磨完了。**「快」从来不是因为省略，而是因为前置。**

## 十一、贯穿全流程的核心方法论提炼

### 11.1 「先萃取再合并」的普适性

这个技巧不只适用于 Skill 教程，它适用于任何**多源信息整合**场景：

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| 竞品调研 | 把 20 个竞品官网直接丢给 AI 总结 | 先让 AI 逐家萃取（每家一页精华），再合并萃取 |
| 课程设计 | 把 10 本参考书丢给 AI 出大纲 | 先让 AI 逐本萃取核心框架，再合并出大纲 |
| 文献综述 | 把 50 篇论文丢给 AI 写综述 | 先让 AI 逐篇萃取（核心论点、方法、结论），再合并 |
| 最佳实践整理 | 把一堆社区帖子丢给 AI 总结 | 先逐帖萃取（核心方法、适用场景、限制），再合并 |

### 11.2 「双工具交叉」的通用模式

| 场景 | 工具 A | 工具 B | 交叉验证什么 |
|---|---|---|---|
| 翻译+解读（本案例） | Trae（翻译） | Antigravity（解读） | 翻译准确性 vs 解读深度 |
| 代码生成+测试 | Claude（写代码） | GPT（写测试） | 功能正确性 |
| 方案设计+批判 | AI A（设计方案） | AI B（批判方案） | 方案的完整性和风险 |
| 调研+验证 | AI A（搜信息） | AI B（验证信息） | 信息的准确性和完整性 |

### 11.3 「2-5 轮不够好」的五种标准动作模板

| 轮次定位 | 动作 | 对 AI 说的话 | 适用场景 |
|---|---|---|---|
| **第 1 轮** | 深度不够 | 「太表面了。我要的不是大家都知道的东西，是官方教程里**藏着**的——不是明说但从示例里能看出来的原则」 | 初版回答停在常识层 |
| **第 2 轮** | MECE 不全 | 「你漏了一类。反面案例/边界条件/例外情况，有没有？」 | 回答只有正面、只有核心场景 |
| **第 3 轮** | 优先级不清 | 「这些信息现在排序不对。读者看完不知道先抓哪条。按重要性/严重程度重排」 | 信息有了但平铺 |
| **第 4 轮** | 实操锚点缺失 | 「现在道理讲清楚了。但读者怎么检查自己做到了没有？加自查清单/检查标准」 | 有原则但没有「怎么做到」 |
| **第 5 轮** | 沉淀模板 | 「可以了。记下这个最终结构，后面其他模块按同样的结构来」 | 单个模块通过后 |

## 十三、可迁移的 L6 原则清单

### 13.1 不要做的事

| 错误 | 为什么不行 | Truman 的正确替代 |
|---|---|---|
| 直接用官方黑盒工具生成 | 不可控，质量随机 | 放弃 skill-creator，走自建路线——翻译→萃取→打磨→封装 |
| 用翻译工具翻技术教程 | 代码、配置、路径会被「美化」掉 | 用 AI 编程工具做「执行 100% 有效」的翻译 |
| 把多个信息源直接合并 | 原始材料的篇幅和噪音会稀释精华 | **先萃取再合并**——先逐源萃取精华层，再在精华层上合并 |
| 对整篇教程笼统反馈 | 精度不够，AI 不知道具体哪里要改 | **逐模块打磨**，每个模块 2-5 轮「不够好」 |
| 只打磨一轮就满意 | 停在「看着还行」 | 每个模块至少五动作循环：解读→交叉验证→MECE→排优先级→补底层逻辑 |
| 不引入外部参照 | 被单一信息源限制视角 | 找至少两份独立来源的参照，交叉测评打分后再吸收 |
| 教程做完就完了 | 下次要搜索调研 Agent 还得从头来 | 把教程转化为「系统提示词+数据资产包」的原子单元，可复用可拼接 |
| 封装完就结束 | 不知道实际跑起来有没有 bug | 部署到 OpenClaw，让 Stella 真正跑一次真实任务 |

### 13.2 一定要做的事

| 原则 | 具体动作 | L6 标识 |
|---|---|---|
| **先锁定源头** | 不满足于社区二手教程，找到官方开源教程中的元技能 | 源头思维——离设计者最近的资料最有价值 |
| **双工具交叉** | 翻译和解读同时进行，互相补位，人做交叉裁判 | 架构思维——不是一个工具做所有事 |
| **执行 100% 有效** | 翻译技术教程时，代码和配置必须能直接跑 | 精度洁癖——工程思维碾压语言思维 |
| **先萃取再合并** | 每个源先单独萃取出精华层，再在精华层上合并 | 方法论核心——创建一个高信噪比的中间层 |
| **逐模块 2-5 轮打磨** | 每个模块：解读→交叉验证→MECE→排优先级→补底层逻辑 | 深度不可速成——每一轮都在逼近源头审美 |
| **交叉验证吸收** | 引入至少两份外部独立参照，交叉测评打分后再吸收 | 防洗脑机制——不盲信任何单一权威 |
| **工业化封装** | 教程→系统提示词+数据资产包→YAI Partner→OpenClaw | 原子单元思维——从「一次性作品」到「可复用资产」 |
| **端到端部署** | 不只是写好教程，而是让 Stella 在真实环境里跑起来 | 交付思维——能跑通的才算完成 |

## 十四、时间分配复盘
