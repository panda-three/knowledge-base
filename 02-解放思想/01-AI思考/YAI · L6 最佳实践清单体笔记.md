## 一、YAI 的起源——一个战略级的「收敛决策」

### 1.1 走遍弯路之后的「第三条道路」

Truman 没有一上来就决定做 YAI。他先花时间看了一圈同行和 AI 工具，结论是：

```
看了一圈越看越悲观：
商业管理领域，真正有效的 AI 工具太难做了。

不同于简单地「写个周报」「做个图」「写一段程序」，
商业决策是一个极其复杂非标，需要极大上下文、业务背景信息，
极其容易失败和误判的工作。
```

在这个悲观的判断基础上，Truman 做了三个基本预判：

| 预判 | 内容 | 否定了什么路线 |
|---|---|---|
| **第一个判断** | 直接帮你做商业决策的 Agent，短期不太现实 | 否定了「全能商业顾问 Agent」的路线 |
| **第二个判断** | 大而全的商业 Agent，是结果，不是 1.0 | 否定了「一上来就做大平台」的路线 |
| **第三个判断** | 人和 AI 同时专业，价值才能放大十倍 | 否定了「AI 替代人」的叙事，确立「人+AI」范式 |

基于这三个预判，Truman 找到了一条**和友商截然不同的道路**：

```
把问题逐步收敛。

一堂围绕几十上百个科学原创课题，
提供最小的解决问题单位：
  提示词（Prompt）+ 数据包（Datapack）

然后大家在各个业务场景里，
自己修改、拼接、封装成自己好用的 Agent。
```

### 1.2 「诺贝尔文学天才」vs「资深编辑专家」——一个关键的产品哲学

Truman 用一个非常精妙的类比说清楚了 YAI 的产品哲学：

| 你希望谁来帮你打磨逐字稿排版？ | 效果 |
|---|---|
| **诺贝尔奖级别的文学天才** | 每次都跟你探讨什么是审美、什么是人性、什么是心理学和用户洞察的原则，然后每次随机发挥 |
| **经验丰富的资深编辑专家** | 封装好的专家，稳定执行就行 |

> 🔑 **L6 产品洞察**：现在的很多通用 LLM 和通用 Agent 的问题就是——**他们很出色，但缺少专长**。
>
> YAI 的核心产品逻辑不是「做一个更聪明的通用 AI」，而是**把一堂在各个商业课题上的专长，封装成一个个稳定的「资深编辑专家」**——足够明确的任务、上下文、必要的专业知识、明确的输出预期。

### 1.3 YAI 的演进路径——从个人工具到团队平台

YAI 不是一次规划出来的。它经历了从个人到团队到平台的渐进演化：

```
阶段一：个人使用
  Truman 在 GEM（Gemini）上配置了一套工具，自己用
  功能：把一个普通提示词自动转化成 AgentStyle
        里程碑、多轮确认、严格管理节点

阶段二：团队协同
  为了和团队协同，封装到 Cherry Studio 里
  问题：工具越来越多，管理和分工开始混乱

阶段三：TCPR 重构
  Truman 想到了一个「绝好的主意」：
  用 TCPR 重构 AI 定位
  → T（教学）C（咨询）P（实践）R（研究）四种角色

阶段四：YAI MVP
  合伙人 zhizhao 熬了几个大夜
  用 VibeCoding 做了一个内部使用的「粗糙 YAI」
  实现了三个产品内核要素
```

### 1.4 12-18 个月后的愿景

```
12-18 个月后，至少在商业和管理领域，
如果每一个人都能配置一个 TCPR 团队，
而且足够专业，足够默契，足够务实，足够具体，
那估计会是一个非常棒的 AI 愿景吧。
```

> 🔑 这不是一个功能愿景，而是一个**范式愿景**——未来每个人的工作方式，不是「用一个 AI 工具」，而是「管理一个 AI 原生团队」。

## 二、YAI 的三层产品内核

Truman 明确说 YAI 有三个核心产品要素。这三个要素不是随意堆砌的，而是有明确的**分层逻辑**——从底座到能力到扩展：

```
第三层：配置 Partner（用户自建层）
        用户可以自行封装系统提示词到固定场景
        这是 YAI 的「开源能力」——无限扩展

第二层：官方 Partner（一堂输出层）
        提供 10 个初始版本的推荐 Partner
        这是一堂的「专业封装」——最佳实践输出

第一层：一堂课程库（知识底座层）
        利用 RAG 把 200 门课 RAG 进来
        可以搜索、答疑、互动和引用
        这是 YAI 的「专业深度来源」——不可替代的壁垒
```

### 2.1 第一层：一堂课程库（知识底座）——YAI 不可替代的壁垒

| 维度 | 内容 |
|---|---|
| **技术实现** | RAG（检索增强生成）——把一堂 200 门课的内容结构化索引 |
| **核心能力** | 搜索、答疑、互动、引用——不只是「问答」，而是「基于一堂方法论的深度对话」 |
| **战略价值** | 这是 YAI 的**不可替代性来源**。任何一个通用 LLM 都能聊商业，但只有 YAI 能「用一堂的方法论来聊商业」 |
| **为什么是壁垒** | 200 门课 = 200 个科学原创课题 × 每门课的逐字稿、作业、案例、模型——这不是任何外部 AI 可以「训练」出来的数据 |

> 🔑 **L6 洞察**：通用 AI 的「知识广度」是它们的壁垒。YAI 的「知识深度」是它的壁垒。RAG 200 门课不是一个技术动作，而是一个**战略动作**——它把一堂 5 年的方法论积累，变成了 AI 可以调用的结构化知识。

### 2.2 第二层：官方 Partner（一堂输出层）——最佳实践的标准化封装

| 维度 | 内容 |
|---|---|
| **初版规模** | 10 个初始版本的推荐 Partner |
| **覆盖角色** | TCPR 四个角色的典型场景 |
| **战略价值** | 这是 YAI 的 **「专业封装」**——不是让用户从零摸索，而是把 Truman 和一堂团队打磨出的最佳实践直接交到用户手里 |
| **迭代方式** | 初版示意，可能会改——保持「粗糙 MVP」心态，不追求一次性完美 |

已知的官方 Partner（从各案例中交叉验证）：

| Partner 名称 | TCPR 角色 | 来源案例 | 核心能力 |
|---|---|---|---|
| **人生红点教练** | T + C | 人生红点诊断 Agent | 出口式咨询引导、千人千面提问、产出红点洞察报告 |
| **作业洞察师** | R | Flomo 洞察 Agent | 从海量作业中洞察背后动机和内心追求 |
| **搜索调研 Agent（Stella）** | R | Skill 最佳实践研究 | 深度搜索调研、交叉验证、撰写结构化报告 |
| **产品设计师** | P | 官网研究 + Skill 最佳实践 | 官网 VibeCoding、产品审美判断 |
| **刻意练习 T Partner** | T | 本课程体系 | 五要素理解与笃定度教练 |
| **五步法分析 Partner** | C | 一堂方法论 | 五步法结构化分析和假设轰炸 |

### 2.3 第三层：配置 Partner（用户自建层）——无限扩展能力

| 维度 | 内容 |
|---|---|
| **核心能力** | 用户可以自行封装系统提示词到固定场景 |
| **封装单元** | 系统提示词 + 数据资产包——一堂课程最小的 AI 交付原子单元 |
| **可部署平台** | 系统提示词、Coze、Skill、Agent（ReACT）、OpenClaw…… |
| **战略价值** | 这是 YAI 的 **「开源能力」**——一堂提供最小单位 + 标准，用户在各自业务场景里自由装配 |

> 🔑 **L6 产品洞察**：YAI 的三个层次不是功能堆叠，而是一个**完整的生态闭环**：
>
> - **课程底座** = 不可替代的专业深度（一堂的壁垒）
> - **官方 Partner** = 最佳实践的标准化输出（一堂的品质保证）
> - **用户自建** = 无限扩展的长尾场景（用户创造的价值）
>
> 这和 iOS 的「系统 + 原生 App + App Store」三层架构逻辑完全一致。YAI 本质上是一个 **AI 原生工作的操作系统**。

## 三、TCPR 角色分工体系——YAI 的「组织设计」

这是 YAI 里最核心的设计思想之一。Truman 的原话是：「我想到了一个绝好的主意：用 TCPR 重构 AI 定位。」

### 3.1 四个角色的定义

| 角色 | 全称 | 一句话定义 | 在 YAI 里的典型 Partner | 解决什么问题 |
|---|---|---|---|---|
| **T** | Teaching Partner（教学） | 变着花样把我教明白，帮我理解和学习 | 刻意练习 T Partner、人生红点教练（T 侧） | 「我不懂，教我」 |
| **C** | Consulting Partner（咨询） | 带着我一步步思考，帮我变得很专业 | 五步法分析 Partner | 「我懂一点但不够深，引导我」 |
| **P** | Practice Partner（实践） | 直接帮我动手解难题，帮我把活儿干完 | 产品设计师、Stella（P 侧） | 「我没空做，帮我做」 |
| **R** | Research Partner（研究） | 帮我从海量信息建模，帮我萃取新规律 | Stella（R 侧）、作业洞察师 | 「信息太多我看不过来，帮我提炼」 |

### 3.2 TCPR 不是四个标签，而是一个「工作流设计模式」

```
一个完整的商业工作流，通常需要四类角色：

遇到一个新课题：
  T（教学）→ 先帮我理解这个课题是什么、为什么重要
  C（咨询）→ 带着我一步步拆解、分析、推演
  R（研究）→ 搜集信息、交叉验证、形成洞察
  P（实践）→ 把洞察变成可交付的产出（报告/设计/方案）
```

> 🔑 **L6 洞察**：TCPR 不是一个分类学，而是一个 **「AI 工作的分工设计模式」**。它回答的问题是：当你想让 AI 帮你工作时，你应该「雇佣」一个四角色团队，而不是一个「万能助手」。

### 3.3 TCPR 与人生红点诊断 Agent 的实战对应

在人生红点诊断 Agent 的开发中，可以清晰看到 TCPR 的影子：

| 开发阶段 | 对应的 TCPR 角色 | 做了什么 |
|---|---|---|
| 注入出口式咨询方法论 | **C（咨询）**——引导式提问框架 | AI 学会了「怎么带着用户一步步思考」 |
| 喂入 Human3.0 + Mr.Ranedeer | **T（教学）+ C（咨询）**——教练魂 | AI 学会了「怎么教、怎么引导」 |
| 配备红点 Datapack | **T（教学）**——专业知识注入 | AI 能「用一堂的方法论来教」 |
| 打磨报告价值感 | **R（研究）**——洞察输出 | AI 能「从对话中萃取洞察，形成报告」 |

## 四、原子单元工业标准——YAI 的「技术哲学」

这是贯穿所有案例、最终在 YAI 上被「产品化」的最核心架构范式。

### 4.1 什么是最小原子单元

```
一堂课程最小的 AI 交付原子单元 = 系统提示词 + 数据资产包

系统提示词（逻辑、工作流和审美）
  ├── 这个 Agent 是什么角色
  ├── 它的工作流是什么
  ├── 它的审美标准是什么
  └── 它的边界是什么

数据资产包（数据、案例、细节）
  ├── 专业知识库
  ├── 最佳实践案例
  ├── 输出模板
  └── 踩坑记录
```

### 4.2 原子单元的产品化——YAI 的三个「最小单位」

Truman 在 YAI 的设计中，把这个思想产品化为三个层次的最小单位：

| 层次 | 最小单位 | YAI 中对应的功能 | 用户能做什么 |
|---|---|---|---|
| **逻辑单位** | 系统提示词 | 配置 Partner——封装系统提示词到固定场景 | 把一堂的方法论和自己的场景结合，定制专用 Agent |
| **数据单位** | Datapack | RAG 课程库 + 自定义数据包挂载 | 调用一堂 200 门课的知识，或挂载自己的数据资产 |
| **角色单位** | TCPR Partner | 官方 Partner + 自定义 Partner | 直接使用或修改官方 Partner，搭建自己的四角色团队 |

### 4.3 原子单元的自由拼接能力

```
同一个系统提示词框架（如「出口式咨询教练」），
挂载不同的数据资产包，可以变成不同领域的专家：

教练框架 + 红点核心理念 Datapack = 人生红点教练
教练框架 + 业务天花板 Datapack = 业务诊断教练
教练框架 + 团队管理 Datapack = 管理教练
教练框架 + 用户研究 Datapack = 用户洞察教练

系统提示词 = 专业骨架
数据资产包 = 领域血肉
骨架可复用，血肉可替换 → 快速装配新专家
```

> 🔑 这个原子单元标准已经在 OpenClaw 云端团队中验证了可装配性——Stella、红点教练、洞察师、产品设计师，全部遵循同一套装配标准。YAI 是这个标准的产品化载体。

## 六、YAI 的「粗糙 MVP」哲学——为什么故意做糙

### 6.1 「粗糙 MVP」的战略意图

Truman 在介绍 YAI 时，明确说的是「非常粗糙的 MVP」「粗糙 YAI」「最粗糙的原型产品」。这不是谦虚，而是一种**刻意的产品策略**：

| 传统产品思维 | YAI 的粗糙 MVP 思维 |
|---|---|
| 先做到完美再发布 | 先跑通核心逻辑，让用户参与打磨 |
| 追求「Wow 效应」 | 追求「内核验证」——课程 RAG、官方 Partner、自定义 Partner 三个假设是否成立 |
| 怕用户看到 bug | 明说「粗糙和各种 bug」，筛选能接受不完美的先锋用户 |
| 大范围推广 | 先 100 个最渴望尝鲜的同学 + 20-30 内部员工，小范围深度测试 |

> 🔑 **L6 产品洞察**：YAI 选择「粗糙 MVP」不是因为能力不够，而是因为**商业管理 AI 的 PMF 不可能在内部想清楚**。它需要真实的用户、真实的场景、真实的使用数据来验证——「商业管理场景的 AI 协作」这件事本身是不是成立的。**粗糙是策略，不是缺陷。**

### 6.2 内测的严格边界设计

| 内测条件 | 内容 | 产品意图 |
|---|---|---|
| **必要条件** | 一堂在籍会员，合伙人指数超过 200 分 | 筛选高投入、高理解力的用户——他们的反馈信号更强 |
| **时间要求** | 每周使用 ≥ 2 小时，每两周提交一份《试用和进步报告》，共 4-5 份 | 确保用户不只是「尝鲜」，而是「深度使用」——只有深度使用才能产生有效反馈 |
| **加分条件** | 渴望落地一堂方法论但缺工具；国内 LLM 高频使用；MBA/教研/NPC | 找「已有方法论基础、只缺工具」的用户——他们能最快验证 YAI 的核心假设 |
| **风险告知** | 接受粗糙和 bug；数据会被收集改善 AI；未来可能失败撤回 | 诚实沟通——建立信任，也让用户有心理准备 |

## 七、YAI 的「独特性」——为什么不能抄一个

### 7.1 友商做不到的三重壁垒

| 壁垒 | 内容 | 为什么别人抄不了 |
|---|---|---|
| **知识壁垒** | 200 门课 RAG——5 年方法论积累的结构化知识库 | 没有一堂 50 万份作业、200 门课、上百个科学原创课题的积累 |
| **审美壁垒** | 出口式咨询、VibeCoding、OSCAR、原子单元标准——Truman 团队打磨出的 AI 协作方法论 | 没有 Truman 级别的「人+AI 双专业」判断力和打磨耐心 |
| **生态壁垒** | TCPR 角色体系 + 官方 Partner + 用户自建的无限扩展能力 | 没有一堂同学群体（创业者、PM、业务负责人）作为高价值场景的「共创者」 |

### 7.2 YAI 真正卖的是什么

```
YAI 不是卖一个「对话工具」。
YAI 卖的是：
  一堂 5 年方法论积累的 AI 化
  + TCPR 角色分工体系
  + 原子单元工业标准
  + 官方打磨的最佳实践 Partner
  + 用户可以自由装配的「AI 原生工作团队」搭建能力

一个裸的 LLM 接口 = 一个诺贝尔文学天才（很聪明，但不专）
YAI = 一个由资深编辑专家组成的专业团队（很专，而且稳定）
```

## 九、可迁移的 L6 原则清单

### 9.1 不要做的事

| 错误 | 为什么不行 | YAI 的正确替代 |
|---|---|---|
| 一上来就做大而全的平台 | 商业管理 AI 太复杂，短期交付不了 | 把问题逐步收敛——提供最小单位（提示词+数据包），让用户自己装配 |
| 做一个「万能商业顾问」Agent | 直接帮你做商业决策的 Agent 短期不太现实 | TCPR 四个专职角色——把「万能」拆成「专能」 |
| 追求产品完美再发布 | 商业管理 AI 的 PMF 不可能在内部想清楚 | 粗糙 MVP——先验证三个核心假设（课程 RAG、官方 Partner、自定义 Partner） |
| 只提供一个空的 LLM 对话界面 | 通用 LLM 缺少专长——每次都在探讨基本原则，每次随机发挥 | 封装好的专家——足够明确的任务、上下文、专业知识、输出预期 |
| 把知识「训练进模型」 | 知识无法更新、不可解释、不可溯源 | RAG 课程库——知识可检索、可引用、可更新 |
| 不给用户自建能力 | 长尾场景无穷无尽，官方永远覆盖不完 | 配置 Partner + 原子单元标准——用户自己装配自己的专家团队 |
| 让所有人来用 | 噪音反馈淹没有效信号 | 严格内测筛选——合伙人指数 200+、每周 2 小时、定期提交报告 |

### 9.2 一定要做的事

| 原则 | 具体动作 | L6 标识 |
|---|---|---|
| **收敛思维** | 「把问题逐步收敛」——找到最小的解决问题单位（提示词+数据包），而不是试图一次解决所有问题 | 战略收敛力——知道什么不做，比知道什么做更重要 |
| **TCPR 角色分化** | 把「一个万能 AI」拆成 T/C/P/R 四个专职角色——每个角色有明确的职责、审美和输出标准 | 分工思维——专才团队 > 通才个人 |
| **知识壁垒化** | 把 5 年的课程积累通过 RAG 变成 AI 可调用的结构化知识——这是任何友商抄不了的 | 知识壁垒 > 技术壁垒 |
| **原子单元标准化** | 系统提示词（逻辑）+ 数据资产包（知识）= 最小交付单元——可自由拼接、跨平台部署 | 工业化标准——不是手工作坊，是流水线 |
| **三层产品架构** | 课程底座（专业深度）+ 官方 Partner（最佳实践）+ 用户自建（无限扩展） | 平台思维——不只是产品，是生态 |
| **粗糙 MVP 验证假设** | 只实现三个产品内核（课程 RAG、官方 Partner、自定义 Partner），其他全砍 | 假设驱动——MVP 不是功能少，是只做验证假设必须的功能 |
| **严格筛选共创者** | 内测不是「让更多人用」，而是「让对的人深度用」 | 信号质量 > 用户数量 |
| **诚实沟通风险和不确定性** | 明确说「粗糙和各种 bug」「未来可能失败撤回」「数据会被收集」 | 信任是粗糙 MVP 能跑的前提 |
