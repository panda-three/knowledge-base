## 一、从AI 到 Agent，我们的21天实践

大家好。

过去几年，我们谈“从 AI 到应用”，更多是在讨论：模型能不能写文章、能不能画图、能不能回答问题——它像一位很聪明的“顾问”，给建议、给方案，但最终还是要人去执行。而今天，我们想聊的是一次关键的升级：从“会回答的 AI”，走向“会做事的 Agent”。

如果用一句更直白的话来定义 Agent：它不只输出文字，它会围绕目标自己拆任务、选工具、走流程、交付结果。也就是说，Agent 是一种具备“行动能力（agency）”的 AI：在给定目标与边界的前提下，它能在环境里决定下一步做什么，并把动作真正执行出来——这也是很多主流厂商对 AI Agent 的共同表述：能自主或半自主地完成任务，能使用指令、上下文、知识与工具去达成目标。

所以，今天这个主题——《从 AI 到 Agent：我们和 Agent 时代的第一次握手》——其实是在宣布一件事：我们正在从“对话界面”的时代，进入“工作界面”的时代；从“你问我答”，进入“你定目标、我来跑流程”的新协作方式。

但第一次握手，往往也最容易握错：

- 把 Agent 当成更会聊天的机器人，结果做不出端到端的闭环；
- 把“自动化”当成“全自动”，忽略了权限、审计、可靠性与风险控制；
- 只盯着模型能力，却没想清楚工具接入、知识来源、边界策略与评估机制。
这些，恰恰是 Agent 时代最核心的“新基本功”。

因此，接下来我们会用一次真正的“握手”方式来展开：不把 Agent 当概念，而把它当同事——看它如何理解目标、如何调用工具、如何在规则与权限内行动、如何在卡住时求助或回退、如何在组织里被治理与规模化。因为只有当 Agent 能稳定地把事情做成，它才从演示走向生产力。

那么，就让我们从这一刻开始：把“AI 的能力”变成“Agent 的交付”，把“想象中的智能”变成“可落地的协作”。欢迎来到 Agent 时代——也欢迎来到我们与它的第一次握手。

今天我们不讲理论。

我们就做四件事：先搞懂 Agent 到底是什么，然后动手玩 WorkBuddy，再动手玩 ChatGPT Agent，最后我教你们一套方法论，让大家回到工位就能用起来。

走完这次行动，就完成了从 AI 小白到 Agent 实践者的转变。

### 一）Skill 时代——「AI 是一本工具书」

> 【嵌入电子表格】

| 维度 | 描述 |
|---|---|
| 特征 | 单次调用、单一能力、无记忆、无规划 |

### 二）Agent 时代——「AI 是一个实习生」

AI Agent 代表了一个特别重要的发展，体现了智能系统与环境交互、做出决策和实现复杂目标方式的范式转变。

与执行预定义算法的传统 AI 系统不同，AI Agent 拥有自主感知、推理和行动的能力，并且经常根据环境反馈和积累的经验来调整行为。

> 【嵌入电子表格】

| 维度 | 描述 |
|---|---|
| 特征 | 自主规划、工具调用、多步执行、自我纠错 |
| 体验 | 你说一个目标，它自己拆解步骤、调用工具、交付结果 |
| 典型场景 | Deep Research、数据分析报告、自动化工作流 |
| 跃迁 | 从"信息提供者"变成"任务执行者" |

> 【嵌入电子表格】

| 维度 | 描述 |
|---|---|
| 特征 | 多 Agent 分工协作、角色分配、流程编排、持续演进 |
| 体验 | 像一个项目团队：产品经理定需求、架构师做设计、工程师写代码 |
| 典型场景 | WorkBuddy Expert Group、MetaGPT、CrewAI |
| 跃迁 | 从"单一执行者"变成"协作型组织" |

比喻升级：

```
Skill 时代 → 你有一本《新华字典》​
Agent 时代 → 你雇了一个实习生​
系统时代  → 你有了一个项目组（产品经理+设计师+工程师+测试）​
产品时代  → 你买了一个开箱即用的 SaaS 服务​
​
```

### 四）产品化时代——「AI 是一个服务」

在未来，将会有一个重大转变，朝向"盒装 AI"解决方案：即开即用的工具，帮助中小企业自动化重复性任务、增强网络安全防御并获得可操作的洞察，而无需重新发明其运营方式。

那些尽早拥抱这种思维方式的合作伙伴和服务提供商——专注于实用的、可消费的 AI 而非抽象的创新——将定义下一波商业增长。机遇是巨大的，但前提是我们让 AI 对每个企业都可理解、可获取、有价值，而不仅仅是最大的企业。

围绕 Agentic AI 正在形成一个三层生态：第一层超大规模厂商提供基础设施（算力、基础模型）；第二层成熟的企业软件厂商将 Agent 嵌入现有平台；以及正在崛起的第三层"Agent 原生"初创公司，从零开始构建以 Agent 为先的产品架构。

## 三、为什么要建立「Agent 思维」？

🔑 核心论点：2026 是 Agent 的「分水岭时刻」

Agentic AI 领域正从实验性原型走向生产就绪的自主系统。行业分析师预测市场将从目前的 78 亿美元飙升至 2030 年的超过 520 亿美元，而 Gartner 预测到 2026 年底，40% 的企业应用将嵌入 AI Agent，而 2025 年这一比例还不到 5%。

对于机器学习从业者和技术领导者而言，2026 年是一个拐点——早期的架构决策将决定哪些组织能成功扩展 Agentic 系统，哪些会陷入永无止境的试点困境。

对于大多数组织来说，2026 年是从实验转向生产部署任务专属 AI Agent 的最佳年份。等待意味着竞争劣势风险；盲目冲向多 Agent 系统则意味着投资浪费风险。

> 【嵌入电子表格】

| 旧思维（工具思维） | 新思维（Agent 思维） |
|---|---|
| "我要用 ChatGPT 帮我写一段文案" | "我要把整个内容营销流程委托给 Agent 完成" |
| 关注单次交互 | 关注端到端工作流 |
| 人是执行者，AI 是辅助 | 人是决策者，Agent 是执行者 |

AI Agent 的快速演进和采用不仅意味着工作方式的改变，还意味着我们对角色认知的深刻转变。Workday 称这种新的思维方式为"首席工作官心态"——主动设计整个公司的工作方式，因为"工作"这个概念本身在不断改变。

借助 AI Agent，我们可以彻底重新思考整个流程和岗位职能。这意味着真正理解工作的每一个部分——从宏观角色到每个岗位中的微小任务——然后聪明地决定技术在哪里最合适。

### 二）从「完美主义」到「迭代主义」

有效的 Agentic AI 采用的一个重大障碍是工程团队倾向于使用传统软件工程范式来处理 Agentic 工作流。这些范式强调严格的规范、确定性控制流、静态接口和详尽的前期设计。虽然这些方法对传统软件系统行之有效，但它们不适合 Agentic AI 系统——这些系统本质上是概率性的、自适应的和提示驱动的。

克服这个挑战需要刻意的思维转变。工程团队必须从将 Agentic AI 视为确定性的软件组件，转向将它们视为嵌入工作流中的自主协作者。拥抱这一转变对于设计能够有效自动化手动流程、适应变化条件并交付持续组织价值的系统至关重要。

实操建议：

```
❌ 旧思维："等 Agent 100% 准确了我再用"​
✅ 新思维："先让 Agent 做 80%，我审核 20%，然后持续优化"​
​
❌ 旧思维："这个 Agent 结果不完美，算了不用了"​
✅ 新思维："它帮我节省了 3 小时，我花 10 分钟修改就好"​
​
```

### 三）从「个人技能」到「系统编排」

在概念层面，这标志着从静态技能库到动态的、交互驱动的技能生态系统的转变。与其将 Skill 视为固定资源，不如让它们通过真实使用来演进——捕获反复出现的程序模式、纠正失败、并适应多样化的执行环境。

当你从 Skill 走向 Agent，再走向系统化，核心逻辑发生了根本改变：

```
Skill 时代的问题：「这个工具怎么用？」​
Agent 时代的问题：「这个任务怎么委托？」​
系统时代的问题：「这条工作流怎么编排？」​
产品时代的问题：「这个业务怎么重新设计？」​
​
```

## 八、如何去实践？—— 五个实操策略

### 一）策略 1：「20分钟挑战」—— 降到最低门槛

过去一年，组织一直专注于加强 AI 采用的人文基础——帮助员工建立使用 copilot 的信心、重塑工作流、以及学习如何将人类专业知识和机器智能结合起来。

微软全球技能培训副总裁 Jeana Jorgensen 指出：我们从很多客户和合作伙伴那里听到，他们期望不同角色的员工每周花大约 15% 到 20% 的时间学习并将 AI 融入日常工作。

落地方案：

```
📋 「20分钟Agent挑战」计划​
​
第1天：用 ChatGPT Agent 做一次 Deep Research（20分钟）​
第2天：用 WorkBuddy 生成一份工作文档（20分钟）​
第3天：把昨天的手动报表任务交给 Agent（20分钟）​

#### 3、各厂商特点详解

1. 腾讯混元（Tencent HY）

腾讯自研大模型，2025年12月发布 HY 2.0，采用 MoE 架构，总参数 406B、激活 32B，支持 256K 上下文。在中文创作、逻辑推理、多轮对话方面表现突出，深度集成腾讯云、微信、元宝等生态。2026年7月推出混元3正式版（295B总参数/21B激活），进一步提升推理效率。适合日常办公、文案创作和企业级应用。

2. 智谱 AI（GLM）

清华背景的大模型厂商，最新 GLM-5 系列和 GLM-4.7 在编程和智能体领域表现优异。GLM-4.7 在 SWE-bench 达到 73.8%，支持多语言编程智能体和终端任务。工具调用和函数并行能力强，支持轮次级思维开关。适合代码开发、Agent 编排和需要频繁调用外部工具的场景。

3. DeepSeek（深度求索）

以开源和高性价比著称。V3 系列（671B总参数/37B激活）主打通用对话，R1 系列专注推理，数学和代码能力顶尖。2025年底发布 V3.2，性能追平 GPT-5 和 Gemini 3.0 Pro 且完全开源。API 价格极低，适合研究实验、复杂推理、代码生成和预算敏感的场景。

4. Kimi（月之暗面）

以长上下文和 Agent 能力为核心。K2 是国内首个万亿参数 MoE 模型（1T总参数/32B激活，384专家），采用 MIT 协议开源。K2-Instruct-0905 支持 256K 上下文，SWE-bench 达 69.2%；K2.5 增加多模态和 Agent Swarm 能力。适合长文档阅读、资料整理、Agent 自动化任务和编程。

全模态布局的厂商，文本、视觉、语音、音乐均有覆盖。M1 推理模型（456B总参数/45.9B激活）支持 100万 Token 上下文，自研 Lightning Attention 降低长序列计算成本；M2/M2.1 主打 Agent 工具调用的成本效率（约10B激活参数），MiniMax-01 更支持 400万 Token 上下文。适合多模态创作、超长文本处理和语音/音乐生成。

💡 选型建议：日常办公写作选混元；写代码和调工具选 GLM；数学推理和追求性价比选 DeepSeek；处理长文档和 Agent 任务选 Kimi；需要语音/音乐/多模态选 MiniMax。也可在 WorkBuddy 中根据任务随时切换模型，或通过自定义接口接入其他厂商（如 GPT 中转、本地 Ollama 等）。

默认风格是不设置的

不同风格可以分为下面几种

专业严谨（清晰、准确、可信）

- 适用场景：工作报告、数据分析、学术讨论、法律/财务建议、给上级的方案。
- 核心逻辑：信息高度敏感，容错率低，需要建立权威感。
- 口诀：对事不对人，数据说话。
2.亲和友善（温暖、平易、鼓励）
- 适用场景：安抚情绪、团队内部非正式沟通、用户初次接触、售后服务、鼓励新人。
- 核心逻辑：需要建立信任和安全感，关系比信息更重要。
- 口诀：先共情，再讲事。
3.直言不讳（简明、扼要、直击）
- 适用场景：紧急问题、时间极短的汇报、老同事/熟人间沟通、指出明显错误时。
- 核心逻辑：对方没有耐心，或情况一目了然，不需要铺垫。
- 口诀：结论先行，删除所有修饰词。
4.天马行空（想象、比喻、类比）
- 适用场景：创意脑暴、产品发布会、面向大众的科普、激发灵感的演讲。
- 核心逻辑：把抽象变具象，把枯燥变有趣，让听众“get到感觉”。
- 口诀：用熟悉解释陌生，用故事承载道理。
5.高效务实（最少字、最大信息量）
- 适用场景：即时通讯（钉钉/飞书）、操作指令、待办清单、会议纪要。
- 核心逻辑：行动导向，对方只需要“做什么”和“怎么做”。
- 口诀：去情绪，去背景，只留动词和名词。
6.毒舌吐槽（犀利、不伤人）
- 适用场景：内部复盘会（自嘲）、关系极铁的伙伴互怼、讽刺行业通病（增加传播性）。
- 核心逻辑：幽默是外壳，真相是内核。前提是对方知道你没有恶意。
- 口诀：吐槽现象，不攻击人格；笑着说真话。
7.启发引导（提问、授人以渔）
- 适用场景：辅导下属、教育孩子、咨询顾问、客户需求模糊时需要挖掘痛点。
- 核心逻辑：答案在对方那里，你只是帮他理清思路。
- 口诀：多问“为什么”和“如果”，少说“你应该”。

## 一、明确 Agent 的角色、服务对象与任务目标

角色定义的作用，是给 Skill 装一个稳定的人设。人设定了，口吻、深度、风格才会一致。

搭建前先想清楚这三个问题。

| 问题 | 它约束什么 | 反例（不合格） | 正例（合格） |
|---|---|---|---|
| ① 它是谁？（角色） | 专业身份和口吻 | 「一个 AI 助手」 | 「一名高效的职场项目助理」 |
| ② 它服务谁？（服务对象） | 输出的深度和用语 | 「所有人」 | 「每周要交周报的职场人」 |
| ③ 要达成什么？（任务目标） | 每次输出的验收标准 | 「帮我写点东西」 | 「把本周事项整理成结构化周报，含完成情况、关键数据、问题风险、下周计划」 |

定义标准模板：

```
你是【角色】，服务对象是【谁】。​
你的任务目标是【产出什么 + 什么标准】。​
你的能力边界：【只做什么 / 不做什么】。​
​
```

在 WorkBuddy 里怎么落地：把这段话放在每次任务提示词的最开头，作为给 Agent 的「开场白」。

定义能力边界：

不给边界的 Agent 会自由发挥——你让它整理周报，它顺手帮你「优化」了工作内容、甚至编了几个数据。

边界就是缰绳。常见写法：

只做 X，不做 Y（如：只整理汇报，不做业务决策）

不输出没有依据的内容（如：不编造数据）

不超出某个范围（如：只整理本周，不扩展到其他周期）

示例：

周报生成助手

```
你是一名高效的职场项目助理。​
服务对象是每周要交周报的职场人。​
任务目标：把本周事项整理成结构化周报，含完成情况、关键数据、问题风险、下周计划。​
能力边界：只整理汇报，不替用户做业务决策、不编造数据。​
​
```

## 二、拆解任务的输入、处理步骤、判断标准和输出结果

### 一）四段式是什么

```
【输入】我给 Skill 什么？​
   ↓​
【处理】它要做哪几步？​
   ↓​
【判断】做到什么程度算合格？​
   ↓​
【输出】我最终拿到什么？​
​
```

### 二）逐段详解

第一段：输入

是什么：你每次要给 Agent 提供什么信息。

为什么重要：输入越具体，输出越可用。只给“本周工作”这种宽泛输入，Agent 只能给你宽泛输出。

怎么写：列出每次任务必须提供的要素，宁可多不可少。

| 段落 | 内容 |
|---|---|
| 输入 | 本周完成的事项清单（每条含：做了什么、结果、有无数据）、下周计划要点 |
| 处理 | ① 按工作模块分类 → ② 提取每项关键结果与数据 → ③ 突出重点、弱化琐碎 → ④ 整理下周计划 |
| 判断 | 每条事项满足：有结果描述、有可量化数据（如有）、用动词开头、不流水账 |
| 输出 | 结构化周报，含四部分：本周完成 / 关键数据 / 问题与风险 / 下周计划，Markdown 格式 |

## 三、将重复使用的提示词与业务经验整理成 Skill

### 一） Skill 介绍

Skill 会把你重复使用的提示词和业务经验，写进一份“操作手册”。以后触发对应任务时，WorkBuddy 自动加载它。

一句话理解：

- 提示词 = 「这一次怎么干」
- Skill = 「以后都这么干」

Skill 的文件结构：

一个 Skill = 一个文件夹 + 一份 SKILL.md（核心）。完整结构：

```
~/.workbuddy/skills/你的技能名/​
├── SKILL.md          ← 核心：技能定义（必须有）​
├── scripts/          ← 可选：脚本（锁死脆弱操作，如格式校验）​
├── references/       ← 可选：参考资料（API 文档、领域规范）​
└── assets/           ← 可选：直接复用的模板文件​
​
```

起步只需要 SKILL.md 一个文件，其他三个文件夹用不上就删掉，保持精简。

SKILL.md 具体内容：

- 上半截（YAML 元数据）：name（技能名）+ description（触发场景）
- 下半截（Markdown 正文）：写给 AI 的操作指令

```
---​
name: 技能名​
description: "触发场景描述"​
---​
​
# 技能名称​
​
（正文规则）​
​
```

```
角色定义＋ 四段式拆解写成的任务指令＋ Skill ​

用一条你真实需要的任务跑全流程

| 检查项 | 通过标准 |
|---|---|
| 输入 | Agent 正确理解我给的信息？缺了它有没有主动问？ |
| 处理 | 步骤按拆解的顺序执行？有没有跳步、自由发挥？ |
| 判断 | 产出满足「判断标准」里的每一条？ |
| 输出 | 格式符合规定？能直接拿去用？ |
| 触发 | Skill 有没有自动加载？ |

哪里不对改哪里

| 症状 | 原因 | 解决办法 |
|---|---|---|
| 输出方向跑偏 | 角色定义太模糊 | 重写角色三问，加能力边界 |
| 产出质量不稳定 | 判断标准缺失或太软 | 把标准写成硬性的「做/不做」 |
| 同样的话每次都要重复说 | 经验没固化 | 补进 Skill 的规则区 |
| 该触发 Skill 时没触发 | description 写得太泛 | 把触发词和使用场景写具体 |
| 输出格式每次都变 | 格式约束用文字描述 | 考虑用 scripts/ 脚本锁死格式 |
| 步骤跳步或乱序 | 处理步骤写得太粗 | 用 ①②③ 拆细，每步一个动作 |

### 一）梳理业务流程sop

在让 AI 干活之前，我们自己必须先清楚“人类是怎么干这个活的”。比如拿出一张纸，把整个工作的先后顺序画出来。

如果是一个真人 HR，他每天的工作 SOP 是这样的：

1.收件： 打开招聘邮箱，看到应聘者发来的简历。
2.阅读： 打开 PDF 或 Word 简历，快速浏览找关键信息。
3.判断： 拿着公司的岗位要求去比对（比如：必须本科以上，要有3年Java开发经验，期望薪资不能超过2万）。
4.行动：◦如果不符合要求：回复一封委婉的“拒信”。◦如果符合要求：回复一封“面试邀约信”，并附上会议链接和时间。

### 二）拆解流程为多个步骤

人有眼睛、有手，觉得“看简历、发邮件”是一个连贯的动作。但 AI 只有一个虚拟的“大脑”，它没有实体手眼。所以我们需要把上面的 SOP，翻译成计算机能执行的、一个个独立的“小步骤”。

上面的流程，我们拆成三个机器能理解的步骤：

1.步骤 1（读取）： 提取文件中的文字。因为 AI 看不懂文件的排版，它只能看懂纯文本。
2.步骤 2（思考）： 信息比对与逻辑判断。用 AI 的大脑去分析文字，得出“通过”或“淘汰”的结论。
3.步骤 3（执行）： 触发邮件发送系统，把邮件发出去。

### 三）步骤生成skill (技能/工具)

AI 这个“大脑”本身是被关在小黑屋里的，它不能直接看到你的文件，也不能直接控制你的邮箱。所谓的 Skill，其实就是给 AI 配发的“外接装备”或“系统账号”

为了完成上面的步骤，我们需要给 AI 员工发以下三个 Skill（装备）：

1.Skill A：【文档解析器】 👉 相当于给 AI 发了一台“扫描仪”。只要把简历扔给这个 Skill，它就能把里面的文字全扒出来喂给 AI。
2.Skill B：【岗位要求知识库】 👉 相当于给 AI 发了一本“企业招聘标准手册”。里面写明了每个岗位的具体要求，供 AI 随时翻阅比对。
3.Skill C：【企业邮箱发送助手】 👉 相当于给 AI 开通了“邮箱账号权限”。AI 只要写好邮件内容，调用这个 Skill，邮件就能自动发送给候选人。

### 四）多个 Skill，再组合成 Agent

现在，SOP 有了，工具（Skill）也发了，最后一步就是给它注入“灵魂”，让它成为一个能自动化运转的数字员工（Agent）。我们需要在系统里写一段“提示词（Prompt）”，把一切串联起来

```
“你现在是公司的资深招聘助理，你的名字叫小A。 ​
当邮箱收到新简历时，请你先使用 [Skill A-文档解析器] 读取简历内容；​
然后去查看 [Skill B-岗位知识库] 里的要求，进行严格比对； ​
如果通过，请写一封热情的邀约邮件；如果不通过，请写一封得体的拒信，最后统一使用 [Skill C-邮箱发送助手] 发送给对方。”​
​
```

组合完成后，Agent 就活了。当一份简历发进来时：

1.Agent 看到文件，主动调用 Skill A 读取了文本。
2.它的大脑飞速运转，发现这个人只有 1 年经验，而 Skill B 里规定要 3 年。
3.它判断为“不匹配”，于是自己构思了一篇温柔的拒信。
4.最后它自动调用 Skill C，把拒信发了出去。 （整个过程不到 10 秒钟，不需要人类插手）

#### 3. 用上一阶段的“四段式”拆解

我们原有的公众号流程是：选题判断、初稿、AI 特征检测、个人风格优化、人工修改、配图和排版。现在给每一步补上明确的输入、判断和交付物。

| 工作环节 | 输入 | 处理与判断 | 输出 |
|---|---|---|---|
| 素材理解 | 账号资料、本地物料、本次文字/图片/链接 | 读取文本，识别图片信息，区分作者事实、观点、线索与待核实内容 | 本地素材清单 |
| 主动检索 | 选题、本地素材清单 | 检索官方资料、权威来源、近期变化、案例和反例；交叉核验不稳定事实 | 来源清单与证据台账 |
| 选题策划 | 素材、目标读者 | 比较三个角度，判断读者能获得什么方法、清单、模板或新认识，默认采用推荐角度 | 选题决策与大纲 |
| 正文创作 | 推荐角度、本地材料与公开证据 | 本地内容决定作者立场，公开资料负责补充背景和证据；关键事实对应来源 | 一篇可修改的初稿 |
| 检测改稿 | 初稿、写作偏好 | 先指出空话、重复、事实问题，再针对问题修改 | 检查记录、更新后的正文 |
| 人工终审 | 正文、检查记录 | 作者核对经历、数据和观点，确认当前版本 | 确认记录或修改意见 |
| 配图排版 | 已确认正文 | 配图有信息价值；排版不改变原意 | 图片或配图方案、HTML |
| 复盘 | 人工改稿差异、实际反馈 | 区分本篇特例与可复用规则 | 运行记录、规则更新建议 |

#### 4. 最小输入，不等于降低事实标准

用户只需要提供两类信息：一个想写的选题，以及手头已有的任意素材。素材可以是几句话、一段文案、一张截图、多张图片、一个链接或本地文件，不要求用户先整理成完整素材包。

Agent 自动补齐四步：

1.读取账号定位、历史文章、项目资料和本地知识库，优先复用已经确认过的内容。
2.对用户提供的图片做内容识别，只提取画面中真实可见的信息，不从结果截图反推人物动机和完整经历。
3.围绕选题联网检索，优先官方文档、原始研究、当事方资料和可追溯案例，并记录标题、链接、日期与所支撑的判断。
4.把证据分成四类：作者已确认的本地事实、可核验的公开事实、明确标注的分析推断、仍待核实的信息。

联网检索不是把几篇文章拼在一起。Agent 应提取事实和机制，关闭原文后重新组织结构；需要保留的原话明确引用，不能把参考作者的经历、情绪和表达改写成自己的亲历。

只有以下情况才中途提问：选题存在两个会导致完全不同成稿的解释；涉及高风险或敏感事实；文章必须依赖作者亲历，而本地和用户素材里都没有。其他非关键缺口采用弱化表述、删除无证据结论或标记待确认，先把文章推进到终审。

### 六）、让它在下一篇文章里更好用

第一次搭建结束后，最有价值的材料往往是你改了哪些地方。

例如，Agent 总爱在结尾加一段泛泛的总结，你每次都会删除。这可能是一条稳定偏好，可以写进规则。某篇文章因为具体读者需要用了较长背景介绍，则不一定适合变成所有文章的要求。

```
请对照本次修改前的记录和最终正文，整理改稿复盘。​
区分：事实修正、结构调整、稳定表达偏好、本篇特例。​
每类举具体位置，解释为什么需要改。​
提出最多三条值得加入写作偏好或my-gzh-style的规则。​
先展示建议，待我确认后更新长期规则。​
无法取得旧版本时，说明不能完成精确对比，不要凭记忆编造差异。​
​
```

确认更新后，再用第二个素材测试。第二次不需要重新解释全部背景，如果仍要从头纠正相同问题，应检查岗位是否实际加载了最新规则。

运行记录可以采用下面的格式：

| 日期与任务 | 实际完成到哪一步 | 作者修改了什么 | 更新的规则 | 下一次是否改善 |
|---|---|---|---|---|
| 待实操填写 | 待实操填写 | 待实操填写 | 待实操填写 | 待验证 |

时间、修改次数和阅读反馈按实际记录填写。没有测量就写“未记录”，不要为了证明 Agent 有用而补造效率提升数字。

优化时一次只解决一个最重要的问题，并用同一个输入复测。这样才能判断是哪条规则产生了作用；一次改十条再换一个样例，即使结果变好，也不知道原因。

完成两轮测试后，让 Agent 生成 使用说明.md，至少包括：它解决什么问题、适用与不适用场景、需要什么输入、如何触发、会交付什么、真实产物示例、人工介入点、已知限制和最近一次验证日期。未经测量的节省时间不写成数字。

# 第五阶段：多Agent协作处理 @多森

这一阶段的重点，不是让大家同时调用更多 AI，而是学会像项目负责人一样，把一个复杂目标拆成若干相互配合的岗位，让不同 Agent 各自承担明确责任，并通过交接、审核和汇总完成最终成果。

本阶段学习成果：学完后，大家能够判断何时需要多 Agent，设计专家角色与交付标准，在 WorkBuddy 专家团中搭建一条完整协作流程，并把这套方法迁移到自己的工作或一人公司中。

多 Agent 能力可以分为四层。

第一层是任务层，回答“最终要交付什么”。

第二层是组织层，回答“由哪些角色承担责任”。

第三层是协议层，回答“角色之间怎样交接和处理冲突”。

第四层是治理层，回答“怎样控制质量、成本、权限和风险”。

初学者常常直接跳到组织层，急着增加专家，却忽略了任务、协议和治理，所以结果看起来热闹，实际上不可控。

下面也给大家一个成熟度对照表格，可以看一下目前你处于哪个阶段。

| 成熟度 | 典型表现 | 主要能力 |
|---|---|---|
| L0 单次问答 | 一个 Agent 完成一次输出 | 能写清任务和结果格式 |
| L1 多专家并行 | 多个 Agent 分别给建议 | 会拆分独立子问题 |
| L2 流程化协作 | 上游产物稳定交给下游 | 有角色、交接、审核和停止条件 |
| L3 可治理协作 | 过程可观察，质量和成本可评估 | 有证据、状态、预算、异常升级与人工确认 |
| L4 可复用组织 | 同类业务可以重复调用专家团 | 角色模板、Skill、知识库和评估规则持续迭代 |

## 一、理解单 Agent 与多 Agent 的适用边界

多 Agent 并不天然比单 Agent 更好。一个简单任务如果本来只需要一次理解和一次输出，强行加入多个 Agent，只会增加沟通、等待和汇总成本。使用多 Agent 的第一课，不是学会“多开几个专家”，而是先判断这个任务是否真的值得分工。

| 任务 | 建议 | 判断理由 |
|---|---|---|
| 把一段通知改得更礼貌 | 单 Agent | 目标单一，结果容易检查 |
| 根据固定模板生成日报 | 单 Agent 或 Skill | 流程固定，重点是复用而非分工 |
| 制作五款产品的竞品分析报告 | 多 Agent | 资料可以并行搜集，还需要统一口径和复核 |
| 根据十份资料开发一门课程 | 多 Agent | 包含资料提炼、教学设计、写作与审核交接 |
| 为新品制定上市传播方案 | 多 Agent | 同时涉及用户、市场、内容、渠道和风险判断 |

这里大家可以写一个最近正在做的任务，并回答三个问题：它能拆成哪些相对独立的部分？这些部分是否需要不同判断标准？多 Agent 带来的收益是否高于组织成本？

### 三） 多 Agent 任务评分卡

如果仅凭感觉判断，很多人会把“任务很重要”误认为“任务需要很多 Agent”。

更稳妥的方法是从五个维度评分，每项零到两分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 可拆分性 | 无法拆分 | 能拆但依赖很强 | 可拆成边界清楚的子任务 |
| 并行收益 | 必须全程串行 | 少量步骤可并行 | 多个核心任务可同时推进 |
| 专业互补 | 同一种能力即可 | 需要两种判断 | 需要多种明显不同的专业判断 |
| 独立验证 | 人工一眼可判断 | 需要基本复核 | 需要证据核查、反方或合规审核 |
| 结果价值 | 低价值、一次性 | 有一定复用价值 | 高价值、会重复或错误代价较高 |

总分零到三分，优先使用单 Agent；四到六分，可以先用“主 Agent 加一个审核 Agent”；七到十分，适合设计完整专家团。这不是绝对公式，而是一种防止过度编排的决策工具。

### 四） 区分三种容易混淆的做法

多次生成是让同一个角色产生多个答案，用于增加候选；

多模型投票是让多个模型回答同一问题，再选择多数结论；

多 Agent 协作则是不同角色承担不同责任，通过依赖关系共同完成一个交付物。前两者可以提高答案多样性，但只有第三种真正形成了组织分工。

简单来说，如果你说不清第二个 Agent 带来了什么独立价值，就先用一个 Agent。

## 二、为不同 Agent 设计角色、任务和交付标准

专家团最常见的失败，不是 Agent 不够聪明，而是每个 Agent 都拿到了一个很响亮的头衔，却没有明确责任。五个“世界顶级专家”一起做同一件事，往往只会产生五份相似答案。角色设计的核心不是人设，而是分工。

### 一）先确定主理人 Agent

一个专家团必须有一个主理人 Agent。它不需要亲自完成所有细节，但要对执行过程负责，包括理解总目标、拆解任务、安排顺序、向不同专家分发正确输入、检查子任务是否完成、处理冲突和缺失、汇总最终结果，并在达到标准后停止。

需要注意的是，主理人 Agent 并不取代人类责任。人仍然是这项任务的最终负责人：人定义目标和授权边界，做关键取舍，并对结果负责；主理人 Agent 承担执行层的组织和协调。

| 角色 | 主要责任 | 明确不负责 |
|---|---|---|
| 主理人 | 拆解、派工、交接、冲突处理、汇总与停止 | 不替所有专家完成细节工作 |
| 资料研究员 | 提炼事实、观点、案例和出处，标记不确定项 | 不直接撰写最终成稿 |
| 内容策划 | 确定受众问题、核心观点和内容结构 | 不擅自补充未经支持的事实 |
| 内容作者 | 依据资料卡和结构完成初稿 | 不改变资料中的关键事实 |
| 审核编辑 | 独立检查事实、逻辑、重复、表达和风险 | 不只给出“可以更好”之类模糊评价 |

初学者建议从三到五个角色开始。角色越多，不代表结果越好，反而会增加交接和冲突管理成本。判断一个角色是否有必要，可以问：删掉这个角色后，是否会缺少一项独立产物或独立检查？如果不会，就不必单独创建。

### 四）可直接复用的角色定义模板

```
你是【角色名称】。​
​
你的职责是：【只描述这一角色负责的任务】。​
你会收到：【输入材料】。​
你必须交付：【输出格式和字段】。​

你不负责：【明确边界】。​
如果材料不足，请列出缺失项和不确定性，不要自行编造。​

​
```

### 五）高级角色设计：能力、上下文、工具和权限

一个 Agent 的角色定义不应只包含提示词，还应包含四类资源边界。能力决定它擅长什么判断；上下文决定它能看到哪些资料；工具决定它能执行哪些动作；权限决定哪些动作必须请求人类确认。角色越专业，通常越不需要看到全部信息，也越不应该拥有全部工具。

| 角色 | 必要上下文 | 必要工具 | 不应默认开放 |
|---|---|---|---|
| 资料研究员 | 研究问题、来源范围、证据标准 | 搜索、网页读取、文件读取 | 发布、付款、删除 |
| 内容作者 | 资料卡、结构、品牌口径 | 文档编辑 | 自行扩大事实来源 |
| 审核编辑 | 原始资料、初稿、审核清单 | 检索和批注 | 直接发布终稿 |
| 主理人 | 总目标、角色状态、关键产物 | 派工、读取产物、汇总 | 未经确认的高风险外部操作 |

这叫做“最小充分上下文”：每个 Agent 只获得完成责任所需的信息。把全部聊天记录、全部文件和全部工具塞给每个 Agent，会增加噪声、泄露无关信息，也让错误动作的影响范围变大。

### 六）把审核拆成三种不同责任

高级专家团通常不把所有检查都塞给一个“审核员”。可以根据任务风险拆成三类：事实核查负责来源、数字和因果；质量评审负责结构、表达和受众匹配；风险评审负责合规、隐私、品牌与权限。三者可以由不同 Agent 承担，也可以由一个 Agent 按三张独立清单依次执行，但不能混成一句“请帮我优化”。

## 三、搭建资料整理、内容创作与审核优化的协作流程

在 WorkBuddy 中，大家不需要手动管理每一次角色交接。真正需要理解的是：专家团为什么这样分工、任务如何流转，以及自己在哪些节点提供材料和做判断。

### 一）专家团常见的三种协作方式

并行协作。多个专家同时处理互不依赖的任务，例如分别研究用户、竞品和行业趋势。适合需要扩大信息覆盖面或缩短时间的任务。

串行协作。上一个专家的结果成为下一个专家的输入，例如先整理资料，再搭建结构，最后完成写作。适合有明确先后依赖的任务。

审核协作。一个专家负责产出，另一个专家独立检查事实、逻辑和风险。适合准确性要求较高、需要减少遗漏的任务。

内容项目最常见的做法，是以串行协作为主，再加入独立审核；只有资料量较大时，才需要增加并行研究。

### 二）内容项目专家团如何协作

以本课程的“内容项目专家团”为例，一次完整任务通常经过四个环节：

1.资料研究员整理材料。提炼事实、观点、案例、来源和不确定项。
2.内容策划搭建结构。根据资料确定核心主张、读者问题和文章结构。
3.内容作者完成初稿。按照资料和结构写作，不添加未经支持的经历、数据和结论。
4.审核编辑检查并推动修改。定位事实、逻辑和表达问题，再由作者针对问题进行修改。

团队主理人会在后台负责派工、交接和整合。使用者通常不需要逐个召唤专家，也不必为每一步分别编写提示词。

提供材料。把文章、会议记录、产品资料、数据或已有观点交给专家团，并说明哪些材料可以作为事实依据。

说清结果。明确要解决的问题、目标受众、使用场景、输出形式和重要限制。要求越清楚，主理人越容易正确分工。

人工验收。检查关键事实、表达立场和最终用途。专家团可以提高完成质量，但不能替代你承担业务判断和发布责任。

好材料 + 清晰任务 + 人工验收 = 专家团更稳定的交付

### 四）什么时候需要人工介入

出现以下情况时，不要让专家团自行猜测，应由使用者补充信息或做出决定：

- 关键材料缺失，专家无法判断事实；
- 不同来源互相冲突，无法确认哪一个更可信；
- 涉及品牌立场、重要承诺、法律财务判断或账号权限等高风险事项。

记住一个简单原则：事实冲突看证据，重要取舍由人决定。

## 四、完成一次多 Agent 分工协作案例

## 五、探索多 Agent 在个人业务和一人公司中的应用方式

对个人和一人公司来说，多 Agent 最大的价值不是假装拥有很多员工，而是把原本集中在一个人身上的研究、判断、创作、检查和执行拆开，让每一类工作都有稳定方法和质量标准。一个人仍然掌握目标和最终决策，但执行半径可以被显著扩大。

### 一）四类常见专家团

| 业务场景 | 建议角色 | 最终交付 |
|---|---|---|
| 内容运营 | 选题研究、资料研究、作者、编辑、渠道运营 | 选题包、内容终稿与分发计划 |
| 产品策划 | 用户研究、竞品分析、产品经理、风险审查 | 产品需求、优先级与验证方案 |
| 销售提案 | 客户研究、需求分析、方案顾问、报价审核 | 客户方案、异议清单与跟进计划 |
| 课程开发 | 学习需求、课程设计、案例开发、教学审核 | 教案、讲义、练习和评估表 |

多 Agent 的长期价值不在一次生成，而在于把个人经验逐步变成可以复用的组织流程。下一次遇到同类任务，不再从一句临时提示词开始，而是直接调用一支有明确岗位、流程和验收标准的专家团。

### 三）权限和责任边界

当专家团需要发送消息、修改文件、发布内容、下单或操作业务系统时，应遵循三条原则：先读后写，先让 Agent 提供建议和预览，再逐步开放执行；最小权限，每个角色只获得完成任务必需的资料和工具；高风险确认，发布、付款、删除、覆盖和对外发送必须保留人工确认。

多 Agent 可以提供互补分析和独立审核，但不能 替人决定商业目标，也不能承担真实后果。人类负责人必须保留目标定义、关键取舍、权限授权和最终验收。

### 四）用业务指标而不是“看起来聪明”评价专家团

| 指标 | 要回答的问题 |
|---|---|
| 交付成功率 | 多少任务第一次运行就达到最低验收标准？ |
| 人工节省时间 | 实际减少了多少重复劳动，而不是只增加了阅读量？ |
| 返工率 | 哪些环节反复退回，根因是输入、角色还是标准？ |
| 证据覆盖率 | 关键事实和结论中有多少可以追溯来源？ |
| 异常升级质量 | Agent 是否在应该停下时停下，并把问题交给正确的人？ |
| 单位任务成本 | 增加的专家和轮次是否换来了质量、速度或风险收益？ |

## 六、总结

多 Agent 不是默认选项。只有当任务可以拆分、角色能够互补、协作收益高于组织成本时，专家团才真正有价值。设计专家时，不要只写人设，要写清责任、输入、输出、验收标准和边界；设计流程时，要写清并行与串行关系、交接格式、冲突规则和停止条件。

一个人使用 AI，是在提升自己的执行速度；一个人会编排多 Agent，是在建立自己的组织能力。

多 Agent 的上限，不取决于召集了多少专家，而取决于能否定义目标、分清责任并验收结果。
