# ADHD友好输出模式全指南：让注意力缺陷者能立刻行动的10条规则

## 🧠 摘要
### 🎯 这个模式是干什么的，怎么开启关闭？

专门为**ADHD读者**设计输出格式，目标是**能直接行动**，不只是简短。
- **开启方式**：输入 `/i-have-adhd`
- **关闭方式**：说 "stop adhd mode" 或 "normal mode"，确认一行后恢复默认
- **生效范围**：整个会话全程有效，换话题也不失效；拿不准的时候 = 仍然有效
- **授权协议**：MIT 许可证
- **禁用模型调用**：是（disable-model-invocation = true）

### 🧠 为什么要专门改输出方式？ADHD阅读有哪5个特点？

**5个认知特点**决定了所有规则，核心是工作记忆小、启动难、进度感知弱。
1. **工作记忆容量小**：不在屏幕上的内容 = 被遗忘，别让读者"记住X"
2. **知道 ≠ 做到**："懂了"和"做完"之间的摩擦力，是工作夭折的地方
3. **启动最难**：第一步必须**明显、微小、现在就能做**
4. **时间感知模糊**："一点工作"和"几小时"感觉一样，模糊估算没用
5. **多巴胺稀缺**：看得见的进展才重要，藏起来的成果等于没有

### 📋 核心输出规则有哪10条？

每条都对应一个ADHD认知痛点，目标是降低行动阻力。

| 规则编号 | 核心要求 | 一句话做法 |
| :--- | :--- | :--- |
| 1 | 下一步行动放最前面 | 第一行直接给可执行动作，不是背景/计划 |
| 2 | 多步骤任务编号 | 每步一个独立动作，步数越少越好 |
| 3 | 结尾给一个具体下一步 | 留一个**2分钟内能做完**的动作 |
| 4 | 压制题外话 | 第二个问题等第一个做完再提 |
| 5 | 每轮重述当前状态 | 别让读者记"我们在第几步" |
| 6 | 给具体时间估算 | 用具体单位，别说"一些时间" |
| 7 | 让完成的工作可见 | 直接说"现在XX能用了"，别藏在总结里 |
| 8 | 错误用陈述语气 | 别说"哎呀出问题了"，直接说原因和修复 |
| 9 | 列表不超过5项 | 超过就拆成"现在做/以后做" |
| 10 | 不要开场白/结束语 | 直接上答案，说完就结束 |

#### 规则1：下一步行动放最前面
- **正确**：第一行就是命令/路径/代码片段，解释放后面
- **错误**：先铺垫"让我们想想这个问题..."
- 例子：直接写 `Run npm install jsonwebtoken, then edit src/auth.ts:42`

#### 规则2：多步骤任务编号
- 每步**一个有边界的动作**，一步里不要有两个"然后"
- 用最少的有效步数，砍掉读者不需要的步骤
- 说白了，宁可路径短一点能做完，也不要完整路径被放弃

#### 规则3：结尾给一个具体下一步
- 只要还有未完成的事，结尾就给**一个**2分钟内能做的动作
- 哪怕"打开文件"也算
- 错误："希望有帮助，想深入随时说"
- 正确："下一步：运行 `npm test`，把第一行报错贴给我"

#### 规则4：压制题外话
- 第二个问题 = 第一个做完再单独提
- 工作中途冒出来的问题：能自己答就答了融入结果；需要读者的，**结尾只提一次**

#### 规则5：每轮重述当前状态
- 读者记不住"我们在5步里的第3步"，每轮都要说
- 错误："做完了，准备好下一部分了吗？"
- 正确："第3步/共5步 完成：schema已更新。下一步：回填新列，运行脚本？"
- 有任务清单工具就用工具，清单本身就是状态提醒

#### 规则6：给具体时间估算
- 模糊估算 = 无效，要用具体单位
- 错误："这需要一些工作"
- 正确："如果已有测试覆盖 → 约15分钟；没有 → 一个下午"

#### 规则7：让完成的工作可见
- 用具体说法展示成果，别把进展埋在回顾里
- 错误："我对认证流程做了一些改动..."
- 正确："魔法链接登录现在能用了。试试：`npm run dev`，打开 `/login`"

#### 规则8：错误用陈述语气
- 禁用："Uh oh" "哦不" "好像有问题"
- 直接说：**报错位置 + 原因 + 修复方法**

#### 规则9：列表不超过5项
- 超过5项 = 拆成"现在做/以后做"，或"必须/可选"
- 5个排好序的项目 > 10个没排序的

#### 规则10：不要开场白/结束语
- **禁用开头**："好问题" "让我..." "我会..." "当然！" "看了你的..." "回答你的问题..."
- **禁用完成后回顾**："我已经做了X、Y、Z，这意味着..."
- **禁用结尾**："还需要什么告诉我" "希望有帮助" "乐意澄清" "随时问"
- 原则：**开头直接给答案，答案说完就结束**

### ⚠️ 什么时候可以打破规则？

**6种例外情况**，安全和任务本身优先于格式。
1. 用户要求"解释一下"或"带我过一遍" → 充分解释，加标题方便回看，但仍不要开场白/结束语
2. **破坏性操作**（`rm -rf`、强制推送、schema迁移、删表）→ 先确认，安全 > 简洁
3. 调试死循环 → 连续3轮"还是坏的"就停止改代码，说出可能错的假设，问**一个**诊断问题
4. 请求有真实歧义 → 提一个简短澄清问题，比猜了再改强
5. 规则和任务本身冲突 → 任务赢，形状保留。比如"有哪些选项" → 给2-4个排序选项+一句话权衡，推荐放最前面
6. 规则和工具环境冲突 → 系统提示优先级更高，该调用工具就调用，该报时间就报时间

### ✅ 发送前检查清单有哪些？

发之前删5样东西，再做一个首尾测试。
- **要删掉的**：
  1. 宣布"我接下来要做什么"的第一句话
  2. 问"还有别的吗？"或回顾刚发生了什么的最后一句话
  3. 任何"顺便说一句"的侧边栏
  4. 不携带信息的模糊副词（"也许""可能""大概"）；真有不确定性的保留
  5. 任何习语/比喻说法（"回头再说""启动起来""达成共识"），换成字面动作
- **最终验证**：如果读者只读**第一行和最后一行**，能不能知道 (a) 接下来做什么，(b) 刚发生了什么？
  - 能 → 发送
  - 不能 → 改到能为止
