# 课程：高效协同Obsidian·02

**一句话结论：** 文件要「人能接着干、AI 能接着改」——靠统一命名规则 + Markdown 清单体；Obsidian 不是必选，是当下「人读+AI 读+批量处理」最顺手的载体。

---

## 一、核心交付

- 一条命名铁律：`00. 主题：具体内容 [版本或阶段].扩展名`。
- 一张选型对比：飞书文档 vs Markdown+Obsidian。
- 一个案例：半肥猫用 AI 把 20 人新媒体团队的活工业化。

## 二、第三阶段：文件还不够，要高效协同

- 26 年两个变化：① 龙虾（自动化工具）降门槛；② Obsidian 普及。
- 一堂协作栈升级为 **龙虾 + Obsidian**（思路源自半肥猫案例）。
- [配图：Obsidian「00.顶层：内核边界」文档，列内核定义与边界规则]

**协作载体的硬要求：**
- 教研可同步协作，AI 也可同步协作。
- 格式用清单体、可批量处理、人读 AI 读都顺。

### 2.1 案例：半肥猫（美业大健康）

| 维度 | 内容 |
|---|---|
| 业务 | 数字化营销，赋能全国 3000+ 线下门店 |
| 旧模式 | 20+ 人新媒体团队做文案/短视频/物料 |
| 痛点 | 月工资十几万二十万，产能还跟不上 |
| 价值 | 团队/业务层面 AI 数据的稀缺价值样板 |

## 三、文件命名规则（可直接照抄）

**统一格式：**
```
00. 主题：具体内容 [版本或阶段].扩展名
```
- 例：`12. 参考：业务公式.md`、`50. 大纲：1小时案例课v2.md`、`91. 复盘：项目文档结构演化.md`。
- 依据 process→archive→workflow；核心目标：**只看文件名和排序，就知道是什么、哪一层、是不是最新**。

| 主体 | 看 | 用 |
|---|---|---|
| 人 | 能否快速理解背景/过程/结论 | 能否接着决策、执行、复盘 |
| AI | 能否读完整、结构化、可信上下文 | 能否继续分析、改、生成、维护 |

## 四、为什么是文件 + 清单体 × Markdown

**为什么要文件，不靠聊天：** 上下文会滚走、会话彼此隔离、人难扫读、AI 难继承、判断埋在口语里。

| 清单体特点 | 对人 | 对 AI |
|---|---|---|
| 专注 | 少花时间排版 | 减少格式干扰 |
| 独立 | 一要点一意思 | 便于识别和局部改 |
| 分点 | 快速扫读 | 便于提取/排序/重组 |
| 分层 | 一眼看结构 | 易理解上下位关系 |

> 清单体不是为记得更多，是为让协作内容**更容易被继续加工**。

## 五、工具对比与选型

### 5.1 备选（回到需求选，不争论绝对）

| 层 | 备选 |
|---|---|
| 展示（看 md） | Sublime / 飞书 / VS Code |
| 全局（扫文件夹） | Sublime / VS Code |
| 同步 | iCloud / Syncthing / 网盘 / 飞书自带 |

### 5.2 飞书文档 vs Markdown+Obsidian

| 维度 | 飞书 | Obsidian+MD |
|---|---|---|
| 多人实时编辑 | **强** | 不擅长同文件实时编辑 |
| 云端/自动保存 | 原生 | 需自选同步方案 |
| 全局文件树 | 弱 | **直接看完整文件树** |
| AI 全量读 | 取决于接口权限 | **Agent 直接面对整个文件夹** |
| 格式开放 | 平台内完整 | MD 开放可迁移 |
| 上手成本 | 低 | 要懂文件与同步 |

> 我们用得最开心的：**Codex + Obsidian**；两种方案不是必须串联，按任务选。

## 六、金句与判断

> 「让任何人只看文件名和排序，就能判断文件是什么、处在哪一层、是不是最新版。」
> 「清单体不是为了记得更多，而是为了让协作内容更容易被继续加工。」

## 七、行动建议

| 层级 | 行动 |
|---|---|
| 基础 | 把一个进行中的项目按「NN. 主题：内容」重命名 |
| 进阶 | 定一份团队命名规范（process→archive→workflow） |
| 高阶 | 选一套同步方案（iCloud/Syncthing），明确「同步≠备份」 |
