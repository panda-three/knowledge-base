## 一、为什么要拆计划——破题篇

> **"太多人有耐心一遍遍返工，却没有时间做一个好计划。"**

### 1.1 不拆计划的代价

| 表现 | 根因 | 后果 |
|---|---|---|
| 项目频繁延期 | 排期凭感觉，依赖关系没理清 | 信任崩塌，团队士气下降 |
| 丢三落四、边做边补 | 事情没拆全，工作模块遗漏 | 执行中不断补坑、补人、补事 |
| 让协作方和领导很虚 | 角色不清，不知道谁负责什么 | 信任快速下滑 |
| 重复返工 | 前期没预判风险，没排好顺序 | 反复推翻重来 |
| 永远在救火 | 计划不做或做得太粗 | 被突发事件牵着走 |

### 1.2 拆计划的核心价值

```text
好的前期计划 = 提前解决 80% 的项目问题。
```

| 价值 | 说明 |
|---|---|
| **可执行** | 排出来有人能干，每件事有明确负责人 |
| **有顺序** | 先做什么后做什么，依赖关系清楚 |
| **时间可控** | 关键路径可见，知道哪些环节会拖累整体 |
| **风险可预判** | 敏感维度提前标注，计划重心有侧重 |
| **信任可建立** | 计划摆出来，协作方和老板心里有底 |

### 1.3 拆计划的本质

> **拆计划就是把一个粗糙的方案，拆成一个可执行的计划——一个做减法的过程，把大目标拆到可执行的小单元。**

## 二、前置判断：六维敏感度模型

> **核心原则：你项目的敏感度在哪里，你的计划重点就在哪里。**
>
> 不是所有项目都值得花同样精力做计划。先判断项目在哪些维度"特别敏感"，再决定计划投入重心。

### 2.1 六维全景

| 敏感维度 | 核心问题 | 判断信号 |
|---|---|---|
| **1. 预算敏感** | 是不是对费用很敏感，不希望超预算？ | 钱紧、预算刚性、超支等于失败 |
| **2. 时间敏感** | 是不是对 Deadline 很敏感，不太接受延期？ | DDL 不可动摇，延期等于重大事故 |
| **3. 人力敏感** | 是不是人力投入敏感，中途加人很不容易？ | 核心人员不可替代，中途不能补人 |
| **4. 协作敏感** | 是不是协作方信任敏感，得让大家觉得你靠谱？ | 多方配合复杂，信任一旦丢了很难挽回 |
| **5. 风险敏感** | 是不是项目有一定风险，需要好好管理避免整体失败？ | 经验不足、不确定性高、不能接受失败 |
| **6. 老板敏感** | 是不是老板特别关注，你希望老板放心甚至开心？ | 老板高度关注、经常过问、影响信任评价 |

### 2.2 实战案例：不同项目的敏感度画像

**案例一：一堂创业马拉松（D 级大项目）**

| 敏感维度 | 程度 | 原因 |
|---|---|---|
| 时间敏感 | 🔴极高 | 年度大课，DDL 不能改 |
| 风险敏感 | 🔴极高 | 不能接受失败 |
| 老板敏感 | 🟡中等 | Truman 高度关注 |
| 人力/预算/协作 | 🟢较低 | 内部资源调配相对灵活 |

> → **计划重心：死守关键路径，做好风险预判和 Plan B。**

**案例二：家里装修（个人项目）**

| 敏感维度 | 程度 | 原因 |
|---|---|---|
| 预算敏感 | 🔴极高 | 刚买房储蓄不多，超预算很痛苦 |
| 时间/人力/协作 | 🟢较低 | 延期一点也能接受 |

> → **计划重心：预算计划表 + 严格审批每一笔支出。**

### 2.3 敏感度判断铁律

```text
1. 先做敏感度判断，再决定计划深度——不是所有项目都需要甘特图。
2. 敏感度判断要诚实——不要因为"应该都重要"就全部标红。
3. 敏感维度一般不超过 2-3 个——全都敏感就是都不敏感。
4. 计划重心要压在敏感维度上——不敏感的地方可以粗放。
```

## 三、第一步：拆事情——把项目拆成可执行的工作单元

> **做项目计划的基础，就是把你的工作拆解开，变成一系列关键工作。**

### 3.1 拆事情三层结构

```text
粗拆：里程碑（走到哪儿了）
  ↓
细拆：工作模块 WBS（具体做什么）
  ↓
精拆：优先级排序（先保什么、可以砍什么）
```

---

### 3.2 第一层：拆解里程碑

#### (A) 什么是里程碑

> 里程碑（Milestone）= 项目完成过程中的重大事件节点，用来推动和测量整个项目的进展。

就像公路上的里程牌——判断你在这条路上走到哪儿了。

#### (B) 里程碑的"两必要 + 两最好"

| 类型 | 节点 | 说明 |
|---|---|---|
| **两必要** | 必经节点 | 项目推进绕不开的关键环节 |
|  | 交付节点 | 对外的关键交付物完成时间 |
| **两最好** | 检查点/评审点 | 停下来检查质量、对齐认知的时刻 |
|  | 前后依赖标记 | 标注哪些里程碑之间有先后依赖关系 |

#### (C) 里程碑的标志性词汇

> 一个好的里程碑描述，必须是一个**确定性事件**——完成了就是完成了，不存在模糊地带。

| ✅ 推荐用词 | ❌ 避免用词 |
|---|---|
| 完成、提交、评审通过、确认、组建、敲定、上线 | 推进、优化、完善、差不多、基本完成 |

#### (D) 里程碑的两条铁律

1. **DDL 铁律** — 每个里程碑必须回答：什么时候，对外交付到什么结果。
2. **Buffer 铁律** — 留 20% 缓冲空间用来应急，不为"一切顺利"做计划。

---

### 3.3 第二层：WBS 工作分解三原则

> 花匠讲的是简版 WBS，来自美团、字节、百度和一堂的现场实践。完整 PMP 版 WBS 适合大型工程项目。

| 原则 | 含义 | 自查问题 |
|---|---|---|
| **1. 独立负责** | 每个工作包有唯一责任人，不出现"大家一起负责" | 这件事只有一个 R 吗？ |
| **2. 靠谱可控** | 工作量可估算、进度可检查、质量可验证 | 3 天内能干完吗？干完怎么检查？ |
| **3. 逻辑完备** | 拆完后加起来等于整体目标，无遗漏无冗余 | 所有子任务加起来，能还原成完整目标吗？ |

> **3 天法则：超过 3 天的任务继续往下拆，直到每个工作包都"看得见摸得着"。**

---

### 3.4 第三层：253 优先级思考法

> **核心洞察：不是每件事都同等重要。分优先级是成熟的标志。**

#### (A) 三层分档

| 层级 | 含义 | 对待方式 | 比例 |
|---|---|---|---|
| **2 — 决定成败** | 这些事做不好，项目就失败 | **死守**，不惜代价保质量、保进度 | ~20% |
| **5 — 重要** | 影响质量/效率/体验的关键事项 | **全力保障**，正常推进 | ~50% |
| **3 — 可以妥协** | 锦上添花，条件不允许时可砍 | **降级、延期或砍掉**，不纠结 | ~30% |

#### (B) 优先级评价五维度

每次给任务标优先级时，从以下五个维度综合判断：

| 评价维度 | 核心问题 |
|---|---|
| 1. 目标是否决定性 | 这件事不做，目标还能不能达成？ |
| 2. 成本 | 这件事要做成，需要多少资源？ |
| 3. 难度和风险 | 这件事做成的把握有多大？失败后果是什么？ |
| 4. 是否关键路径 | 这件事在关键路径上吗？延迟会影响整体 DDL 吗？ |
| 5. 是否老板关心 | 老板会主动问这件事的进展吗？ |

#### (C) 优先级表达方式

| 方式 | 适用场景 |
|---|---|
| 253（决定成败/重要/可妥协） | 一堂推荐，简洁清晰 |
| SABC | 传统分级 |
| 高中低 | 最直观 |
| P0/P1/P2 | 互联网常用 |

## 四、第二步：拆角色——RASCI 五大角色模型

> **拆完事情之后，需要把所有事情落到具体的人身上。角色混乱是项目延期和冲突的最大来源之一。**

### 4.1 RASCI 五大角色全景

| 缩写 | 全名 | 角色 | 核心职责 | 使用概率 |
|---|---|---|---|---|
| **R** | Responsible | **负责人** | 牵头、推动者、管项目，干活的人 | 高 |
| **A** | Accountable | **批准者** | 授权者、批准、拍板，对结果最终负责 | 中 |
| **S** | Supportive | **支持者** | 支持、辅助、参与执行 | 高 |
| **C** | Consulted | **咨询者** | 提供关键信息、关键能力 | 低 |
| **I** | Informed | **知会者** | 接受信息，事后被告知 | 中 |

### 4.2 三条铁律

| 铁律 | 含义 | 反例 |
|---|---|---|
| **每件事必须有且只有一个 R** | 不能出现"大家一起负责" | "Leo 和张田田一起负责"——谁牵头？ |
| **每个模块必须明确 A** | 关键决策必须有人拍板，不能悬空 | 方案改了三轮没人说"好，就这样" |
| **S 必须提前确认** | 支持者要提前沟通，不能临时抓人 | "我以为你会帮我做"——你没说过 |

### 4.3 三类最常见的角色混乱

| 混乱类型 | 表现 | 后果 |
|---|---|---|
| **不分工** | 所有人都觉得自己"参与"，但没人知道自己具体负责什么 | 事情落地时互相推诿 |
| **缺负责人** | 关键模块没有明确的 R，A 也不清楚是谁 | 出问题找不到人问责 |
| **关键成员缺失** | 需要的 S 或 C 没有被拉进来，或拉得太晚 | 方案反复被推翻、执行时才发现缺能力 |

### 4.4 RASCI 使用层次

| 项目级别 | RASCI 使用程度 |
|---|---|
| **A 单人项目** | 心里过一遍 R/A 即可 |
| **B 小项目-多人** | 完整 RASCI 表，每个关键任务标注 R、A、S |
| **C 中项目-跨部门** | + 沟通计划表（注明 C 和 I 何时、以什么方式参与） |
| **D 大项目-公司级** | + 关键人备份 + 职责分工正式文档画押 |

## 五、第三步：拆排期——从依赖关系到最终排期表

> **靠谱排期三原则：能执行、有顺序、时间短。**

### 5.1 第一层：确定依赖关系

#### (A) 什么是依赖关系

> 项目任务不是一条线按顺序执行，也不是可以随便并行。**工作之间是有依赖关系的**——有些事必须等另一些事做完才能开始。

#### (B) 依赖关系三种类型

| 类型 | 含义 | 示例 |
|---|---|---|
| **FS（完成→开始）** | A 完成了，B 才能开始 | 方案确认了 → 才能开始设计 |
| **SS（开始→开始）** | A 开始了，B 就能开始 | 内容撰写开始 → 视觉设计同步开始 |
| **FF（完成→完成）** | A 完成了，B 才能完成 | 内容定稿 → 排版定稿 |

#### (C) 画出进度网络图

```text
把所有任务的依赖关系画出来 → 形成一张进度网络图
```

---

### 5.2 第二层：关键路径分析

#### (A) 什么是关键路径

> **关键路径 = 从项目开始到结束，最长的一条路径。**
>
> 这条路径上的任何延迟，都会直接导致项目整体延期。

#### (B) 关键路径三动作

| 动作 | 含义 | 方法 |
|---|---|---|
| **找出关键路径** | 哪条任务链决定了最短完成时间？ | 顺着依赖关系，找出总时长最长的路径 |
| **缩短关键路径** | 怎么让关键路径变短？ | 加人、并行、简化、集中决策、减少等待 |
| **盯紧关键路径** | 日常管理重点放在哪里？ | 关键路径上的任务优先关注，延迟立刻预警 |

#### (C) Leo 案例：如何缩短关键路径

> Leo 做手册项目，关键路径 51 天，但 DDL 只有 45 天。花匠带他做了三件事：

| 调整动作 | 具体做法 | 节省天数 |
|---|---|---|
| **压缩决策时间** | 周末集中决策，手册定义从 6 天变 2 天 | -4 天 |
| **加人力** | 教研团队加一倍人力，撰写从 25 天变 20 天 | -5 天 |
| **集中审核** | 定稿审核周末集中做，5 天变 3 天 | -2 天 |

> **结果：关键路径从 51 天缩短到 40 天，留下 5 天 Buffer，计划靠谱了。**

#### (D) 关键路径的核心原则

```text
1. 只在关键路径上加人加资源才有意义——非关键路径优化不改变整体工期。
2. 非关键路径上的任务有一定浮动空间，但关键路径一天不能耽误。
3. 关键路径可能随项目推进而改变——不是一次性分析。
```

---

### 5.3 第三层：最终确定排期——三种排期工具

| 工具 | 简单排期 | 完整排期表 | 甘特图 |
|---|---|---|---|
| **工作重点** | 只排关键交付和里程碑 + 设置截止时间 | 给每个关键任务排期 + 必须有截止时间 + 最好有开始时间 | 依赖关系可视化 + 起止时间可视化 |
| **适合条件** | A 级简单项目 / 流程清晰的 B 级项目 | 大部分 BCD 项目 / 人力或时间敏感的项目 | 复杂协作的 BCD 项目 / 人力或时间敏感 / 协作敏感 |
| **推荐工具** | Excel、飞书表格 | Excel、飞书表格 + Tower、Teambition | Excel、飞书表格 + Tower、Teambition + Project |

> **选择原则：匹配项目级别，不是越重越好。**

## 六、Leo 的七轮迭代成长——完整拆计划演示

> Truman 评价："如果当年他看到这个案例，项目管理的成长至少可以省半年时间。"

### 6.1 项目背景

**任务：** 制作一本手册，4 月 1 号启动，5 月 15 号送到同学们手里。

### 6.2 七轮迭代轨迹

| 版本 | 迭代内容 | Leo 学到什么 |
|---|---|---|
| **V1** | 只有一堆任务清单，没有时间、没有优先级、没有负责人 | "我以为列了清单就是做了计划" |
| **V2** | 加了里程碑，但没有拆细 | "里程碑太粗，执行时还是不知道先做什么" |
| **V3** | 拆了工作模块，但没标优先级 | "所有事情看起来都重要，不知道该保哪个" |
| **V4** | 加了 253 优先级分档 | "终于知道哪些事可以砍，哪些死也不能放" |
| **V5** | 加了 RASCI 角色分工，每件事有且仅有一个 R | "原来之前很多事没人负责所以老掉地上" |
| **V6** | 画出依赖关系和关键路径，发现 51 天 > 45 天 DDL | "关键路径不分析根本不知道时间根本不够" |
| **V7** | 缩短关键路径 11 天 + 完整排期表（带开始和截止日期） | "计划终于靠谱了，心里有底了" |

### 6.3 Leo 的核心成长

```text
第1版：一堆散装任务 → 第7版：一条靠谱可执行的完整计划

成长本质：从"想到什么列什么"到"分层拆解、标优先级、定角色、画关键路径、做排期"。
```

## 七、不同项目类型的拆计划递进要求

| 项目类型 | 拆计划要求 |
|---|---|
| **A 单人项目** | 拆事：WBS + 里程碑 / 拆人：心里过 R/A / 拆排期：交付节点 + 依赖关系 |
| **B 小项目-多人** | A 类 + 科学估算成本 + 执行排期表（日历）+ 计划严格评审（画押）+ 预算计划表 + 职责分工表 |
| **C 中项目-跨部门** | B 类 + 253 优先级思考 + 执行排期（甘特图）+ 项目汇报机制 + 沟通计划表 + 六维敏感度分析 |
| **D 大项目-公司级** | C 类全部 + 关键人备份 + 风险管理升级 + 关键路径重点标注 |

│  - 里程碑     │  两必要+两最好 / 标志性词汇   │

│  - 优先级     │  253思考 / 五维度评价        │
├───────────────┼───────────────────────────┤

## 九、花匠的核心管理哲学

| 金句 | 含义 |
|---|---|
| "反复救火是一种项目管理非常业余的表现。" | 成熟的 PM 用计划预防问题，不是用救火解决问题 |
| "我更喜欢用前期做计划解决问题。" | 计划不是负担，是让执行从容的手段 |
| "太多人有耐心一遍遍返工，却没有时间做一个好计划。" | 时间投资的错配——省计划的时间，花返工的时间 |
| "计划不做好，一定跑不了。" | 墨菲定律在项目管理中反复应验 |
| "拆，是预判，是规划。" | 所谓"科学"做计划，本质就是拆解+预判+规划 |
| "凡事预则立，不预则废。" | 古话在项目管理中仍然成立 |
| "你项目的敏感度在哪里，你的计划重点就在哪里。" | 不要均匀用力，要把计划重心压在敏感维度上 |

## 十、L6 刻意练习自检清单

> 以下清单用于每次做项目计划前、中、后的自我检查。

### 拆计划前——敏感度判断

- [ ] 我是否用六维敏感模型判断了项目的敏感度？
- [ ] 项目的 1-2 个最敏感维度是什么？我的计划重心是否压在它们上面？
- [ ] 我是否根据项目级别（A/B/C/D）匹配了计划深度，而不是过度或不足？

### 拆事情

- [ ] 我是否拆出了清晰的里程碑（含 DDL + Buffer），且每个里程碑是可验证的确定性事件？
- [ ] 每个里程碑的描述是否用了"完成/提交/评审/确认"等标志性词汇，而不是"推进/优化"？
- [ ] 我是否做了 WBS 分解，且每个工作包满足"独立负责、靠谱可控、逻辑完备"三原则？
- [ ] 超过 3 天的工作包是否继续拆下去了？
- [ ] 我是否用 253 思考对事项做了优先级分档（决定成败 / 重要 / 可妥协）？
- [ ] 标"2"的事项是否真的是"不做项目就失败"级别的？

### 拆角色

- [ ] 每件事是否有且只有一个 R？
- [ ] 每个关键模块是否明确了 A（批准者/拍板人）？
- [ ] S（支持者）是否提前沟通过，而不是临时抓人？
- [ ] C（咨询者）是否在关键决策前被问到，而不是做完再通知？
- [ ] 是否存在"不分工 / 缺负责人 / 关键成员缺失"三类角色混乱？

### 拆排期

- [ ] 我是否画出了所有关键任务之间的依赖关系？
- [ ] 我是否找出了关键路径，并标注了它的总时长？
- [ ] 关键路径总时长是否小于 DDL？如果超了，我是否做了缩短动作？
- [ ] 非关键路径上的任务是否有浮动空间？
- [ ] 我是否根据项目复杂度选择了匹配的排期工具（简单排期 / 完整排期表 / 甘特图）？
- [ ] 排期表是否包含了每个任务的开始日期、截止日期和负责人？

### 综合自检

- [ ] 我是否把计划给关键相关方看过并拿到了确认（至少 A 角色）？
- [ ] 计划是否留了 20% 的 Buffer？
- [ ] 我是否真的能做到"心中有数"——不看文档也能说出项目的关键路径和最大风险点？
- [ ] 和上次做计划相比，我这次在哪个维度上有可感知的进步？
