# 全员必修：低成本验证认知篇 — L6 清单体笔记

---

## 一、课程定位与核心金句

> **「创业最难的，不是从0到1、从1到100，而是从-1到0——把"我以为"变成"事实如此"。」**

> **「很多人的创业，本质上是花200万和两年时间，验证了一个在星巴克里花20块钱和两个小时就能用MVP验证掉的假设。」**

> **「在今天的AI时代，MVP和低成本验证这件事越来越重要——因为节奏不一样了。原来3个月能做的事，现在3天就够了。」**

> **「优秀的人验证一个项目是10万块钱，而你可能要花100万。差距不在执行，而在验证方法。」**

**课程定位**：

```text
低成本验证系列 · 全景地图：
  全员必修：低成本验证认知篇（认知入门）← 本节课
    → 精益验证实操篇（四类武器+8种MVP方法实操）
      → 需求侧精益验证（验证需求假设）
        → 供给侧精益验证（验证方案假设）
```

**本节核心交付**：**精益验证四类武器 + 8种MVP方法全景 + MVP段位图L1-L6。** 帮你建立低成本验证的完整审美——区分四种验证武器，理解8种MVP方法的核心逻辑和适用场景。

**推荐谁学**：在这条路上总是不笃定的创业者——要么靠信念(蒙眼狂奔)，要么靠精益(低成本验证)。如果你想知道「我的想法到底对不对」但又不想花200万试错，这节课就是你的必修课。

**课程渊源**：精益验证专项是一堂的看家课。硅谷创业家 Steve Blank + Eric Ries 的理论体系 + 一堂本土化同学的创业案例 + 多年实践迭代 = 今天这套系统的低成本验证方法论。

## 二、预热思考 · 三连问

| # | 问题 | 用意 |
|---|------|------|
| 1 | 你上一次认为"这个方向肯定行"，是在投入了多少钱、多少时间之后才发现不对的？如果回到当初，你最多愿意花多少钱来提前验证？ | 建立对"不验证就投入"的真实痛感 |
| 2 | 如果明天你要验证一个新想法，只能花1000块和3天时间，你会怎么做？你会首先验证哪个假设？ | 逼出"最小可行验证"的本能反应 |
| 3 | 给你100块钱和三天时间，你能不能测出一个业务方向要不要真金白银投入？ | 检验用户是否具备低成本验证的真实能力 |

## 三、课前故事：两个创业者的分岔路

### 3.1 故事背景

```text
时间回到几年前，那时还没有AI。

两个人，都想在商场里开一个射击馆。

第一个人：家传四代射击教练（猎人），有三个月时间
          传统思维——租场地、进设备、装修、开业
          三个月后，装修到一半没钱了，项目停滞

第二个人：从来没有碰过枪，只有一周时间
          做了一个极简测试——
          找一块布画了几个同心圆，拿一个玩具枪
          给路人发："打中10环送一瓶水"
          → 路人反应："这游戏有点无聊，有没有气球可以打？"
          （这就是后来流行的气球射击）
```

**对比结果**：

| 对比维度 | 第一个人（传统） | 第二个人（精益验证） |
|----------|:----------:|:----------:|
| **投入时间** | 3个月 | 1周 |
| **投入成本** | 数万元（装修+设备） | 9.9元（布+玩具枪+水） |
| **拿到认知** | ❌ 没拿到（装修未完） | ✅ 拿到了（"要有气球"） |
| **项目结果** | 装修一半没钱，停滞 | 知道该做什么调整 |

### 3.2 核心启示

```text
第一个人的问题不是"不聪明"或"不努力"。
他是家传射击教练——他比别人都懂射击。
他的问题是：没有低成本验证的意识。

他总是想着"做一个完整的射击馆"——为面子、为完整度——
花了三个月时间和大量金钱，却没拿到任何关于真实用户需求的认知。

而第二个人的9.9元测试，用极低成本拿到了最关键的信息：
用户要的不是"专业射击体验"，而是"有反馈、有乐趣的打气球游戏"。
```

### 4.2 武器一：假实验（Fake Experiment）

> **「发布虚假产品，测试用户意愿——用户还没有产品可以体验时，测用户对概念/卖点的真实反应。」**

| 维度 | 内容 |
|------|------|
| **一句话** | 创建虚假的产品/服务入口，观察用户的真实行为 |
| **测什么** | 用户意愿——"如果真的有这个产品，用户会不会点？会不会留资？会不会付定金？" |
| **不测什么** | 用户满意度——用户还没用上产品，无法测满意度 |
| **什么时候用** | 产品还没做出来，但想验证需求是否真实存在 |

**两个关键原则**：

| 原则 | 说明 |
|------|------|
| **给用户真实的场景感** | 落地页、海报、产品介绍要看起来像真的——让用户在"以为是真的"的情况下做出自然反应 |
| **测用户行为而非用户说的话** | 不是问"你会用吗"，而是看"他有没有点"——点击、留资、付定金 > 口头表态 |

**关键技巧**：

```text
在"假"的前提下，给用户最真实的选择场景。
测的是行为，而非"用户说的话"。
```

---

### 4.3 武器二：人工MVP（Manual MVP / Wizard of Oz）

> **「用人工替代产品，让用户先体验——产品还没做出来或做出来成本高时，用人工模拟产品功能来拿反馈。」**

| 维度 | 内容 |
|------|------|
| **一句话** | 用人来替代机器/系统/算法，让用户先体验服务，拿到反馈 |
| **测什么** | 解决方案是否真的创造价值——用户用了之后满意吗？愿意付费吗？ |
| **不测什么** | 规模化能力——人工MVP验证不了系统稳定性 |
| **什么时候用** | 产品开发成本高、周期长，但可以用人工先跑通服务闭环 |

**关键原则**：

```text
用最低成本的人工方式，模拟产品的核心功能。
先验证"这个服务有没有人需要"，再考虑"要不要用系统来替代人工"。
```

---

### 4.4 武器三：简化版（Simplified MVP / Concierge MVP）

> **「只做最核心功能，看看有没有人用——产品可以做但不想花太多时间时，做一个极简版快速上线测反馈。」**

| 维度 | 内容 |
|------|------|
| **一句话** | 只保留产品最核心的1-2个功能，最快速度上线 |
| **测什么** | 核心功能是否被用户需要和使用 |
| **不测什么** | 完整产品体验——简化版只测内核，不测体验 |
| **什么时候用** | 技术可行、开发成本可控，但不想一开始就做大而全 |

**关键原则**：

```text
砍到只剩产品内核。
不要加任何"锦上添花"的功能——
只验证"用户愿意选择你的最小解决方案"。
```

---

### 4.5 武器四：代理变量（Proxy Variable）

> **「用替代数据指标，间接验证关键假设——根本无法直接测目标变量时，用一个容易观测的代理变量间接验证。」**

| 维度 | 内容 |
|------|------|
| **一句话** | 找一个和目标变量高度相关但容易测量的替代指标 |
| **测什么** | 间接验证目标假设是否成立 |
| **注意** | 代理变量和目标变量之间的相关性必须足够强，否则结论无效 |
| **什么时候用** | 目标变量无法直接测量，或测量成本过高 |

**关键原则**：

```text
代理变量不是"随便找一个相关的东西"。
必须是和目标变量有强因果关系或高度相关的指标，
且相关性需要被验证过。
```

---

### 4.6 四类武器对比速查

| 对比维度 | 假实验 | 人工MVP | 简化版 | 代理变量 |
|----------|:------:|:------:|:------:|:------:|
| **产品存在吗** | 不存在 | 不存在 | 存在（极简版） | 不一定 |
| **用户能用上吗** | ❌ 不能 | ✅ 能（人工版） | ✅ 能（简化版） | ❌ 不能 |
| **测什么** | 意愿 | 价值 | 核心功能 | 间接指标 |
| **成本** | 极低 | 低 | 中 | 极低 |
| **验证强度** | 中 | 高 | 最高 | 低（间接） |
| **典型做法** | 假落地页/海报 | 人工客服/人工推荐 | 只做一个功能上线 | 看类似产品的数据 |

## 五、MVP的定义与8种精益验证方法

### 5.1 什么是MVP

> **「所谓最小可行产品（MVP），是在《精益创业》中提出的理念，简单来说，就是在做一个新产品时，不要一下子做一个"完美"的产品，要先花最低的成本、最小的代价，做一个"简陋"的版本，去验证产品是否真的满足用户需求。」**

```text
MVP = Minimum Viable Product
     = 最小可行产品
     = 花最少的力气、最短的开发时间，
       去经历一次完整的「开发→测量→认知」循环，
       验证产品是否真的满足用户需求。
```

### 5.2 MVP验证的本质

```text
MVP验证的本质 = 假设驱动的科学实验

不是在做一个"简陋的产品"，
而是在设计一个"恰好能验证关键假设的测试"。

关键问题不是"产品够不够好"，
而是"我通过这次测试，学到了什么？我的关键假设被证实还是证伪了？"
```

### 5.3 8种精益验证方法全景（核心交付）

```text
┌───────────────────────────────────────────────────────────────┐
│              8种MVP验证方法 · 全景图                              │
├──────┬──────────────────┬────────────────────────────────────┤
│  序号  │     方法名称      │              一句话简介              │
├──────┼──────────────────┼────────────────────────────────────┤
│  1   │ 产品介绍/假 Landing Page │ 做一个产品介绍页/落地页，测有多少人点击/留资  │
│  2   │ 兜售实验/预定     │ 在没产品的时候，尝试向用户兜售/收预订款    │
│  3   │ 众筹测试         │ 在产品做出来之前，发起众筹，看有没有人付钱  │
│  4   │ 山寨/借用         │ 借用现成产品/工具拼凑出一个"看起来像"的版本 │
│  5   │ 单功能版         │ 只做核心功能，砍掉所有周边功能             │
│  6   │ 人工替代         │ 用人来替代机器/算法，先跑通服务闭环        │
│  7   │ 视频/图文概念测试  │ 用视频/图文模拟产品体验，看用户反应        │
│  8   │ A/B测试          │ 同时跑两个版本，看哪个数据更好             │
└──────┴──────────────────┴────────────────────────────────────┘
```

### 5.4 8种方法 · 对应武器分类

| 方法 | 所属武器类型 | 测什么 | 成本级别 |
|------|:----------:|--------|:------:|
| 假Landing Page | 假实验 | 用户意愿 | 极低 |
| 兜售实验/预定 | 假实验 | 付费意愿 | 极低 |
| 众筹测试 | 假实验 | 付费意愿+市场验证 | 极低 |
| 视频/图文概念测试 | 假实验 | 用户兴趣和意愿 | 极低 |
| 山寨/借用 | 假实验/简化版 | 解决方案可行性 | 低 |
| 单功能版 | 简化版 | 核心功能价值 | 中 |
| 人工替代 | 人工MVP | 解决方案价值 | 低 |
| A/B测试 | 简化版/代理变量 | 不同方案对比 | 中 |

### 5.5 8种方法详解

#### 方法1：产品介绍/假Landing Page

| 维度 | 内容 |
|------|------|
| **怎么做** | 做一个假的产品落地页/产品介绍页，通过投放或分享观察用户点击、留资、预约等行为 |
| **测什么** | 用户对这个产品概念的意愿值——有多少人看到后愿意点进来、留电话、预约 |
| **经典案例** | 早期的Dropbox——在写好代码之前，做了一个3分钟的产品介绍视频，一夜之间10万人注册 |
| **关键技巧** | 页面要足够真实——让用户以为这是真的产品入口；看行为数据而非问卷结果 |

---

#### 方法2：兜售实验/预定

| 维度 | 内容 |
|------|------|
| **怎么做** | 在产品还没做出来之前，尝试向用户兜售/收取预定款 |
| **测什么** | 用户的真实付费意愿——愿意付定金是比点击更强的信号 |
| **经典案例** | 特斯拉Cybertruck——车还没量产，预定金就收了数十万辆 |
| **关键技巧** | 预定款要设计得刚好——太高没人付，太低测不出真实意愿 |

---

#### 方法3：众筹测试

| 维度 | 内容 |
|------|------|
| **怎么做** | 在产品做出来之前，在众筹平台（Kickstarter/Indiegogo/淘宝众筹等）发起众筹 |
| **测什么** | 市场对产品概念的接受度+真实付费意愿 |
| **经典案例** | Oculus Rift VR头显——众筹阶段就验证了巨大的市场需求 |
| **关键技巧** | 众筹页面本身就是一份"产品内核说明书"——能写清楚卖点，说明你对产品的理解到位了 |

---

#### 方法4：山寨/借用

| 维度 | 内容 |
|------|------|
| **怎么做** | 借用现成产品/工具拼凑出一个"看起来像"的版本，快速拿反馈 |
| **测什么** | 解决方案的可行性——用户能不能通过这个"拼凑版"获得价值？ |
| **适用场景** | 技术门槛不高、可以用现成工具组合模拟的场景 |
| **关键技巧** | 不要纠结"拼凑版不够好"——拼凑版的目的不是上线，是拿认知 |

---

#### 方法5：单功能版

| 维度 | 内容 |
|------|------|
| **怎么做** | 只做产品最核心的一个功能，其他全部砍掉 |
| **测什么** | 核心功能是否有用户需要和使用 |
| **适用场景** | 开发资源有限，想先验证产品内核 |
| **关键技巧** | 砍掉的功能不是"不重要"，而是"不是决定性要素"——用产品内核课的方法论 |

---

#### 方法6：人工替代

| 维度 | 内容 |
|------|------|
| **怎么做** | 用人工来替代机器/系统/算法，先让用户体验完整的服务闭环 |
| **测什么** | 解决方案是否真的创造价值——用户愿意为这个人提供的服务付费吗？ |
| **经典案例** | Zappos创始人——先去鞋店拍照上传，有人下单就去鞋店买来寄出。没有系统、没有库存，就验证了"有人在网上买鞋"这个假设 |
| **关键技巧** | 用户不知道背后是人还是机器——只要服务体验一致，反馈就是真实的 |

---

#### 方法7：视频/图文概念测试

| 维度 | 内容 |
|------|------|
| **怎么做** | 做一个产品概念的视频或图文，模拟产品使用场景，投放或分享看用户反应 |
| **测什么** | 用户对产品概念的兴趣和意愿——播放量、完播率、转发、评论情绪 |
| **经典案例** | Dropbox的3分钟视频——"感觉就像在电脑上操作一样" |
| **关键技巧** | 视频不是"产品广告"，而是"产品体验模拟"——让用户看完就知道用起来什么感觉 |

---

#### 方法8：A/B测试

| 维度 | 内容 |
|------|------|
| **怎么做** | 同时跑两个版本——不同的落地页、不同的定价、不同的功能——看哪个数据更好 |
| **测什么** | 两个方案中哪个更优 |
| **适用场景** | 已经有基础版本和数据管道，想优化关键指标 |
| **关键技巧** | 一次只测一个变量——同时改多个变量就无法归因 |

### 段位速查表

| 段位 | 能力 | 典型标志 | 价值 |
|------|------|----------|------|
| **L1** | 缺MVP思维 | 有验证欲望但不得法——每次都做完整版再测 | 从0到0.5：开始意识到"可以先测一下" |
| **L2** | MVP入门 | 会用1-2种基础验证方法（通常是假Landing Page和人工替代） | 从0.5到1.0：至少有了第一个低成本验证的实践 |
| **L3** | 多个MVP验证 | 可以自己设计MVP测试方案，能组合使用多种验证方法 | 从1.0到1.5：不再依赖"别人的模板"，能根据自己业务定制验证方案 |
| **L4** | 预判能力强 | 对四类武器+8种方法都很熟，能在动手前就选对验证策略 | 从1.5到2.0：不是"测了才知道"，而是"知道哪种测试最有效" |
| **L5** | 建模能力强 | 定量优先级排序——知道先测哪个假设、后测哪个 | 从2.0到3.0：MVP验证从一个"动作"升级为一个"系统" |
| **L6** | 动态验证系统 | 动态建模+精准测量+快速判断——持续优化验证体系 | 从3.0到4.0：验证不再是创业的一个阶段，而是持续运行的机制 |

## 七、验证假设类型：需求假设 vs 方案假设

### 7.1 两种假设对比

| 对比维度 | 需求假设 | 方案假设 |
|----------|----------|----------|
| **问什么** | "用户有这个需求吗？" | "我的方案能解决这个需求吗？" |
| **验证什么** | 需求是否存在、多强烈、多普遍 | 解决方案是否有效、用户是否满意 |
| **最适合的武器** | 假实验（假Landing Page/兜售/众筹） | 人工MVP / 简化版 |
| **常见错误** | 用户口头说"需要"就当真 | 做了一个完整版本才去测 |
| **在一堂五步法中** | 对应"需求"环节 | 对应"解决方案"环节 |

### 7.2 先测需求，再测方案

```text
正确的验证顺序：
  ① 先用假实验测需求——"有没有人要？"
  ② 需求验证通过了，再用人工MVP/简化版测方案——"我的方案好用吗？"

错误顺序（绝大多数人）：
  ❌ 凭直觉认为需求存在 → 直接做完整产品 → 上线后发现没人用

正确顺序（精益验证）：
  ✅ 假Landing Page测需求意愿 → 确认有人要
     → 人工替代测方案价值 → 确认方案有效
       → 简化版测核心功能 → 确认功能被需要
         → 完整版上线 → 大规模复制
```

## 八、AI + 低成本验证

### 8.1 AI时代规则变了

```text
在今天的AI时代，MVP和低成本验证这件事越来越重要。
因为节奏不一样了——

原来3个月能做的事，现在3天就够了。
原来需要设计师+程序员+运营做的事，现在AI一个人就能搞定。

这带来的不是"可以做更多测试了"——
而是"不做低成本验证的人，将比以前死得更快"。
因为对手的验证速度是你的10倍，迭代速度是你的10倍。
```

### 8.2 三类认知差

```text
第一层：知道可以用AI加速
第二层：知道可以把MVP变成在纸面上预判的更少MVP
第三层：建立个人验证武器库，内化成为本能
```

### 8.3 AI能加速的环节

| 环节 | AI能帮你做什么 | 你仍然需要做什么 |
|------|---------------|-----------------|
| **假Landing Page** | AI自动生成落地页文案、设计、结构 | 设计测试变量、判断数据含义 |
| **视频概念测试** | AI生成产品概念视频 | 定义核心卖点和目标用户画像 |
| **人工MVP** | AI替代一部分人工服务 | 设计服务流程、判断反馈质量 |
| **A/B测试** | AI自动分析测试结果 | 决定测什么变量、解释为什么A比B好 |

## 九、常见踩坑清单

| 常见坑 | 表现 | 正确姿势 |
|--------|------|----------|
| **完美主义陷阱** | "等我做得再好一点再去测" | MVP的M就是Minimum——越简陋越好，只要能测关键假设 |
| **测错假设** | 产品还没人需要就去测定价 | 先测需求假设（有人要吗），再测方案假设（好用吗），最后才测增长假设 |
| **相信用户说的而非做的** | 用户说"我会用"就当验证通过 | 看行为：点击>留资>付定金>复购——行为链条越长，验证强度越高 |
| **一次测太多变量** | 同一轮测试改多个变量 | 一次只测一个变量。改了定价又改了功能又改了文案——无法归因 |
| **测试样本太少** | 问了三个人都说好就觉得验证通过 | 样本量和验证强度正相关——10个人点>3个人说好 |
| **不设成功标准** | 测完不知道算不算通过 | 测之前先定义：什么样算"证实"？什么样算"证伪"？|

## 十一、L6 级别进阶认知

### 认知一：低成本验证不是"做测试"，而是"建系统"

> L1-L3的人把低成本验证当成"偶尔做一次"的动作——想测了，做个假Landing Page看看。但L5+的人把低成本验证当成一个持续运行的机制：每个关键假设都有对应的验证方案，每个验证方案都有明确的成功标准，每轮验证的结果自动进入下一轮迭代。**从"动作"到"系统"，是低成本验证能力最关键的质变。**

### 认知二：AI时代的低成本验证不是"更快"，而是"重新定义了MVP的M"

> 以前做M（Minimum）需要设计师+程序员+产品经理，现在AI一个人能生成落地页、视频、甚至模拟客服对话。但这不是说可以随便测更多了——而是说**你可以把精力从"做测试材料"转移到"设计测试逻辑"上。** AI让M的门槛降低了，但对"为什么要测这个""怎么判断结果"的要求反而更高了。

### 认知三：优秀的人验证一个项目是10万块钱，而你可能要花100万

> 差距不在执行，在验证方法。同一个商业假设——有人用9.9元的玩具枪+一瓶水就能测出关键认知，有人需要花几十万装修完才知道不对。**差距不在谁更努力，在谁更会用低成本验证的方法。**

### 认知四：创业最难的，是从-1到0

> 从0到1、从1到100讲的是增长和复制。但从-1到0——把"我以为"变成"事实如此"——这一步才是杀死最多创业者的环节。**低成本验证，就是帮你从-1走到0的唯一科学方法。**

### 认知五：验证强度是链条长度——不是"信不信"，是"有多信"

> 用户口头说"我会用"→验证强度=1。用户点击了→强度=3。用户付了定金→强度=7。用户持续复购→强度=10。**不要满足于低强度验证，也不要追求100%验证才行动——每一层验证都在增加你的信心，直到信心足够支撑决策。**

## 十二、行动建议

| 层级 | 行动 |
|------|------|
| **基础** | 选一个你正在考虑的业务假设——是需求假设还是方案假设？从8种方法中选出最适合验证这个假设的1种方法，用1周和100块钱完成一次低成本验证 |
| **进阶** | 画出你的关键假设链：①最重要的需求假设是什么？②最重要的方案假设是什么？③最重要的增长假设是什么？然后为每一个假设匹配1-2种验证方法。看看你的验证链条中，哪个假设的验证强度最低 |
| **高阶** | 建立你的验证系统：每次验证前明确"什么样算证实、什么样算证伪、本轮成本上限是多少"。连续做3轮验证，每轮记录"学到了什么""假设被证实还是证伪了""下一轮要测什么" |

---

> 📌 **最后提醒**：低成本验证是一堂的看家课。它不是一个一次学完就扔的方法，而是一种贯穿你整个创业周期的思维方式。在AI驱动的快节奏时代，验证速度本身就是一种竞争优势——对手验证一轮的时间，你已经完成三轮。**记住：创业最难的从来不是从1到100，而是从-1到0。低成本验证，就是帮你从-1走到0的唯一科学方法。**
