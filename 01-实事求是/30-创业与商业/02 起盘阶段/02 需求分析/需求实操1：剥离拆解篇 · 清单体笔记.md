# 需求实操1：剥离拆解篇 · 清单体笔记

## 一、课程定位与价值

**课程定位**：一堂五步法需求模块实操第一课，对应需求分析四字诀「拆–推–评–算」中的**拆**，交付模型为 **「USP 需求洞察公式 + 拆解三原则 + 2C/2B 全套拆解小抄」**。

**课程身份卡**：

| 维度 | 信息 |
|---|---|
| **讲师** | Truman，一堂 CEO |
| **系列位置** | 重新理解需求原点（认知）→ **剥离拆解篇**（实操1）→ 场景推演篇 → 定性评估篇 → 算天花板篇 |
| **核心交付** | 硬剥离需求的能力 + 拆解三原则 + 2C/2B 拆解小抄 |
| **适合谁** | 新手：还没被需求误判教训过 → 打基础；老兵：深刻体会需求拆解决定性价值 → 对标高手、平等对话 |
| **课程成果** | 集体成果——数千份作业挖掘 + Gemini/ChatGPT/DeepSeek 最新模型知识 + 十几人专家组经验 |

**一句话内核**：
- **需求本质上，是跟你无关的客观事实**——跟你怎么想、打算怎么做、想怎么定价一点关系没有。这是实事求是的理解市场现状

**在需求四字诀中的位置**：

| 四字诀 | 训练目标 | 对应课程 |
|---|---|---|
| **拆** | 训练拆解用户需求的意识——这是基本功 | 剥离拆解篇（本节） |
| **推** | 训练推演用户使用场景，理解问题 | 场景推演篇 |
| **评** | 训练定性评估需求可行性，判断价值 | 定性评估篇 |
| **算** | 训练定量估算市场大小，理性思考 | 算天花板篇 |

**使用注意**：拆–推–评–算是一个从前往后有积累和承接的「工具组合」，但**不是完整的、严丝合缝的工作流**——在任一步得到答案或证伪就可以结束，也可以跳步执行。

**课程三段结构**：

| 段落 | 内容 | 目标 |
|---|---|---|
| **第一部分·基础** | 破除「需求和产品绑死」的妄念，掌握硬剥离技巧 | 能把需求从解决方案里剥离出来 |
| **第二部分·进阶** | 剥离的目标——过大过小都是问题，把需求分析转化成关键高风险假设 | 用假设驱动需求分析 |
| **第三部分·高阶** | 完整拆解策略集 + 大量案例——2C/2B 全套拆解小抄 | 形成自己的拆解章法 |

## 二、为什么必须学：商业误判的最大根因

**核心病因**：大量商业出现重大误判，**往往就是出在「剥离不够」**。

**典型症状——需求与解决方案绞死**：

| 表现 | 问题 |
|---|---|
| 开口就是「我想做一个 XX 产品」 | 需求和产品内核混在一起，无法独立分析 |
| 「用户需要 XX 功能」 | 把解决方案包装成了需求 |
| 「市场上还没有人做这个」 | 可能是没有人需要，而不是没有人想到 |
| 「我验证过了，用户都说好」 | 验证的是产品概念，不是客观需求 |

**一堂内部案例——合伙人评审**：
- 同学 A 做了一个完整方案找合伙人 B 寻求支持
- B 看完方案直接问：「你先别说方案，你到底想解决的问题是什么？我有各种手段可以解决这类问题，我们先别急，先把问题探讨清楚」
- **好好研究需求，往往只需要花原本方案成本 10% 的新手段，就能拿到更好的解决方案**

**核心认知转变**：

| 旧认知 | 新认知 |
|---|---|
| 需求 = 用户想要什么功能 | 需求 = 市场上客观存在的问题和事实 |
| 需求分析和产品设计是一件事 | 需求可以被**独立剥离、独立分析、独立测试** |
| 用户会告诉我他们需要什么 | 用户嘴里说的是解决方案，背后才是需求 |

## 三、核心武器：USP 需求洞察公式 + JTBD

### 3.1 USP 需求基本公式

```
需求 = 用户 × 场景 × 问题
Demand = User × Situation × Problem
```

**三要素拆解**：

| 要素 | 定义 | 关键词 |
|---|---|---|
| **用户 User** | 需求的「载体」——拥有特定属性和角色，且具备支付能力/决策权 | 谁在承受这个痛苦？ |
| **场景 Situation** | 需求的「触发器」——产生需求的特定时空环境、触发事件及当下状态 | 什么时候、什么情况下疼？ |
| **问题 Problem** | 需求的「原动力」——用户现实和预期的差距（显性/隐性），甚至想达成的「进步」 | 疼到什么程度？现在怎么凑合？ |

**注意**：用户是简化表达，包含 2C、2B，也包含使用者和决策者。

### 3.2 JTBD 深层框架

**JTBD = Jobs to be Done（待办任务）**

| 维度 | 说明 |
|---|---|
| **基本定义** | 需求不是关于产品本身，而是关于客户在特定环境下想要达成的**进步（Progress）** |
| **核心逻辑** | 客户不是购买产品，而是「雇用」产品来帮他们完成某项任务 |
| **经典表述** | 人们不想买四分之一英寸的钻头，他们想要四分之一英寸的洞 |
| **创业启示** | 真正的需求隐藏在客户的**挫败感和未完成的任务**中，而不仅仅是他们口头要求的「功能」 |

**JTBD 思维破解「乔布斯不调研」谬论**：

| 流行谬误 | 实事求是 |
|---|---|
| 「平庸产品经理满足需求，顶级产品创造需求」 | 乔布斯、张小龙对用户的理解和洞察是**极其顶级和优秀**的 |
| 「乔布斯从不调研用户」 | 他们清楚地知道用户想要什么，只是**不会傻到直接向用户要现成的解决方案** |
| 「用户只会要更快的马，不会要汽车」 | 用户要的不是马，是「更快地从 A 到 B」——这就是 JTBD |

## 四、第一部分·基础：硬剥离需求

### 4.1 核心问题——「能不能拆？该不该拆？」

**表面答案**：该拆，能拆，一定得拆。

**实操真相**：绝大部分同学**没有办法把「需求」从「解决方案」里剥离出来**——全交织在一起了，全是主观判断和心里按捺不住的创意和灵感。

### 4.2 三个真实案例——识别「假剥离」

| 案例 | 版本 A（假剥离——混着方案） | 关键特征 |
|---|---|---|
| **宠物寄养柜子** | 城市一二线养宠用户，过节度假时无法照顾宠物，愿意付费寄养在门店里，这是刚需 | 「寄养在门店里」= 已锁死方案 |
| **醒酒产品** | 日常高频商务喝酒的人，愿意花 50-100 元/次去醒酒和缓解痛苦 | 「醒酒含片」= 已锁死产品形态 |
| **AI 智能工牌** | 销售驱动型公司培训成本极高，愿意采用 AI+智能教练的方式降本增效 | 「AI+智能教练」= 已锁死技术路线 |

### 4.3 正确姿势——「硬剥离」三步法

**第一步**：把「我打算怎么做」全部删掉
**第二步**：只描述客观事实——用户在什么场景下遇到什么问题
**第三步**：描述现在怎么凑合的，凑合得有多痛苦

**三个案例的硬剥离改版**：

| 案例 | 版本 B（硬剥离——纯需求） | 剥离后可以做的事 |
|---|---|---|
| **宠物寄养** | 城市一二线养宠用户，过节度假时无法照顾宠物，会出现 XX 问题，现在解决方案是 XX、XX，但依然存在很多问题和风险 | 解决方案不一定是「自营宠物门店」——寄养家庭、互助平台都可能 |
| **醒酒产品** | 日常高频商务喝酒的人，喝酒前存在痛点 123，喝酒后存在痛点 456，现在解决方案 ABC 都不够好 | 解决方案不一定是「醒酒含片」——可能是预防饮品、预约代驾套餐 |
| **AI 工牌** | 销售驱动型公司，在新人培养上花费 XX 成本，人效很低，新人上手周期 XX，留存率 XX | 解决方案不一定是「智能工牌」——可能是培训体系重构、师徒制优化 |

### 4.4 剥离后的三大立竿见影效果

| 效果 | 说明 |
|---|---|
| **早期更专注** | 把稀缺注意力放在更基础、更前置的**关键假设**上——不必一开始就纠结产品细节 |
| **低成本验证** | 用很少的成本、局部测试、调研、证伪就行——不需要做出产品才知道对不对 |
| **手段更灵活** | 不会轻易拘泥于某一个方案、产品和定价——**有很大灵活空间**，先确认问题再选武器 |

### 4.5 现场三练习

| 练习 | 场景 | 硬剥离答案 |
|---|---|---|
| **练习1** | Prompt 超级管家——用户有多平台使用 LLM 的需求 | **剥离**：用户使用多端 LLM，同步变成一个普遍痛点，大幅影响效率。方案不一定是「管家式 App」 |
| **练习2** | 匿名吐槽公司 APP | **剥离**：职场人在公司内部遭受不公或压力时，想要表达但怕职场报复不敢发声。深层需求可能是职场压力和企业文化建设 |
| **练习3** | AI 快速录入 CRM 系统 | **剥离**：一线销售人员每天手动填客户跟进记录超 1.5 小时，工作量大挤占销售时间，且因团队厌烦导致数据填写敷衍甚至大量遗漏 |

## 五、第二部分·进阶：剥离的「度」——拆多大、拆多细

### 5.1 核心命题

> 「这个剥离姿势看似很对，但是太粗了啊——模模糊糊一句话，没什么用啊」

**必须进一步进入用户的视角和决策现场，去分析具体的需求。**

### 5.2 为什么要继续拆？——「我服务所有 XX」不行吗？

**热身思考**：

| 模糊表述 | 问题 |
|---|---|
| 「我服务所有年轻女生」 | 18 岁大学生和 30 岁职场妈妈的痛点完全不同 |
| 「我服务所有法律行业」 | 律所合伙人和法务专员的决策逻辑完全不一样 |
| 「我服务所有单身中产」 | 这个标签下的人群需求可能互相矛盾 |

**战略级别的认知**：需求和场景选择，**就是第一个重大的战略**。

### 5.3 拆解的目标——找到最重要的 3–5 刀

**核心追求**：不是拆得越细越好，而是**找到最重要、最值钱的 3–5 刀**——找到整个产品、服务、商业模式所依赖的**非常真实的客观需求**。

| 原则 | 说明 |
|---|---|
| **3–5 刀是经验值** | 既比较具体又不至于太复杂，导致执行和协作困难 |
| **拆粗拆细不重要** | 关键是找到最关键的差异化维度 |
| **拆用户还是拆问题不重要** | 关键是找到最影响商业成败的那个维度 |

### 5.4 拆解程度判断标准

| 判断维度 | 拆得不够（需要继续） | 拆得刚好 |
|---|---|---|
| **需求一致性** | 拆成 1/2/3/4/5 类，需求不一致甚至矛盾——无法兼容，必须取舍 | 每类用户的需求同质、可一起服务 |
| **营销效率** | 拆到 1/2 层，不够具体和疼，很难做营销和销售，商业效率很低 | 能精准定位、精准触达、精准转化 |

**典型案例·必须继续拆**：洗头机（面向所有人洗头 vs 面向卧床失能人群）、甲骨文动画片（所有孩子 vs 特定年龄段+特定学习场景）、育儿课程多平台分发（所有宝妈 vs 不同阶段妈妈需求完全不同）

## 七、需求拆解三原则（核心框架）

### 7.1 全景总览

**三原则定位**：过往上千个案例中，三类最容易被忽略的关键假设。

```
需求 = 用户 × 场景 × 问题
           │
    ┌──────┼──────┐
    │      │      │
原则一   原则二   原则三
向上支撑  内部证伪  横向自检
```

**一句话总结三个原则**：面对用户/场景/问题，用细分的 3–5 刀，找到细分的 1–30% 的需求 → 能向上支撑 → 内部一致且 sharp → 同时横向里程碑相互匹配自洽、没有显著矛盾和冲突。

### 7.2 原则一 · 向上支撑原则

**核心问题**：你拆出来的需求，跟你追求的**长期预期**匹配吗？

| 长期预期 | 对需求的要求 |
|---|---|
| **预期 5–6 分**（小而美/一人公司/AI项目/IP项目） | 需求不需要太大，够养活自己就行——不必追求大市场 |
| **预期 6–7 分**（规模化/头部） | 必须要找到一个**足够大、足够稳定、足够有机会**的需求——九死一生 |
| **中间地带** | 在一个不够大的需求空间里构建复杂的业务和能力系统——**ROI 往往不高** |

**一句话**：如果你的目标是做头部，但需求只够养活一个小团队——这就是向上不支撑，要么调目标，要么换需求。

### 7.3 原则二 · 内部证伪原则

**核心问题**：你拆出来的需求，内部逻辑自洽吗？能经得住「证伪」吗？

**两个关键检查**：

| 检查维度 | 问题 | 举例 |
|---|---|---|
| **矛盾 or 一致** | 拆出来的多类需求之间有没有明显矛盾？ | 既要高端定制又要极致低价——两类用户需求矛盾，很难同时满足 |
| **模糊 or Sharp** | 需求描述是够具体、够可验证，还是模模糊糊无法证伪？ | 「用户想要更好的体验」= 模糊；「用户希望在 3 次点击内完成下单」= Sharp |

**典型案例·内部矛盾**：

| 案例 | 矛盾点 | 解法 |
|---|---|---|
| **洗头机** | 面向所有人 vs 实际只有失能/卧床人群是刚需——「所有人」需求太散 | 砍到核心刚需人群 |
| **甲骨文动画片** | 所有孩子 vs 真正有甲骨文兴趣的孩子极少 | 重新定义用户和场景 |
| **育儿课程多平台分发** | 孕期/0-1岁/3-6岁妈妈需求完全不同，无法用一套内容覆盖 | 必须取舍阶段 |

### 7.4 原则三 · 横向自检原则

**核心问题**：你拆出来的需求，和后面的里程碑（解决方案/商业模式/增长/壁垒）匹配吗？

**高难度原则**：理想情况可以完全「独立看需求」，但真实情况往往是已有商业全局预判（画布）或已有产品和业务——**需要看「需求」和其他匹配是否有明显的硬伤**。

**横向自检典型案例**：

**案例①·新人直播 AI 助手——「需求 vs 商业模式」硬伤**：

| 维度 | 内容 | 问题 |
|---|---|---|
| 需求 | 新直播素人缺少话术、卖点和 KnowHow 训练 | 看着合理 |
| 产品 | SaaS 训练后台——话术支持、逐字稿打磨、直播反馈 | 看着合理 |
| 商业模式 | 按季度/年续费，月均 1K，替代 5K-2W 陪跑教练 | **❌ 硬伤** |
| **诊断** | 如果产品有用，两三个月就不是新人了 → 自然不需要续费。如果需要续费，需要解决更持续化、日常的痛点 | **用户-商业模式匹配有常识性硬伤** |

**案例②·金同学医美医院——「用户 vs 增长」硬伤**：

| 维度 | 内容 | 问题 |
|---|---|---|
| 需求 | 整形/注射/光电三类求美者 | — |
| 产品 | 整形（重修工程）+ 注射（精装修）+ 光电（日常维护） | — |
| 增长 | 期望业务间相互导流、通过复购/升单实现增长 | **❌ 硬伤** |
| **诊断** | 注射客户很难升单到整形（怕动刀）；整形客户一般一次性服务难卖长期维养；光电客户只追求低价难升单 | **三项业务之间很难实现导流增长** |

**案例③·张同学高端防脱洗发水——「需求 vs 解决方案」硬伤**：

| 维度 | 内容 | 问题 |
|---|---|---|
| 需求 | 年轻脱发焦虑人群——维持发量、防脱固发 | — |
| 产品 | 高端护理——月 200-300 元，主打珍稀植萃成分 | **❌ 硬伤** |
| **诊断** | ①价格不便宜 → 立即被用户和医疗方案做对比，疗效不如医疗 ②若具备严格防脱功效 → 研发周期长成本高，与洗发水价格带不匹配 ③若追求细分头部 → 需客观宣传，但这样很难完成商业目标 | **三个方向互相拉胯** |

**正向案例·秦鹏物联网芯片——「需求 vs 壁垒」匹配**：

| 决策 | 分析 | 结果 |
|---|---|---|
| 选大客户还是中小客户？ | 大客户对收入品牌有利，但无忠诚度；中小客户转化成本高（无研发能力、非常依赖） | 意识到「转化成本」是第一壁垒 → **坚定选中小客户** |
| 后续 | 坚定融资 + 保持低价策略 → 快速抢占市场 → 获得先发优势 | 在更高集中度同时构建「品牌」壁垒，争取未来溢价空间 |

## 八、拆解实操案例集

### 案例①·Evelyn：可视化空气炸锅的需求拆解（2C 经典）

| 版本 | 用户定位 | 数据/逻辑 |
|---|---|---|
| **1.0** | 服务所有想买空气炸锅的人 | 太宽泛，无法精准触达 |
| **2.0** | 用巨量云图拉取厨房电器兴趣人群：25-35 岁占比 62%，女性为主，集中在新一线及以上城市 | 缩小了范围但不是基于产品特性 |
| **3.0** | 基于产品容量小且定价高：愿意为「智能功能溢价 30%+」的用户仅占 18%，约 600 万人 | 关键特征：租房居住、厨房空间小、社交分享欲强 |
| **最终决策** | **放弃已婚已育家庭用户，All-in 都市独居/合租青年** | **转化率达标 + 客单价通过捆绑销售包拉升至 628 元** |

### 案例②·彭同学：工业企业销售报价系统（2B 经典）

**真实痛点**：工业产品结构复杂，前期报价成本无法精准测算，依赖人工经验，导致订单毛利率无法满足要求甚至亏损。

**使用对象**：工业企业负责产品报价的营销人员/成本测算人员/项目管理人员。

**明确非使用对象**（这是高阶拆解的标志——知道不服务谁）：

| 非使用对象类型 | 原因 |
|---|---|
| 产品标准化程度高的企业 | 成本稳定，不需要复杂报价系统 |
| 产品复杂程度低的企业 | 物料清单不超 3 层，成本测算简单 |
| 已上线报价系统的企业 | 不再需要新系统 |
| 营收小于 5 亿的企业 | 管理水平和业务能力跟不上系统 |
| 流程行业（石油化工/医药等） | 产品一次成型，不需要各阶段成本测算 |
| 快销品行业（烟酒日化等） | 自主定价，不需要面向客户报价 |

## 九、高段位心法：需求分析三要素内在逻辑

**进阶理解·USP 完整模型**：

```
用户（User）
  ├── 上一个场景 → 场景（Situation / JTBD）→ 下一个场景
  │                                        │
  └── 差距（Gap）← 阻碍/问题（Problem）←──┘
                         │
                    需求（Demand）
```

**关键理解**：
- JTBD（待办任务）是用户渴望达成的进步（Progress）——它连接了场景和问题
- 差距（Gap）= 用户「现在在哪」和「想去哪」之间的落差
- 需求 = 用户 × 场景 × 问题——三要素缺一不可

**为什么不是「用户 × 场景 × 需求」？**
- 因为「问题」是客观的、可验证的——「需求」常常被用户自己包装成解决方案
- 如果把「需求」放进公式，就回到了「用户嘴里说的功能」——失去了剥离的意义
