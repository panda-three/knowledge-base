## 〇、课程总纲

> **"明明计划做得好好的，怎么到执行都是灾难？需求老变、大量返工、大量延迟、团队懈怠、关键人要走……但那又怎么样？好的项目管理是神挡杀神，佛挡杀佛，无论如何项目都能完成的。"** —— 花匠

### 课程定位

| 维度 | 说明 |
|---|---|
| **所属系列** | 项目管理五课中的第 4 节 |
| **对应基本功** | 项目管理四步中的第 3 步——**管执行** |

## 一、Leo 的失败案例——为什么计划完美不等于执行顺利

> **这 45 天如果让你来管，你会怎么带这个项目组？**

### 1.1 项目背景

| 要素 | 内容 |
|---|---|
| **项目** | 制作一本手册，把一堂课程关键工具/模型/清单放进去 |
| **时间** | 4 月 1 日启动 → 5 月 15 日 90% 同学拿到 |
| **总时长** | 45 天 |
| **敏感维度** | 时间敏感（DDL 不可动）+ 人力敏感（不能补人）+ 协作敏感（新人第一次管）+ 风险敏感（无经验）+ 老板敏感（Truman 高度关注） |

### 1.2 Leo 是怎么管的（失败的管法）

```text
Leo 的邮件：

"大家好，下周一（4.1）开始执行，5 月 15 日结束。文档看附件。
项目期间，每周四下午 3-4 点开一个项目例会，碰一下进展。加油！"
```

| Leo 做的 | Leo 没做的 |
|---|---|
| 发了方案文档和甘特图 | 没有开启动会，没有当面确认分工 |
| 定了每周四一次周会 | 沟通频次一周一次，等发现延期已经是 5 天后 |
| 周会前花 2-3 小时收集进展 | 没有提前定质量标准，没有评审关键交付 |

### 1.3 灾难的连环事故

| 事故 | 教训 |
|---|---|
| 设计师 4 月 7 日突然生病请假 3 天，各模块受影响 | 没有关键人备份意识，没有高频跟进 |
| 排版完成找 Truman 评审发现内容有问题，5 天工作量重做 | 质量节点没有前置评审，内容没审就排版 |
| 设计师崩溃发飙 | 体验管理缺失，团队心态崩了 |
| 第一周结束，排期完全失效 | 变更发生时没有走变更流程 |
| 项目连滚带爬结束后，同事偷偷跟老板说"下次能不能换个项目经理" | 信任崩塌——**项目能交付但人崩了，长期是更大的失败** |

> **核心教训：做好计划只是规划，大量项目结果是靠中期过程管理出来的。如果只做计划不管过程，等于把命运交给运气。**

## 二、前置判断：六维敏感度 → 管执行侧重点

> **和拆计划一样，管执行也要先判断项目敏感度在哪，把管理重心压在最敏感的维度上。**

| 敏感维度 | 对应的管执行重点 | 说明 |
|---|---|---|
| **预算敏感** | 质量管理 | 一次性做对、少返工 |
| **时间敏感** | 进度管理 | 盯住关键路径每一天 |
| **人力敏感** | 变更管理 | 应对不确定性，提前预判 |
| **风险敏感** | 变更管理 | 识别变化 → 分析风险 → 变更处理 |
| **协作敏感** | 体验管理 | 让大家愿意跟着你做项目 |
| **老板敏感** | 向上管理 | 让老板省心、放心、有信心 |
| **各类冲突** | 冲突管理 | 及时化解，不留隐患 |

> **铁律：管执行不是平均用力。你项目的敏感度在哪，你的管理精力就重点投在哪。**

## 三、管好事情①：进度管理

> **核心思想：盯时间。核心是对执行 GAP（差距）——对目标和计划，是不是如期进行。**

### 3.1 三层递进

| 层级 | 动作 | 具体内容 |
|---|---|---|
| **第一层：培养意识** | 遵守计划 | 项目计划已做好，请按时间表执行 |
|  | 定期同步 | 用好周报/周会/日会的机会 |
|  | 及时周知 | 有风险，第一时间周知（至少向上周知） |
| **第二层：丰富手段** | 根据场景选工具 | 线上/线下 × 同步/异步沟通象限图 |
| **第三层：提升频次** | 匹配敏感度 | 越敏感的项目沟通越密 |

### 3.2 进度跟进沟通象限图

> **选择什么沟通方式，看四个维度：复杂程度、紧急程度、沟通成本、沟通范围。**

| | **异步沟通** | **同步沟通** |
|---|---|---|
| **线上** | 顶层文档、电子看板、群聊消息、邮件 | 1v1 发消息、1v1 电话、项目群 |
| **线下** | 墙面看板 | 坐你旁边、1v1 当面、团队例会、攻坚小组、封闭研发 |

**选择原则：**

- 线上 & 异步：成本很低，效率高，但互动弱
- 线下 & 同步：方便讨论，速度快，但成本高
- 邮件超过 3 轮还没解决 → 直接当面过，不要继续邮件拉锯

### 3.3 沟通频次 Checklist

| 频率 | 管理手段 |
|---|---|
| **里程碑** | 评审会、复盘会 |
| **月** | 月会、月报 |
| **周** | 周会、周报 |
| **天** | 日例会、日报、早晚 1v1 |
| **全程陪伴** | 搬小板凳坐旁边、攻坚小组（0.5-5 天集中突击） |

> **Leo 的核心教训：45 天的高敏感度项目只开一周一次周会，发现延期时已经是 5 天后，5 天的工作量就已经浪费了。沟通频次必须和项目敏感度匹配——越敏感越密。**

## 四、管好事情②：质量管理

> **核心思想：守节点。质量管理不是狭义的"质量"，而是『关键节点的完成水准』。在创业公司，如果不主动管质量，那些问题最终会成倍地还给你。**

### 4.1 质量失控的四种常见后果

| 后果 | 表现 |
|---|---|
| **事后返工** | 前一环节出问题，倒推回去重新做（如 Leo：排版完才发现内容要改，5 天白干） |
| **领导推翻** | 做了一大堆，领导说不行，重新做 |
| **项目失败** | 没达到质量指标，最终目标没达成 |
| **掩耳盗铃式质量** | 评审会变夸夸会，3 个人"帮忙审"没人认真看，老板一晚上找出 50 个错误 |

### 4.2 质量管理的三类关键节点

> **守住三类重要的质量节点：完成子目标 + 检查质量过关 + 评审关键交付。**

| 类别 | 核心问题 | 关键要求 |
|---|---|---|
| **A. 关键子目标** | 最终目标依赖哪些子目标必须完成？ | 从最终目标拆出，定量，符合 SMART 原则 |
| **B. 质量约定** | 做到什么程度才叫质量过关？标准和约定是什么？ | 提前约定好标准，不要中途乱改乱加；检查人要签字负责 |
| **C. 交付物评审** | 关键交付物需要谁评审、拍板才能进入下一步？ | A 角色（拍板人）必须在；关键利益相关方一起评 |

### 4.3 质量管理画布（以手册项目为例）

| 质量把控 | 具体内容 |
|---|---|
| **A. 关键子目标** | 收集地址率 > 85% |
| **B. 质量约定** | ①错别字 = 0 / ②排版错误 = 0 / ③二维码错误 = 0 |
| **C. 交付物评审** | ①手册封面评审（Truman）/ ②目录大纲评审（Truman + 花匠）/ ③工具页风格评审（Truman）/ ④小样终版评审（Truman + 花匠） |

### 4.4 质量评审的铁律

| 原则 | 说明 |
|---|---|
| **质量通过** | 可以进入下一步；可以交付任务撤出去；可以付钱 |
| **质量不通过** | 原地修改、迭代，直到验收合格 |
| **评审不是夸夸会** | 关键评审要严肃，不能嘻嘻哈哈，漏掉的问题会后成倍还给你 |
| **质量可以硬，沟通可以软** | 该卡住就卡住，但对人的态度要柔软——你管质量是在帮他补短板 |

### 4.5 "被卡心态"缓解

> 有些 R 会觉得你在故意卡他。你可以说：
>
> - "我知道你是为项目好，我也是。正因为我们都想做好，这个节点才必须过一遍。"
> - "这不是针对你，这是咱们一起对最终结果负责。"
> - "早卡出来，比后面推翻重做强 100 倍。"

> **质量管理没做好 = 返工 + 推翻 + 失败。管质量不是在卡人，是在救整个项目。**

## 五、管好事情③：变更管理

> **核心思想：控变化。项目执行中变化一定会发生，关键不是不让变，而是有一套处理变更的流程。**

### 5.1 变更处理四步法

```text
识别变化 → 分析风险 → 变更处理 → 风险可控
```

### 5.2 第一步：识别变化——常见变更类型清单

> **作为项目经理，变化发生的第一时间要有敏感性：这个变化重要吗？会有高风险吗？**

| 分类 | 具体情况 |
|---|---|
| **方案类** | 老板新想法 / 政策变了 / 甲方变了 / 前期没细化没想清楚 / 有更优选项 / 情况不符合预期 |
| **进度类** | 计划要提前 / 大量任务超时 |
| **人力类** | 有人请假了 / 成员被调走 / 被卡在其他项目上 / 能力远不如预期 |
| **质量类** | 大家能力不够需降低标准 / 改标准才能达到目标 |
| **预算类** | 预算少了 / 预算花多了 |

> **建议把这个清单多读两遍，培养敏感性。有敏感性才能第一时间识别变化。**

### 5.3 第二步：分析风险——重要变更 vs 灵活处理

> **判断核心：这个变化是否严重影响最终目标、资源投入、团队协作？**

| 处理方式 | 判断维度 |
|---|---|
| **走变更流程** | ①严重影响最终目标 ②严重影响资源投入 ③严重影响团队协作 |
| **灵活处理** | ①不影响最终目标 ②不影响资源投入 ③不影响团队协作 |

> **有些人总是小变化很计较，大变更却很随意。你要兼顾灵活性和计划性——太硬失去主动性，太软计划全废。**

**举例：** 年会 PPT 尺寸从 16:9 改 4:3，什么情况下算重要变更？

- 已经 4-5 个人做好几十页 → 影响团队协作 → **走变更** ✅
- 不改没法在最终机器上播放 → 影响最终目标 → **走变更** ✅
- 刚做好模板一个人改一下就行 → **灵活处理**

**举例：** 手册项目哪些算重要变更？

- 内页从黑白变彩色 → 影响人力/排期/预算/协作 → **走变更** 
- DDL 从 5 月 15 日改为 12 日 → 影响排期 → **走变更**
- 改变纸张材质 → 只影响一个小细节 → **灵活处理**

### 5.4 第三步：变更处理——三项工作

| 主要工作 | 具体做法 | 注意事项 |
|---|---|---|
| **重新评审** | 拉老板 & 相关负责人一起讨论，估算 ROI，预估风险是否可控 | 避免简单拍脑袋 |
| **迭代计划** | 修改方案和计划文档，最好加上版本号 | 避免混乱 |
| **周知确认** | 用邮件 / 开会 / 当面等方式，确认团队知晓；重要负责人 1v1 当面确认 | 避免信息不对齐 |

### 5.5 第四步：风险可控

变更落地后，在后续项目例会上：

- **强调这个变更**，做备忘
- **强调变更的价值**（如果变更带来正面收益）
- **感谢大家的支持**，不要让团队觉得"又变了很烦"

### 5.6 Leo 变更前后对比

| | **原来的 Leo** | **变强后的 Leo** |
|---|---|---|
| 识别变化 | 新点子：升级成彩色更好 | 新点子：升级成彩色更好 |
| 分析判断 | "肯定更好啊，风险没事儿，改。" | 评估风险：①预算风险 ②人力风险（设计+排版）③时间风险 ④协作风险 |
| 执行变更 | （没有） | ①拉评审会（关键负责人+Truman + ROI估算）②升级计划（更新方案+排期）③同步周知（邮件+1v1当面确认） |
| 风险可控 | 设计师不爽 / 排期没同步 / 运营后来才知道 | 后续 2 次例会：强调变更 + 强调彩色价值 + 感谢支持 |
| **结果** | delay、返工、信息脱节 | 风险可控，团队知晓，顺利推进 |

## 六、管好团队①：向上管理

> **核心思想：给安心。管得好不好，本质上是你领导的工作是不是成功。如果老板不知道你做了什么，相当于你没做。**

### 6.1 什么是好的向上管理？

**三心 + 二意：**

| 维度 | 含义 | 反例 |
|---|---|---|
| **省心** | 主动把关心的信息告诉我，别让我担心 | 老板没事就过来问"咋样啦？" |
| **放心** | 知道在轨道上，如期进行，把心放肚子里 | 老板比你还焦虑 |
| **有信心** | 对团队和完成目标，有越来越强的信心 | 老板觉得别人的项目做得更好 |
| **有意识要资源** | 搞不定的事主动请求支持 | 硬扛到最后一刻才说 |
| **有意识做汇报** | 里程碑和进展主动汇报 | 老板从别人那听到你的坏消息 |

### 6.2 向上管理的五个具体动作

| 动作 | 核心要点 |
|---|---|
| **1. 让老板省心** | 给文档，让老板方便知道进展；关键进展/交付物拉老板参与进来 |
| **2. 让老板放心** | 关键风险尽早让老板知道——**比起坏消息，老板更怕没消息；比起没消息，老板更怕从别人那里传来你的坏消息** |
| **3. 让老板有信心** | 风险不但要说，还要带着解决方案去说——"这个风险我们已经有方案了，A/B 两个选项，我建议 A" |
| **4. 有意识要资源** | 七类可要的资源：老板花时间评审 / 老板花时间推进 / 加更多资源 / 团建成本 / 老板刷脸催进度 / 争取专家或关系 / 给团队特别支持（信心/打气） |
| **5. 有意识做汇报** | 里程碑达成、关键交付完成、重大变更落地——主动开会或发邮件，感谢老板和同事 |

### 6.3 Leo 向上管理前后对比

| | **Before** | **After** |
|---|---|---|
| 省心 | 老板不问就不说 | 保证基本文档同步制度 + 关键事项主动说 |
| 放心 | 重大风险是别人告诉老板的 | 内容可能写不过来了，主动说一下 |
| 有信心 | 经常让老板临时补位 | 想好怎么解决风险保证项目完成 |
| 要资源 | （不会要） | 自己搞不定的部分，让老板补人或帮忙写 |
| 做汇报 | （没有） | 内容定稿，主动开汇报会，感谢老板和同事 |

## 七、管好团队②：体验管理

> **核心思想：舒服安心。让大家觉得"自己有收获，顺便达成了你的目标"——而不是"帮你完成了 KPI"。**

### 7.1 十五字体验管理法则

| 法则 | 含义 | 话术示例 |
|---|---|---|
| **讲地位** | 让对方知道他在项目里很重要 | "终于跟你合作上了！""听说是你负责我好放心" |
| **有成长** | 让成员在项目中学到东西 | "相信做完这个项目，你在平面设计上就能独当一面了" |
| **在一起** | 保持归属感和连接感 | "你自己加班太辛苦了，我陪着你，想吃啥我去买" |
| **给信任** | 放心授权，不 micromanage | "在这方面你才是最专业的，你的意见我就觉得没问题" |
| **喜欢你** | 真诚尊重和关心团队成员 | "这次幸亏有你，咱们才能及时做完这个项目" |

### 7.2 体验管理四类问题场景

| 场景 | 解法启发 |
|---|---|
| **对方觉得这个项目跟他没关系** | 用"讲地位"：告诉他这个项目的价值，他的角色为什么不可替代 |
| **对方觉得只是额外负担** | 用"有成长"：做完这个项目他能得到什么新能力、新经验 |
| **团队氛围冷淡/互相不熟** | 用"在一起"：不只是工作群，创造并肩作战的体验 |
| **R 不敢做决定，事事等你确认** | 用"给信任"：明确说"这件事你定，出了问题我扛" |
| **项目做完团队散了没人记得** | 用"喜欢你"：真诚感谢每个人的贡献，让付出被看见 |

> **Leo 的教训：项目能交付但团队体验崩了，同事偷偷说"能不能换个项目经理"。一个让团队痛苦的项目经理，做成的项目也在透支未来的协作信任。**

## 八、管好团队③：冲突管理

> **核心思想：止争论。冲突是现象，根源通常在四类问题上：理解问题、质量问题、资源问题、立场问题。**

### 8.1 冲突的四类根源

| 类型 | 核心问题 | 典型表现 |
|---|---|---|
| **理解问题** | 信息没对齐，或思考方式不同 | "你上次不是这么说的""我以为你知道" |
| **质量问题** | 在评估标准上有分歧，觉得被卡住 | "你为什么总是卡我？""这个标准怎么不早说？" |
| **资源问题** | 已经说好了又改，安排被打乱 | "我都安排好了你要我加班？""说好不改你又变" |
| **立场问题** | 部门不同、屁股不同、目标不同 | "我们部门的优先级不是这个""这不符合我们的规范" |

### 8.2 冲突管理五步法（从低到高使用）

```text
好好说话 → 对齐信息 → 协调资源 → 各退一步 → 向上升级
```

### 8.3 五步法详解

| 步骤 | 适用场景 | 核心话术（保姆级） |
|---|---|---|
| **1. 好好说话** | 情绪化沟通、着急、争吵 | ①看见情绪："如果我刚才的话让你感觉不好了，我跟你道个歉" ②自己平静："咱们先深呼吸一下，慢慢说" ③外力放松："来来来吃饭去，没有啥是一顿火锅解决不了的" ④肯定态度："我知道你是为项目好，我和你是一条心想解决问题" |
| **2. 对齐信息** | 信息不对称、误解 | ①明确冲突："你觉得咱们现在讨论的冲突点到底是啥？" ②澄清信息："你是这个意思吗？（对 A）你是这个意思吗？（对 B）" ③找到共识："我听下来不矛盾，都是一个意思" |
| **3. 协调资源** | 资源不足、时间不够 | ①"是不是你最近太忙了？我跟老板说帮你补个人" ②"时间压力太大，改到 XX 可以吗" ③"我知道 XXX 有这方面经验，我去协商让他支持你" |
| **4. 各退一步** | 双方都有道理，但有分歧 | ①"要不然我把功能简化一下，这两天你能辛苦点赶赶进度？" ②"如果这么做，你可以得到 XXX，我需要付出 XXX，对我们都合适" ③"这样，我们都各退一步行不行？（你看他都退了，你也退一步吧）" |
| **5. 向上升级** | 立场/优先级不可调和 | ①"我们目标不一致，拉 XX 进来一起判断" ②"这个优先级问题，升级让老板来判断" ③"哪个级别的老板能判断？拉进来" |

### 8.4 Leo 的冲突管理实战

> 设计师和教研在封面颜色上吵起来了——
>
> 设计师："怎么能不用黄色？一堂品牌 VI 都是黄色！"
> 教研："黄色在直播间绿幕抠像会有问题，太丑了！"
>
> Leo 用三步解决了：

| 步骤 | Leo 的话 |
|---|---|
| **1. 好好说话** | "我去，没想到大家对这个手册这么上心，脾气最好的两个人都急了。来喝口水，我们一起看看折中方案如何？" |
| **2. 对齐信息** | "咱们的冲突点主要是品牌一致性和绿幕问题对吧？绿幕这个问题重要吗？如果重要，就只解决它就好了。" |
| **3. 协调资源** | "所有问题都卡在绿幕这？我去协调，换成蓝幕应该就好。增加大概几百块预算，替换一下直播间幕布，全部搞定！" |

> 结果：一个可能升级的冲突，三步就化解了。

## 九、一个被严重低估的工具：执行启动会

> **"前面开好启动会，后面不用跑断腿。"一个好的启动会，可以把今天讲的重点全部放进去。用 2 小时前置解决执行阶段的很多问题。**

### 9.1 启动会能前置解决的 80% 内容

| 今天学的内容 | 在启动会上怎么讲 |
|---|---|
| **明确分工** | 当场确认一遍计划、排期、Deadline |
| **培养意识（进度）** | 要求大家按计划执行，及时同步，及时抛风险 |
| **确定质量** | 明确最重要的 3-5 个质量点，要认真评估、把控 |
| **明确变更** | 有变更及时提，我们有变更讨论流程 |
| **营造氛围（体验）** | 讲讲项目价值、大家的地位、彼此要信任 |

### 9.2 剩下 20%：打好预防针

| 预防针 | 目的 |
|---|---|
| "这项目很重要，我会高频跟进的" | 让大家接受高密度沟通 |
| "老板很关心，请大家有风险及时抛出来" | 建立"透明 > 隐瞒"的文化 |
| "质量线会严格把控，关键节点不妥协" | 让评审不被当作"找茬" |
| "大家难免会有摩擦，希望大家多多体谅" | 降低冲突发生时的情绪烈度 |

### 9.3 启动会 SOP（简版）

```text
会前：
- 确认参会人员：谁必须来，谁看纪要就行
- 提前 24 小时发文档，关键人员提前沟通方案可行性
- 准备几句点燃的话（甚至写逐字稿）

会中：
1. 开篇阐述价值：讲项目为什么重要，点燃大家（公司价值 + 个人成长激励）
2. 明确关键方案：再次同步项目目标、关键方案点
3. 明确关键事项：关键任务、里程碑、交付物
4. 明确关键职责：现场确认 R 和 S，确认任务和交付时间
5. 明确协作机制：沟通制度、风险对策

会后：
- 输出会议纪要，下一步计划写清责任人 + 截止时间
- 发邮件，要求回复确认或签字画押
```

## 十、Leo 的完整改变——管执行升级全景

### 10.1 Leo 六大维度升级对照

| 维度 | 原来的 Leo | 变强后的 Leo |
|---|---|---|
| **进度** | 每周一次周会，等发现延期已经是 5 天后 | 关键路径每天跟进，非关键路径每周 2-3 次 |
| **质量** | 做完才找人看，排版完发现内容要重做 | 提前定质量画布：关键子目标 + 质量约定 + 交付物评审 |
| **变更** | "肯定更好啊，风险没事儿，改。" | 识别变化 → 评估风险四维度 → 拉评审会 → 更新计划 → 周知所有人 |
| **向上管理** | 老板不问就不说，重大风险别人告诉老板 | 省心/放心/有信心/有意识要资源/有意识做汇报 |
| **体验管理** | 只盯进度表，不管人感受 | 讲地位/有成长/在一起/给信任/喜欢你 |
| **冲突管理** | "别吵了别吵了"（插不进话） | 好好说话 → 对齐信息 → 协调资源（三步化解颜色之争） |

### 10.2 最终结果

```text
从：连滚带爬勉强搞定，同事悄悄说"下次能不能换个项目经理"
到：高效推进、团队舒服、老板安心、风险可控
```

## 十二、花匠的核心管理哲学

| 金句 | 含义 |
|---|---|
| "明明计划做得好好的，怎么到执行都是灾难。" | 计划解决"做什么"，管执行解决"怎么做到" |
| "好的项目管理是神挡杀神，佛挡杀佛，无论如何项目都能完成的。" | PM 的终极信念：什么变量来了都能应对 |
| "方案定了、计划拆了只是规划，大量项目结果是靠中期过程管理出来的。" | 不要以为计划做好了就等于项目做好了 |
| "如果你不做向上管理，老板就会来向下管理你。" | 你不是在巴结老板，是在让决策者始终掌握足够信息 |
| "比起坏消息，老板更怕没消息；比起没消息，老板更怕从别人那里传来你的坏消息。" | 透明 > 隐瞒；主动 > 被动 |
| "你自己有收获，顺便达成了我的目标——这才是最好的体验管理。" | 成就他人 = 成就项目 |
| "前面开好启动会，后面不用跑断腿。" | 启动会是被严重低估的管理杠杆 |
| "质量可以硬，沟通可以软。" | 该卡住就卡住，但对人的态度要柔软 |
| "管执行不是平均用力。敏感度在哪，你精力就重点投在哪。" | 精要主义同样适用于项目管理 |

## 十三、L6 刻意练习自检清单

### 进度管理

- [ ] 我是否判断了项目的敏感度，并据此决定了沟通频次（而不是固定每周一次）？
- [ ] 我的沟通手段是否匹配了当前场景（复杂度/紧急度/成本/范围四个维度）？
- [ ] 当发现执行 GAP 时，我是否第一时间调整了跟进步调，而不是等下个周会再说？
- [ ] 我是否有能力根据项目节奏在"月/周/天/全程陪伴"之间灵活切换？

### 质量管理

- [ ] 我是否在动手执行前，就画好了"关键子目标 + 质量约定 + 交付物评审"三列画布？
- [ ] 每个关键交付物是否明确了评审人（A 角色）和评审标准？
- [ ] 我的评审会是不是真的在"审"，而不是变成了夸夸会？
- [ ] 当有人觉得我在"卡他"时，我是否能既坚持质量标准、又照顾对方感受？

### 变更管理

- [ ] 变化发生时，我是否第一时间走完了"识别变化 → 分析风险 → 变更处理 → 风险可控"四步？
- [ ] 我是否能区分"重要变更走流程"和"小变化灵活处理"？
- [ ] 变更处理后，我是否更新了计划和文档，并周知了所有相关人？
- [ ] 变更落地后，我是否在后续例会上持续跟踪、确认风险没有复发？

### 向上管理

- [ ] 我是否做到了让老板省心（主动同步信息）、放心（风险提前说）、有信心（带解决方案）？
- [ ] 老板是否不需要追着我问"咋样了"？
- [ ] 搞不定的事，我是否主动向老板要了资源（而不是硬扛到最后一刻）？
- [ ] 关键里程碑达成 / 重大变更时，我是否主动做了汇报？

### 体验管理

- [ ] 我是否在项目启动时就让大家知道"这件事为什么值得做"（讲地位）？
- [ ] 每个核心成员是否知道自己做完项目后能收获什么（有成长）？
- [ ] 项目期间，我是否创造了"在一起"的体验，而不只是线上发消息？
- [ ] 我是否对关键成员表达了真诚的信任和感谢？

### 冲突管理

- [ ] 发生冲突时，我是否先做了"好好说话"——安抚情绪、肯定态度？
- [ ] 我是否能快速定位冲突根源（理解 / 质量 / 资源 / 立场）？
- [ ] 我是否按五步法从低到高推进，而不是一步跳到"向上升级"？
- [ ] 冲突化解后，我是否确认了双方对解决方案都认、团队关系没有裂痕？

### 综合自检

- [ ] 启动会是否覆盖了今天学到的全部关键内容（分工 / 标准 / 变更流程 / 氛围 / 预防针）？
- [ ] 我的管理手段是否和项目敏感度匹配（而不是一成不变地用固定套路）？
- [ ] 和上次管项目相比，这次在哪个维度上有可感知的进步？
- [ ] 项目做完后，团队成员是更愿意还是更害怕下一次跟我合作？
