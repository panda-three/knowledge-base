# 知识库输入归档（分拣）

把 05-收件箱 里的待分拣输入（多来源汇聚的唯一缓冲区）按既定规则沉淀进知识库四层，AI 全权维护、用户零手工、**原件永不物理删除**。

## 职责边界（重要）

- **接收 ≠ 分拣**：定时任务每天 12:00 只负责把飞书「知识库输入」群新消息落盘到 05-收件箱；本 skill **只做分拣**——从收件箱读取，不做群拉取（除非用户明确说"顺便把群里的也收了"）。
- 收件箱是多来源缓冲区：飞书群（定时任务收）/ 其他对话（用户说"存到知识库"时落盘）/ 手动文件（用户自己放），都会出现在这里，分拣时按条目的 `source` 字段区分。

## 执行流程（六步）

### ① 扫描收件箱

1. `ls 05-收件箱/` 读取全部待分拣条目；
2. 每条含：原文 + 来源 + 日期 + 意图标记（A 任务 / B 资料 / C 混合）；
3. 收件箱为空 → 提示"暂无待归档；如果群里发过消息但定时任务没跑到，告诉我我手动接收一次"，结束。

### ② 留存筛选（四类标准，任一命中即留）

逐条对照，输出"留/不留+理由"：

1. **结构符合/新体系**：能放进现有子文件夹，或构成新知识体系；
2. **事实可验证+可成案例**：数据查得到，能围绕我的相关主题（教育/AI/刻意练习/双三角/作品）变成案例；
3. **新启发**：读完产生新认知或联想；
4. **知识库逻辑补充**：库中没有但按知识库逻辑有意义。

不留典型：空文件、一次性工具、社媒杂集、鸡汤、无法核验的断言、与库内重复且无增量。不留的条目**同样移入归档区**（不删除），汇报时说明理由。

### ③ 来源核验

对"留"的条目联网搜索核验：来源真实、发布者可靠、关键事实可查证。结果写 YAML `source`：
- 核验通过 → 按类型正常落位；
- 核验不过/来源不明 → 降级进 02，标 `status: 初稿` 待验证；
- 完全不可信 → 不留（理由：来源无法核验），原件仍进归档区。

### ④ 知识类型判定

对照知识库现有内容（检索相关文件夹）判定：新知识 / 旧知识（无增量不留，有增量补充原笔记或独立落位）/ 已验证知识（优先合并引用）/ 强逻辑关系知识（YAML `related` 关联）/ 案例类（01 或 03/95-素材）/ 证明类（01，`related` 关联结论笔记）。

### ⑤ 转化落位（四层去向）

- **01-实事求是**：**默认拒入（2026-09-19 准入闸）**——外部新素材一律先落 02；仅「经过准入闸勾验、成体系可调用、经用户拍板升级」的成熟体系才进（一堂官方体系 / 经典公认 / 高验证度外部作品四验齐全 / 本人反复验证且真·成体系可对外调用，否则留 03）。进 01 的文件 YAML 须写 `verification:`（方式/证据/日期）。拿不准一律降 02，不自动往 01 放新东西；
- **02-解放思想**：新观点/假设/思考/时效性评测（外部观点、方法论、研究笔记都先进这里，实践验证后升 03）；
- **03-知行合一**：本人亲身实践/可复用素材（新增默认 `status: 待应用`，凭证缺失即待应用）；
- **00-天一生水**：规则、任务、关于我、评估、日志（任务→`01-系统文档`、规则→`03-基本法`、评估→`06-评估报告`）；
- **判不了或需用户裁决** → 暂留 `05-收件箱`，汇报时列为"待裁决"。

**落位铁律**：
- 落**子文件夹**绝不落根目录（无匹配子目录的新建主题域或进 `99-其他`）；
- 文件名 = 类型前缀 + 主题（≤15字），如 `研究：AI上下文工程.md`、`思考：xxx.md`、`方法：xxx.md`；
- 补 YAML：`type / status / date / source / audience / tags / related`；
- **写 markdown 一律用 python3 原始字节**（Write 工具会把 frontmatter 的 `---` 转成 `***` 破坏 Obsidian YAML）：
  ```python
  with open(path, "w", encoding="utf-8") as f: f.write(content)
  ```
- 涉及隐私/未定稿/对外发布的内容先不落位，标注"需用户裁决"；
- 用户偏好：**过程文档归档前先列全部候选清单经用户确认**，或由用户主动触发，不静默自动落位。

### ⑥ 原件归档 + 汇报记录

1. **原件移入归档区**（关键安全机制，永不物理删除）：
   - 把收件箱每条（留和不留的都算）原样移动到 `00-天一生水/99-归档/收件箱原文/YYYY-MM/<原名>`；
   - **成品特例（2026-09-17 定）**：输入本身即成品（无需提炼加工、落位=原样放置，如已转录完成的课程文档/已定稿文件）时，归档区**不再整份复制**，只记一条索引说明（`.md`：原件名 + 落位位置 + 日期 + 来源），原件本体即落位文件，不重复存；
   - 落位文件内可加一行 `> 原件归档：99-归档/收件箱原文/YYYY-MM/<原名>` 方便追溯；
   - 收件箱此时为空（= 原件已搬走，不是删除）。
2. 更新 `00-天一生水/00-vault-log.md`（记：日期、收 X 条、留 N 条去向、不留 M 条原因、待裁决 K 条、原件归档位置）；
3. 向用户汇报：今日收 X 条 → 留 N 条（各去向分布）→ 不留 M 条（原因摘要）→ 待裁决 K 条；每条消息的去向 + 原件位置交代清楚。

## 归档区生命周期管理（防堆积，但删除权在用户）

- **默认永久保留**：原件移入归档区后不动；
- **30 天后 AI 体检**（每次归档或收到"清一下归档区"指令时顺带做）：检查每个原件对应的落位文件是否已完整包含原件内容：
  - 已完整 → 标记「可清理候选」（内容已在库中，原件冗余）；
  - 未完整 → 继续保留（还有未提炼的信息，AI 补提炼后再标）。
- **用户拍板**：用户说"清一下归档区"时，列出《可清理候选清单》（原件名 + 对应落位文件 + 日期），用户确认哪些删 → AI 才删；不说就不删。用户也可手动删归档区文件。
- 每次归档汇报时顺带一句归档区规模（如"归档区现有 23 条，其中 8 条可清理"）。

## 常见输入形态处理

| 输入 | 处理 |
| --- | --- |
| 文字片段 | 提炼核心转档（意图识别合并连续消息） |
| 公众号链接 | 抓正文；抓取受限时存链接+摘要（用户已确认可接受） |
| 飞书 wiki/docx 链接 | 抓正文（web_fetch 或 lark-doc），外部课程文档归 02 |
| PDF/图片 | 解析或 OCR（用 doubao-pdf 等） |
| 任务指令（A） | 归档 `00-天一生水/01-系统文档/任务：*.md`（含原话+AI 解析+状态待确认） |
