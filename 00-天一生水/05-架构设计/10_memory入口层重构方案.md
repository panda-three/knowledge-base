# 10 memory 设计思想迁移与入口层重构方案

> **一句话结论**：memory 治「记忆与协作」，当前库治「存储」，两者正交。本方案**保留六层内容结构**（00-05 不动），但**推翻「根目录只放 _Home」与「规则集中写」两条旧前提**，按 memory 思路重构入口层——根目录放「身份四件 + 系统入口」、新增「专注区」承载当前工作、每个文件夹就近放 `_agent.md` 规则。主入口统一用厂商中立的 `AGENTS.md`（不加 CLAUDE.md 指针），保证换模型/换工具不受影响。

---

## 〇、两个第一手事实（本次核查，决定方案前提）

1. **memory 是一套「零实战」模板**：全部 15 个文件修改时间都是同一秒（2026-11-15 20:02，即拷贝那一刻），`_本周.md` 全是占位符、`MEMORY_LOG.md` 是示例、`ITERATION_LOG.md` 只有基线条目。**设计思想好，但从未被真正跑通过。** 故采纳其思想，落地必须小步试点验证，不能假设已成熟。
2. **当前库 Obsidian 是活的**：`.obsidian/workspace.json` 持续在更新。改根目录结构会牵动工作区与自动化（体检/分拣/双链脚本），必须带验证改。

---

## 一、目标重述（用户真正要的）

不是「把 memory 文件夹搬进来」，也不是「一套逻辑上最优的分类体系」，而是——**一个打开就懂、AI 不会漏读规则、能一眼看到自己在干嘛的工作台**。具体三个明确诉求：

1. **根目录放灵魂/记忆/用户等文件**，方便查看（每次开机零成本可见）。
2. **独立专注区**，进入知识库即可看到「当前正在做什么」。
3. **每个文件夹一个 agent 规则文件**，查询某模块时就近依据该文件的规则。

**两个正交问题**：

| 问题 | 现状 | 结论 |
|---|---|---|
| 存储问题（东西放哪、怎么分层） | 六层结构 + 准入闸 + YAML + 收件箱流水线，是资产 | **保留，一个文件不动** |
| 记忆/协作问题（AI 怎么持续了解你、怎么协作） | 偏好散三处、无生命周期、无专注区、规则集中写 | **按 memory 思路补建** |

---

## 二、CLAUDE.md 跨模型问题与入口文件决策

**分两层看**：

- **内容层 100% 跨模型**：CLAUDE.md 里全是自然语言规则，任何模型都能读懂照做，与 Claude 无绑定。
- **「自动读取」层是工具约定，不是模型能力**：`CLAUDE.md` 被自动注入是 Claude Code/Cowork 的私有约定；Cursor 认 `.cursor/rules`、Copilot 认 `.github/copilot-instructions.md`、Gemini 认 `GEMINI.md`。换工具后内容仍可用，但「自动注入」可能失效。

**决策（用户已定）**：

- 主入口**统一用 `AGENTS.md`**——厂商中立开放约定（Codex/Cursor/Copilot/Jules 等均认），换模型/换工具不受影响。**不加 `CLAUDE.md` 指针**，避免双入口。
- `SOUL.md / USER.md / MEMORY.md / 00-专注区` **不是任何厂商约定，只是普通文件名**，任何模型通用，无需改动。

## 三、目标结构

```
knowledge-base/
├── AGENTS.md           ← 系统入口（厂商中立，统一入口，AI 每次会话首读：启动序列+全局铁律）
├── SOUL.md             ← AI 协作人格（搭档风格/禁区/协作模式/冲突处理）
├── USER.md             ← 用户画像速览（权威入口）
├── MEMORY.md           ← 长期记忆（动态+程序性，带★强度/衰减/毕业）
│
├── 00-专注区/          ← 【新增】当前在做什么（时间维度）；序号 00 排在最前的 00 组，先于 01-05 内容层
│   ├── _本周.md         ← 本周工作台：口述→任务→进展→产出
│   ├── MEMORY_LOG.md    ← 记忆系统日志（AI 这周了解了你什么）
│   └── _归档/           ← 历史周文件
│
├── 00-天一生水/         ← 保留：库自身的系统档案（基本法/架构设计/工具标准/评估/vault-log/09关于我）
├── 01-实事求是/         ← 保留：内容归宿（原文层）
├── 02-解放思想/         ← 保留：框架层
├── 03-知行合一/         ← 保留：产出层
├── 04-作品出口/         ← 保留：成品层
├── 05-收件箱/           ← 保留：输入缓冲
│
└── 每个文件夹一个 `_agent.md`   ← 区域规则 > 全局规则，就近可查
```

## 四、分工逻辑（避免 SSOT 冲突）

| 位置 | 职责 | 访问频率 |
|---|---|---|
| 根目录四件 + AGENTS.md | 你 + AI + 当前的「身份与协作」，每次开机必读 | 高频、浅 |
| 00-专注区/ | 当前在做什么（时间/状态维度），与六层内容维度正交不打架 | 高频、浅 |
| 00-天一生水/ | 库自身的系统档案（基本法/架构/评估/日志），按需查阅 | 低频、深 |
| 各文件夹 _agent.md | 该模块的就近规则，区域规则 > 全局规则 | 查该模块时读 |

**SSOT 约定**：`USER.md` 是画像权威速览，`00-天一生水/09关于我/` 是详细档案（USER.md 用指针引用）；现有 `AI-开机必读.md` 降级为指针或并入 `AGENTS.md`，避免「身份写在多处」腐烂打架。

## 六、核心约束（最高优先级，不可违反）

1. **用户当前明确意图 > 历史规则文本**：旧铁律该让路，但须同步修订基本法，消除自相矛盾。
2. **可见性/就近性是第一功能**：身份、当前任务、规则必须零成本可见、就近可得；形态本身就是功能，不为分类纯粹牺牲它。
3. **六层内容结构保留**：01-05 内容层一个文件不动，重构只发生在入口层（根目录 + 专注区 + 各 _agent.md）。
4. **SSOT**：每个信息一个权威位置，其余是指针。
5. **入口文件厂商中立**：主入口用 AGENTS.md，不绑定单一模型/工具。
6. **结构改动必带验证**：改前看清自动化依赖，改后用冷启动测试 + 体检 + git diff 证明没搞坏。
7. **区分设计理念与实战验证**：memory 是零实战模板，先试点跑一周再推广。

## 七、验收标准（不靠主观，靠可执行检验）

| 验收项 | 怎么证明 |
|---|---|
| 冷启动有效 | 新会话 AI 只看根目录，能答出「用户是谁、当前在做什么、某模块规则是什么」 |
| 存储层无损 | 迁移前后 `git diff` 显示 01-05 内容层零改动 |
| 结构健康 | 体检断链率 0%、无新增孤儿/重复 |
| 规则就近可查 | 每个目标文件夹存在 `_agent.md`，且与全局规则不矛盾 |
| 记忆机制上线 | MEMORY.md 存在带「强度/证据/衰减」的条目，新会话能读到 |
| 改动可追溯 | `git log` + vault-log 证明改动只落在入口层 |
