# 二、可沉淀的经验（做对了什么）

1. **忠实转录、按图编号顺序**：全部图片按文件名 01、02… 顺序逐张读取，标题、正文、列表、表格原文保留，不做概括改写。
2. **纯文字、不插图片**：当前用户偏好为纯文字转录，飞书文档不保留图片引用/不插原图（早期 03 曾插图，已纠正）。
3. **结构分层**：h1=截图编号（截图01…），h2=课件内板块（快速认识/互动/案例/敲黑板说重点/灵感闪现等），有序/无序列表与表格按原文转换。
4. **长图裁剪分段读取**：高度 >4000px 的长图先用脚本按 3800px 分段（输出 sjXX_partN.png），逐段 Read 后再按顺序拼接，避免长图 OCR 漏读或截断（07 的 7 张长图裁成 30 段全部读全）。
5. **界面截图括注法**：软件/网页界面截图不逐字转录 UI 文字，用一句话括注（界面：核心信息），保证信息密度。
6. **写入链路稳定**：`docs +script init-draft` → 写 XML → `docs +script parse`（结构校验 passed）→ `docs +create --doc-format xml --parent-token`（直接挂到父节点）→ `wiki +node-list` 确认挂载 → `docs +fetch` 抽查回读。
7. **代理坑**：所有 lark-cli 命令前必须 unset/unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY，否则连接被拒。

# 三、识别/执行中的不足（待改进）

1. **拆分粒度不统一**：05 只拆 2 篇（单篇 2.7 万字），06 拆 9 篇，03 拆 7 篇——应统一按"课程叙事阶段"拆 3-6 篇。
2. **子文档命名不统一**：03 无编号、06 带 .md、05 无截图范围标注——统一为「0N 主题（截图a-b）」。
3. **历史文档与偏好冲突**：03 早期文档仍保留图片引用与"来源：xx.png"标注，可按需清理或保留（不影响后续）。
4. **06 以 file 类型存在**：无法用 docs +fetch 回读校验正文，后续统一用 docx 类型创建（docs +create），保证可回读、可校验、可编辑。
5. **转录忠实度口径未定**：OCR 偶有断行/错字，需固定规则——正文忠实原文（含口语化表达），仅对明显 OCR 噪声（乱码、断句）做修正并括注，不擅自改写内容。
6. **长图分段依赖临时脚本**：分段脚本与中间产物放在 /tmp，会被系统清理，需重新生成——SOP 中应把分段步骤写成可复用脚本。
7. **缺少文件夹预检**：开始转录前应先检查文件夹内全部图片的格式（png/jpg/webp）、尺寸、命名顺序，以及是否混入非截图文件。
8. **未固化为一键流程**：目前每次任务需人工读图+写 XML+建文档；下一步应固化为 Skill（如 course-images-to-feishu），用户给文件夹路径即自动触发全流程。

## 第 4 步 · 拆分决策

- 按课程叙事阶段拆 3-6 篇：开篇/框架/个人篇/组织篇/总结 等；每篇一个独立 XML 草稿。

- 用 wiki +node-create 在知识库建「0X 课程名-截图笔记」父节点（--obj-type docx），拿到 node_token。
