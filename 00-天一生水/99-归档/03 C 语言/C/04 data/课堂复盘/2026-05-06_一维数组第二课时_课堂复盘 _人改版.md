# 一维数组第二课时课堂复盘：最值查找、顺序查找与折半查找

> 来源：AI 生成（基于 XX课逐字稿 + 人工标注） 状态：已人工修改确认 版本：2026-01-XX

## 1. 折半查找段：学生为什么犹豫？

### 现象

学生在折半查找开始处明显慢下来，尤其是从「left、right、mid」进入「根据大小改 left/right」这一段。

### 原因

主要不是举例不够，而是**概念前置压缩得太快**。

前面顺序查找的逻辑是：

> 一个一个看，找到就停，找不到就结束。

学生容易跟。

但折半查找突然变成：

> 先确定区间 → 算中间 → 比较中间值 → 扔掉一半 → 改边界 → 重复。

这里对学生来说多了两个新东西：

1. 查找对象不是单个元素，而是一个「区间」
2. 每次比较不是为了判断这个位置是不是答案，而是为了决定下一轮去哪一半

学生犹豫的点大概率在第二个：他们还没完全理解「为什么 x > a[mid] 就一定去右边」，就已经进入 `left = mid + 1` 了。

### 下次可以试的一个具体调整

在写代码前，先只做一张表，不写程序：

| 轮次 | left | right | mid | a[mid] | x 和 a[mid] 比 | 下一轮区间 |
|---|---:|---:|---:|---:|---|---|
| 第 1 轮 |  |  |  |  |  |  |
| 第 2 轮 |  |  |  |  |  |  |
| 第 3 轮 |  |  |  |  |  |  |

先让学生口头回答：

> 这一轮扔掉哪一边？为什么？

等他们能说出「因为数组有序，所以左边都更小 / 右边都更大」，再进入代码。

## 2. 最大值最小值后补「次大次小」：为什么反应下降？

### 现象

最大值、最小值学生还能跟；一补到「次大次小」，反应立刻下降。

### 原因

问题出在**变量数量和判断分支同时增加**，跳跃太大。

最大值只有一个核心变量：

```c
max
```

判断也只有一个：

```c
if (a[i] > max)
```

但次大值至少要同时处理：

```c
max
second
```

而且学生要理解两种情况：

1. 当前数比最大值还大：原来的 `max` 要退到 `second`
2. 当前数不如 `max`，但比 `second` 大：只更新 `second`

这已经不是「照着最大值改一改」，而是多了一个**位置让位关系**。

如果直接从最大值跳到次大值，学生容易只记代码，不懂为什么 `max` 要先让给 `second`。

### 下次可以试的一个具体调整

不要直接讲「次大次小」。先加一个中间台阶：

> 先找最大值和最大值的位置。

建议顺序改成：

1. 只找最大值
2. 找最大值 + 最大值下标
3. 把最大值排除，再找剩下里面的最大值
4. 最后再讲一次遍历同时维护 `max` 和 `second`

这样学生先理解「次大 = 排除最大后的最大」，再接受优化版代码。

## 3. 语速偏快：是全局问题还是特定段落更明显？

### 现象

语速偏快不是平均分布的全局问题，而是**在规则密集段落更明显**。

尤其明显的段落是：

1. 最值扩展到位置交换、次大次小附近
2. 折半查找 `left/right/mid` 参数定义
3. 折半查找区间调整规则
4. 失败案例里 `left > right` 的退出判断

### 原因

这些地方不是单纯「讲得快」，而是信息密度高：一个句子里同时塞了变量名、条件、更新语句、算法意义。

比如折半查找这段，学生要同时听懂：

- `left` 是左边界
- `right` 是右边界
- `mid` 怎么算
- `mid` 对应的是数组下标
- `x` 和 `a[mid]` 比较
- 大了改 `left`
- 小了改 `right`
- `left > right` 才失败

这对中职学生来说，一口气太满。

### 下次可以试的一个具体调整

遇到这种规则密集段落，固定加一个「停顿句」：

> 先别记代码，我们只记一句话：每一轮只做一件事——扔掉不可能的一半。

然后再继续讲 `left/right` 怎么改。

## 总判断

这节课的问题不是内容选错了，而是**算法梯度有几处压得太紧**。

最需要调整的不是多讲理论，而是把几个跳点拆开：

- 最大值 → 最大值位置 → 排除最大再找最大 → 次大
- 顺序查找 → 有序数组 → 区间查找 → 折半查找代码
- 讲规则前先让学生口头判断「扔哪边、为什么」

下次最值得试的一个动作是：

> 每进入一个新算法，不先写代码，先用表格走 2 轮，让学生只回答「当前区间是什么，下一轮去哪边」。
