## 复盘：裁剪反复返工的根因与解决方案

**背景**：08-10 批处理中裁图返工 8 次（08-05 返工 4 次、10-06 返工 3 次），用户要求分析原因。

### 根因（按重要性排序）

**1. 工作顺序做反了（最根本）**
这项工作的主体是**正文逐字转录**（决定文档能不能读），裁图只是辅助。
但实际投入是「裁图+ 验证图片」≈ 70% 工具调用，正文被压缩。
结果：文档主体没做扎实，图片却反复返工。

**2. 把自动密度扫描的输出当成了可靠边界**
行密度扫描只能找「有颜色的行区间」，它**无法区分**：
- 图与正文之间的渐变/淡色底纹边界（08-04/08-05 元素周期表有淡色底纹）
- 图内部的白色空隙会把一张图切成多个 run（10-06 三行作品图被切成3段 → 每行都切一半）
- 正文密集区的密度与图接近（08-06 直接裁到正文区）

**3. 凭"上一张图的下边界"推算下一张图起点**（08-08 只裁到一角，纯属猜测）

**4. 架构错误：素材放/tmp**
把源图复制到 `/tmp/srcB/`，系统清理后全部丢失，只能重新复制。

### 解决方案（已在实践中验证有效）

**核心方法：带 y 刻度的整段预览图**
生成整段预览、左侧按 200px 画红色刻度并标注绝对 y 坐标，肉眼**一次看清结构，直接读出每张图的准确边界**。

- 脚本已固化：`.workbuddy/tools/preview_with_scale.py`
- 用法：`python preview_with_scale.py <源图> <y0> <y1> <输出名> [缩放]`
- **实测：08剩余 6 张、09/10 剩余 6 张，全部一次裁准，零返工**（对比之前单张返工 3-4 次）

**配套原则**
1. 先读完一节正文并记录每张图的内容与位置，**读完再一次性裁剪**——坐标来自观察不是猜
2. 素材复制到**工作目录**，不依赖 `/tmp`
3. 同一张图在多节重复出现时**共用一个文件**（已发现「Feature周期律表格」在 08/09/10 三节重复）

## 追加：WorkBuddy 反复崩溃的根因（Electron EXC_CRASH）

### 崩溃报告的决定性证据
```
"Electron" 意外退出（macOS 12.7.5，WorkBuddy 5.7.7 Build 122）
Exception:  EXC_CRASH (SIGABRT) / EXC_CORPSE_NOTIFY
Kernel Trace: VM - Fault hit memory shortage← 决定性证据
Time Awake Since Boot: 1600 seconds        ← 长时间连续运行后出现
```

### 根因：整图解码
我反复写了 `Image.open(p).convert('RGB')` —— 这会把**整张超长图一次性解码进内存**。

**实测代价（本课程 10 号截图 1936x22695）**：

| 写法 | 单次内存 |
|---|---|
| ❌ `Image.open(p).convert('RGB')` | **125.7 MB** |
| ❌ 再叠加 `resize(1.4x)` | 再 ×1.96 |
| ✅ `Image.open(p).crop(box)` 后 `load()` | **1.9 MB**（省 66 倍） |

本课程 15 张源图一次性整图解码 = **738 MB**；最大三张：
`10 顶级参谋` 125.7MB / `06 Feature思维1` 84.4MB / `08 实操体系` 81.8MB。
10 节我反复打开十几次 → 累积上 GB → 崩溃。

### 原理
PNG 是无损压缩格式，`Image.open()` 默认**不解码**，
只有对某区域调用 `.load()` / `.convert()` / `.resize()` 时才解码**该区域**。
**先 crop 再 load，就永远不会把整张超长图读进内存。**

### ⚠️ draft() 对 PNG 无效
实测 `im.draft('RGB', (w//2, h//2))` 在本课程 PNG 上**尺寸完全不变**，别指望它降采样。

### 解法：imgsafe.py（已落地）
路径：`.workbuddy/tools/imgsafe.py`，同时并入技能 `scripts/imgsafe.py`

| 函数 | 用途 |
|---|---|
| `warn(src)` | 内存预警，超 80MB 会警告 |
| `safe_crop(src,out,y0,y1)` | 裁一段（核心函数，先crop 再load） |
| `safe_seg(src,dir,step,upscale)` | 切阅读段 |
| `safe_preview(src,y0,y1,out)` | 带 y 刻度预览（兼定位坐标） |
| `cleanup(*patterns)` | 清理临时文件 |

**实测验证**：11 节（7436px）完整切 5 段 + 13 节预览，**峰值内存仅 1.9 MB**，耗时 4.4s。

### 铁律（已写入技能 V3.4最高优先级）
1. 永远不要对整图调用 `.convert()` / `.resize()` / `.thumbnail()`
2. 先 crop → 再 load/convert → 立刻 `close()` + `gc.collect()`
3. `step<=2000`、`upscale<=1.4`

## 追加：崩溃与 Skill 本身的关系 —— **有，而且是主因**

用户追问「和当前 Skill 有关系吗」。查证结果：**关系很大，主因就在 Skill 自带的脚本里**。

### 证据：`crop_embedded_images.py` 第 97-98 行（修复前）
```python
im = Image.open(path).convert("RGB")# ← 整图解码
mask = (255 - np.asarray(im).min(axis=2)) > NONWHITE_DIFF   # ← 再转 numpy，又一份
```
这行**必然整图解码**，且是**双份内存**（PIL 图像 + numpy 数组）。

**实测峰值 252.2 MB/张**（10 号截图）。脚本对每个文件都这么干一遍 → 必然崩溃。

### 已修复主脚本
改造为**分段检测**，峰值与图长无关：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 单张峰值 | **252.2 MB** | **1.9 MB**（降 132 倍） |
| 实现方式 | 整图 `convert` + `np.asarray` | `row_nonwhite()` 分条带（2048px/条）算行占比 → `row_extent()` 按需解码单条求列边界 |
| 内存持有 | H×W 矩阵 | 仅长度 H 的 1 维数组 |

**验证**：10 号截图检测出 10 块，坐标与我手工读出的吻合（9452 / 8088 / 17324）；两张超长图 CLI 端到端峰值 11.1 MB。
（注：`find_blocks` 已兼容 1D/2D 两种输入，旧调用方式不受影响）
