| C6 | 用户说"懂了"不等于真懂了 | 收束时必须收集"实操提升信心判断"（行为验证） | §6 F8 定义 |

| C10 | AI 结尾停在模糊语句，用户不知道等还是回 | 强制要求每轮结尾给明确任务或触发词 | §10 + §12 禁止 14 |

## 三、三层架构说明

### 3.1 为什么不是一个大文档

```text
单一大文档的问题：
  - 改一行话术 → 要改整个文档
  - 不同要素的教学内容挤在一起 → AI 检索困难
  - 无法独立迭代某个要素的教学策略

三层架构的好处：
  - 文档 1（系统提示词）只控行为，不控内容
  - 文档 2（总包）只控通用流程话术
  - 文档 3-7（要素包）只控专项教学弹药
  - 想给"非舒适区"加一个新策略？只改文档 5，不动其他 6 个
```

### 3.2 三层架构的设计步骤

```text
Step 1：先把所有内容写进系统提示词（粗胚）
Step 2：识别"流程通用部分" → 抽到总包 PACK_FLOW
Step 3：识别"要素专项部分" → 抽到 5 个要素包
Step 4：系统提示词只保留"什么时候调哪个包"的调用逻辑
Step 5：在系统提示词 §1 建立别名映射表
```

### 3.3 T Partner 三层架构全景

```text
─────────────── 总控层（文档 1）───────────────
系统提示词 V0.6
  §0  身份 + 成功标准
  §1  数据包别名映射 + 用户语言规则
  §2  主公式 + 十倍速因果
  §3  T/C/P 边界 + 场景边界（2 轮闸门）
  §4  状态机（20+ 布尔槽 + user_state）
  §5  F0→F9 主线
  §6  每个状态的进入/完成/禁止/过渡
  §7  报告准入闸门（8 条件）
  §8-9  报告调用 + 交接条件
  §10  5 种应答模板
  §11-12 14 条风格 + 20 条禁止
  §13  15 条每轮自查
─────────────── 流程支撑层（文档 2）───────────
PACK_FLOW
  §1-15  覆盖 F1-F9 全部通用话术、段位图、评分参考刻度、
         报告模板、练习清单、C 交接话术、状态处理
─────────────── 要素弹药层（文档 3-7）─────────
PACK_LONG / ROUTINE / DISCOMFORT / FEEDBACK / REPETITION
  每个包 13 小节：定位 → 调用时机 → 误解 → 校准 →
  十层解读 → 有无对比 → 策略小抄 → 卡点路由 → 反讲 →
  推进模板 → 收束 → 边界 → 速查
```

## 四、P0 走查 → 顶层设计 → 系统提示词 的完整映射

### 4.1 从 P0 走查到顶层设计的 9 个模块

| 顶层设计模块 | P0 走查来源 |
|---|---|
| 一句话定义 | 从"用户把刻意练习理解成什么"反推准确定义 |
| 核心对话模型 | 从"用户从哪一步开始跑偏"反推流程步骤 |
| 场景×策略路由表 | 从"不同用户卡在不同的要素上"反推分支策略 |
| 硬禁止清单 | 从"AI 在这个环节最容易犯什么错"直接提取 |
| 必须做的事 | 从"用户在这个环节最需要什么"反推 |
| 成功标准 | 从"用户离开时应该知道什么"用行为指标描述 |
| 边界 | 从"用户在什么情况下应该被引导到 C Partner"反推 |
| 知识底座 | 从"AI 需要什么外部知识才能支撑教学"反推数据包 |
| 关键提醒 | 从"真实部署中发现的意外问题"反推设计者须知 |

### 4.2 从顶层设计到系统提示词的模块映射

| 顶层设计模块 | 系统提示词对应小节 |
|---|---|
| 一句话定义 | §0 Runtime Contract |
| 核心对话模型 | §5 Main Flow + §6 State Definitions |
| 场景×策略路由表 | §2 Core Model + §7 Response Contracts |
| 硬禁止清单 | §12 Hard Prohibitions |
| 必须做的事 | §6 State Definitions（各状态的完成条件） |
| 成功标准 | §0 Runtime Contract（六句话） |
| 边界 | §3 Boundaries + §9 C Handoff Conditions |
| 知识底座 | §1 Knowledge Packs |
| 关键提醒 | 散见于 §4/§6/§13 的约束性注释 |

## 五、构建过程中的关键决策点

| 决策点 | 选项 A | 选项 B | T Partner 选择 | 原因 |
|---|---|---|---|---|
| 评分方式 | 一个总分 | 笃定分 + 实操分拆开 | 拆开 | 用户"知道重要但做不到"和"不相信重要"是两种完全不同的卡点 |
| 流程控制 | 自然语言判断 | 布尔槽状态机 | 布尔槽 | 防止 AI 凭感觉判定"聊得差不多了" |
| 长期追求 | 和四个训练要素一起竞争"最卡的 1-2 个" | 单独先看 | 单独先看 | 长期追求是地基，地基不稳后面要素没有讨论意义 |
| 数据包结构 | 一个大包 | 总包 + 5 个要素包 | 总包 + 5 个要素包 | 解耦通用流程和专项内容 |
| 事件深入深度 | 不限 | 硬闸门 | 最多 2 轮 | 防止 T 滑成 C |

## 六、作为构建案例样本的使用方式

**Partner 搭建教练在以下时机引用本样本**：

| 时机 | 引用方式 |
|---|---|
| Phase 1 P0 走查 | "就像刻意练习 T Partner 的 P0 走查发现：用户说'不会做'时，可能卡在 6 种不同层面。你这个案例暴露了什么不同性质的卡点？" |
| Phase 2 顶层设计 | "刻意练习 T Partner 的顶层设计有 9 个模块，但每个模块的内容都来自 P0 走查的具体发现。我们来看看你的 P0 走查能对应到哪几个模块。" |
| Phase 3 系统提示词 | "刻意练习 T Partner 复用了标准 13 模块模板。我们现在把你这几个模块的内容填入同样的骨架。" |
| Phase 4 数据包 | "刻意练习 T Partner 有 6 个数据包，是因为它的领域知识（五要素教学）足够复杂。你的 Partner 需要几个数据包？是按题型拆，还是按知识模块拆？" |
| 用户想跳步时 | "刻意练习 T Partner 在部署后发现了很多 P0 走查时没暴露的问题——比如 AI 会把'专属双分'这种内部词说给用户听。如果当初跳过了 P0，这些问题会在真实对话里翻车。" |

## 七、样本边界说明

1. **本样本是参考模板，不是唯一正确路径。** 不同领域的 Partner 可能需要不同数量的数据包、不同的状态机复杂度、不同的评分体系。
2. **本样本的"2 个 P0 案例"是 T Partner 的起点。** C 语言 Teaching Partner 用了 10 个案例才收敛——案例数量取决于领域复杂度。
3. **三层架构适用于"教学型"Partner。** 如果搭建的是执行型（P）或咨询型（C）Partner，架构可能需要调整。
4. **本样本不包含 T Partner 的 7 个完整文档。** 如果需要查看具体文档内容（如系统提示词 V0.6 全文、某个要素包的完整内容），需单独上传。
