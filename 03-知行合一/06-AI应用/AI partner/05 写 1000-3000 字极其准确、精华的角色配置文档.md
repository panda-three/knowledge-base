# "说到天上去，最后就是写 1000-3000 字极其准确、精华的角色配置文档，分配到 5-7 个文档里"

## 一、先破除一个误解

很多人听到这句话，第一反应是："哦，就是写一段很长的提示词嘛。"

不是。

| 误解 | 真相 |
|---|---|
| 写一段长提示词，把要求全塞进去 | 写一套**角色配置文档**，它不是"指令"，而是"运行协议" |
| 1000-3000 字是总量 | 1000-3000 字是**角色配置文档**的精炼程度，但整个系统由 5-7 个文档组成，总字数远超这个数 |
| 重点是"写" | 重点是"极其准确"——每一个字都在约束行为，没有废话 |

打个比方：

```text
普通提示词 = 给演员一张台词纸："你演一个老师，对学生要耐心"
角色配置文档 = 给演员一套完整的导演脚本：
              第几幕进场、什么时候改语气、什么条件下切换状态、
              什么信号出现时必须收、什么情况下绝对不能做某件事
```

**极其准确的 1000-3000 字，不是字数目标，是精炼程度的结果。**

## 二、案例：刻意练习 T Partner 的完整文档结构

这是我正在运行的完整配置。**正好 7 个文档。**

```
文档 1：系统提示词 V0.6（角色配置文档本体）
├─ 0. Runtime Contract        ← 身份、任务、成功标准
├─ 1. Knowledge Packs          ← 数据包别名索引
├─ 2. Core Model              ← 主公式 + 十倍速因果
├─ 3. Boundaries               ← T/C/P 边界 + 场景边界
├─ 4. Dialogue State Machine   ← 内部状态变量
├─ 5. Main Flow               ← F0 → F1 → ... → F9 → C_HANDOFF
├─ 6. State Definitions        ← 每个状态的进入条件、完成条件、必须调用的包、禁止行为
├─ 7. Report Entry Conditions  ← 报告准入闸门
├─ 8. Report Calling Rules     ← 报告标题和结构规则
├─ 9. C Handoff Conditions     ← 什么时候引导转 C Partner
├─ 10. Response Contracts      ← 10 种对话场景的应答模板
├─ 11. Style Rules             ← 14 条风格约束
├─ 12. Hard Prohibitions       ← 20 条绝对禁止
└─ 13. Operating Summary       ← 15 条每轮自查清单

文档 2：PACK_FLOW（总包·流程与教学支撑包）
├─ F1-F9 每个环节的厚话术
├─ 宽场景关键词表
├─ 段位图 L1-L6
├─ 评分参考刻度
├─ 报告模板
└─ C Partner 交接话术

文档 3：PACK_LONG（要素包·长期追求）
文档 4：PACK_ROUTINE（要素包·固定套路）
文档 5：PACK_DISCOMFORT（要素包·非舒适区）
文档 6：PACK_FEEDBACK（要素包·及时反馈）
文档 7：PACK_REPETITION（要素包·大量重复）

每个要素包包含：
├─ 十层解读素材
├─ 常见误解识别
├─ 有无对比
├─ 策略小抄厚解释
├─ 反讲话术库
└─ 收束追问模板
```

这 7 个文档的关系是：

```text
文档 1（系统提示词）= 总指挥
  它不负责"讲什么"，只负责"什么时候讲、怎么推进、什么不能做"

文档 2-7（数据包）= 弹药库
  文档 2 负责通用流程的"讲什么"
  文档 3-7 分别负责五个要素的"讲什么"
```

## 三、什么叫"极其准确"——拿系统提示词的一个切片看

不要用形容词。我直接给你看一段配置，然后解释它为什么"准确"。

### 切片：状态机的 F2 定义

```yaml
F2 宽场景唤醒：
  目标：
    1. 用一篮子常见关键词建立讨论语境
    2. 让用户看到刻意练习覆盖生活、工作、AI、高阶业务等很多场景
    3. 防止用户被"过去练成的能力"卡住
    4. 防止对话锁死在单一案例

  必须调用：
    1. PACK_FLOW 第 3 节「F2 宽场景唤醒」
    2. 优先使用 PACK_FLOW 第 3.2 节「宽场景开篇带动法」

  必须遵守：
    1. 不要求用户立刻选一个技能做方案
    2. 不问"你过去有没有一个已经练出来的能力"
    3. 用户只说出 2-3 个有连接感的场景时，视为 F2 已完成，
       不得继续追问这些场景的具体经历、目标、卡点或最近案例

  F2 → F3 过渡规则：
    4. 如果用户只选择了几个场景，下一轮必须先简短接住，
       并说明后面会用它们做例子
    5. 然后自然转入 F3 的轻量理解暖身
    6. 推荐话术：[具体话术]
    7. 不要说"避免滑进细节""防止 C 化""这里只是锚点"
       等暴露流程控制意图的话
```

### 为什么这叫"极其准确"

每一行都在**消除模糊地带**。对比一下：

| 普通写法 | 极其准确的写法 |
|---|---|
| "先问用户几个场景" | "用户只说出 2-3 个有连接感的场景时，视为 F2 已完成，不得继续追问具体经历" |
| "不要深入细节" | "不要说'避免滑进细节''防止 C 化''这里只是锚点'等暴露流程控制意图的话" |
| "自然地过渡到下一个环节" | 给定了推荐话术的原文，同时明确了禁止使用的表达 |
| "根据情况判断" | 用 yaml 定义了 `completed_evidence` 的布尔槽，不达标不能推进 |

**"极其准确"不意味着写得像法律条文，而是意味着：执行者（AI）拿到这份文档后，几乎不会出现"我该不该追问""现在能不能推进""这句话能不能说"的犹豫。**

## 四、什么叫"精华"——每句话都在消除一个具体的失败模式

继续切片，看系统提示词里的第 12 节"Hard Prohibitions"。它不是泛泛的"要有礼貌""要认真"，而是针对**这个 Partner 在过去真实对话中翻过的车**逐条封堵。

```text
禁止：
1. 把"过去练成的能力"作为正式入口
   → 因为一聊这个，对话就会滑向 C 型方案咨询

2. 一上来让用户填满五个要素十个分数
   → 因为 T 的目标不是测评，是教学

3. 以纯陈述句或模糊指令结束回复，让用户不知道下一步该说什么
   → 因为用户会停在"等 AI 继续输出"还是"我该说点什么"的中间态

4. 对延伸性问题不解释用意，导致用户不知道为什么要回答
   → 因为用户会觉得"这是在审讯我吗"
```

每一条背后都有一个真实的翻车案例。**"精华"的意思不是"写得漂亮"，而是"每句话都在防止一次已知的失败"。**

## 五、为什么必须"分配到 5-7 个文档"

### 5.1 如果只放在一个文档里

| 问题 | 后果 |
|---|---|
| 上下文窗口被撑爆 | 前面塞得越多，后面 AI 就越容易遗忘早期指令 |
| 角色配置和教学内容混在一起 | AI 分不清"这是让我做的"还是"这是让我教的" |
| 无法独立迭代 | 改一个要素的案例，就要重新部署整个系统 |
| 无法复用 | 同一套运行协议配不同的数据包，应该能生出不同的 Partner |

### 5.2 7 个文档的分层逻辑

```text
第 1 层：文档 1（系统提示词）
  角色：总控
  特点：最短、最精、最稳定。不改它。

第 2 层：文档 2（PACK_FLOW 总包）
  角色：通用流程的弹药库
  特点：F1-F9 的所有话术都在这。改教学节奏改它。

第 3 层：文档 3-7（五个要素包）
  角色：每个要素的专项弹药库
  特点：互相独立。改"非舒适区"的反讲话术，不影响"固定套路"的十层解读。
```

这种分层的工程价值是：

```text
想调整 F2 的开场话术 → 只改 PACK_FLOW
想补充非舒适区的新策略 → 只改 PACK_DISCOMFORT
想把 T Partner 的"运行协议"复用到另一个教学场景 → 系统提示词整体迁移，只换数据包
```

**分配到 5-7 个文档，不是分拆字数，而是建立模块化的工程结构。**

## 六、一个真实交互，看文档是怎么运行的

假设用户说了一句：

> "我最卡的是没人给我反馈。领导很忙，平时反馈很少。"

### 系统提示词在做什么

```text
1. 识别：用户暴露了"及时反馈"卡点
2. 路由：active_training_element = 及时反馈
3. 状态推进：F5 → F6
4. 调用规则：必须调用 PACK_FEEDBACK（文档 6）
5. 禁止行为检查：不把反馈讲成评价人、不替用户搭完整反馈系统
6. 退出条件：has_training_element_scores + has_score_explanation 都为 true 才能推进
```

### PACK_FEEDBACK（文档 6）在做什么

```text
1. 识别误解：用户可能把"反馈"等同于"领导评价"
2. 调取纠偏话术：
   "反馈不是别人评价你，而是帮你找到 GAP——
    真实套路是什么，你现在差在哪里，下一次该怎么调。"
3. 调取有无对比：
   "没有专家确实会难很多，但不等于完全没有反馈。
    你可以用版本对比看 GAP，用事实数据看 GAP，
    用同伴互评补视角，用最佳实践池子制造标杆差距。"
4. 调取策略小抄：版本对比、事实反馈、主动索取、最佳实践池子
5. 推进追问：
   "你现在最现实的入口是哪一个？
    先做版本对比，还是先建最佳实践池子，还是下次主动问专家一个更具体的问题？"
```

### 两者的配合

```text
系统提示词（文档 1）= 知道"现在该进 F7，讲及时反馈，不能讲成评价"
PACK_FEEDBACK（文档 6）= 知道"及时反馈怎么讲、误解怎么破、策略有哪些"

系统提示词没有厚教学内容，它不用知道富兰克林怎么写文章；
PACK_FEEDBACK 不知道流程状态，它不用关心 F7 之后是 F8。

两者解耦，各自迭代，互不污染。
```

## 七、一段话收束

这句话的真正含义是：

```text
不要被"AI 智能体""多 Agent 协作""ReACT 框架"这些词吓住。

翻到最底层，你交付的就是几个纯文本文档。
一个文档管"怎么跑"（系统提示词），几个文档管"弹药在哪"（数据包）。

但"极其准确"这四个字才是护城河——
每一行都在消除模糊地带，
每一句话都在封堵一个已知的失败模式，
每一个"禁止"背后都有一个真实的翻车案例。

1000-3000 字不是字数目标，而是你把所有这些想清楚之后，
自然收敛成的那个精炼程度。
```
