## 及时反馈 · Vibe Coding 场景版

---

### 一、核心定义

> **及时反馈不是别人评价你，而是让自己尽快看见差距（GAP）——真实高水平的样子是什么，你现在差在哪里，下一次具体改哪一步。**

- 不是「好不好」（那是评价）
- 不是「能跑就行」（那是结果确认）
- 是「哪一步好、哪一步差、和最佳水平差在哪、下一次怎么改」

---

### 二、Vibe Coding 场景的特殊性

| 传统场景                    | Vibe Coding             |
| ----------------------- | ----------------------- |
| 代码是人写的，可以对比高手代码         | 代码是 AI 写的，比语法风格意义不大     |
| 反馈主要来自 Code Review、测试结果 | 反馈需要你**主动设计来源**，不能等别人给  |
| 最佳实践 = 开源项目、行业标准        | 最佳实践 = 别人做项目的方法论，不是代码本身 |
|                         |                         |
|                         |                         |

**核心洞察**：在 Vibe Coding 里，及时反馈不能等、不能只靠「能不能跑」来判断，要靠你主动索取和主动研究。

---

### 三、两大反馈来源

#### 来源一：主动索取（让 AI 直接告诉你 GAP）

这是最轻、最快、每次都能用的反馈方式。

| 时机 | 问 AI | 这什么问题 |
|---|---|---|
| 做完一个功能，刚跑通 | 「这版代码和上一版比，哪里变好了？哪里引入了新问题？如果只改一处，你最建议改哪里？」 | 版本对比 + 差距定位 |
| 改完一个 Bug，刚修好 | 「这个 Bug 的根因是什么？是我需求没说清、代码逻辑有缺陷、还是边界没覆盖？下次我怎么一句话预防它？」 | 根因分析 + 规则提炼 |
| 项目做完，收尾时 | 「回顾整个项目，我提需求的方式哪里让你理解准确、哪里让你跑偏了？你是不是有些时候其实不确定我的意图但硬做了？」 | 反向追问自己的盲区 |

**关键**：这三个问题逼着反馈从「好不好」下沉到「哪一步好、哪一步差、下一次怎么改」。

---

#### 来源二：最佳实践池子（研究别人方法论，反向照自己）

在 Vibe Coding 里，最佳实践不是找代码对比，而是：

> **研究别人好的项目的方法论，反过头来作用于自己的项目。**

| 做什么 | 具体操作 |
|---|---|
| 找 3-5 个高质量 vibe coding 项目 | 不是找代码，是找把项目做出来的人分享的方法论文章、视频、推文 |
| 研究他们怎么做 | 怎么开局？怎么拆需求？怎么给 AI 反馈？遇到坑怎么绕？ |
| 和自己对比 | 我的固定套路里，哪一步和他类似但可以更好？哪一步他做了我完全没做？ |
| 反向作用 | 挑 1-2 个可以立刻嵌进自己套路的方法，下一次项目就试 |

---

### 四、如何嵌进你的固定套路

在「知识沉淀」那一步之前，塞进这两件事：

```
项目做完 →
  1. 主动索取：问 AI 那三个问题，拿到过程差距
  2. 最佳实践池子：研究别人方法论，反向照出自己的 GAP
  3. 沉淀进 Context / 陷阱 / ADR
```

每次不用都走两个，看任务大小：

| 任务类型 | 走哪条 |
|---|---|
| 微任务 | 只做主动索取（问 AI 一个最贴切的问题） |
| 普通任务 | 主动索取 + 有触动了研究一次别人方法论 |
| 复杂项目 | 两条都走，做完后花 20 分钟集中对照 |

### 五、收束评分

| 维度 | 分数 | 说明 |
|---|---|---|
| 笃定 | 9 分 | 你天生相信「没有反馈就没有成长」，校准后更清楚——反馈不是结果好坏，而是过程差距 |
| 现实实操 | 5 分 | 过去只有一个反馈来源：结果能不能跑 |
| 实操提升信心 | 7 分 | 主动索取三个问题 + 研究别人方法论反向照自己，两条路都通了 |
