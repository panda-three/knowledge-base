# 一封信 Partner 构建过程复盘报告

## 从两个学生案例到可部署系统——一场 24 轮的人机协同构建

---

## 第一部分：项目概览与成果

### 1.1 项目起源

起点不是"我要设计一个 Partner"，而是一个真实场景：学期末，老师想给几个学生写信，但不知道怎么写才能说中要害。两个案例——张瀚铭（向上但被误解）和毛俊杰（下滑但原因不是懒）——被扔进对话窗口，成为整个系统的种子。

### 1.2 项目数据

| 维度 | 数据 |
|---|---|
| 总轮次 | 24 轮（从「帮我设计一封信 Partner」到五个文档全部输出） |
| 构建方式 | 先跑真实案例 → 从对话记录倒推系统 → 部署测试 → 迭代修正 |
| 总产出文档 | 5 个完整文档（系统提示词 + 总包 + 3 个能力包） |
| 文档总字数 | 约 12,000 字（五个 .md 文件合计） |
| 验证案例数 | 2 个（张瀚铭、毛俊杰），已跑通全流程 |
| 迭代轮次 | 2 次（V1.0 → V1.1 修正 3 个问题；V1.1 暴露 2 个新问题待修） |
| 部署平台 | 扣子（Coze 国内版） |
| 关键方法论发现 | 4 条可迁移规律 |

### 1.3 最终成果

**一封信 Partner**，一个帮助老师为不同学生状态生成个性化期末信的 AI 系统。

```text
一封信 Partner
│
├── 文档 1：系统提示词 V1.1（部署版）
│   核心：看见 × 命名 × 锚定 × 展开
│   流程：F1 建立画像 → F2 提取事件 → F3 初轮洞察 → F4 老师校准（闸门）
│         → F5 确定锚点 → F6 生成信件 → F7 老师微调
│   约束：17 条绝对禁止 + 五段信件结构 + 零"你应该"扫描
│
├── 文档 2：PACK_FLOW（总包·流程支撑包）
│   追问话术库（5 种场景）+ 校准提问模板（3 种场景）+ 占位符规则
│
├── 文档 3：PACK_INSIGHT（能力包·洞察生成）
│   洞察类型库（5 种类型）+ 素材交叉规则 + 质量自查（4 项必查）
│
├── 文档 4：PACK_ANCHOR（能力包·锚点与结构）
│   锚点生成四步规则 + 四维自查 + 信件五段结构模板
│
└── 文档 5：PACK_TONE（能力包·语气与措辞）
    语气类型库（4 种）+ "你应该"→"我注意到"转换 + 回应外部质疑规则
```

## 第二部分：构建全过程还原

### 阶段 0：背景——从 T Partner 到一封信 Partner

在构建一封信 Partner 之前，已经完成 T Partner（刻意练习五要素理解与笃定度教练）的完整设计——7 个文档、半严格状态机、5 个要素专项教学包。但 T Partner 从未部署测试。

一封信 Partner 的构建，本质上是一次**方法论验证**：能不能用更小的系统、更少的案例、更短的周期，把一个 Partner 从零建到可部署？

### 阶段 1：P0 走查——两个案例跑通全流程（对话轮次 1-12）

#### 案例 1：张瀚铭——向上但被误解

**老师原文**：
> 有个张瀚铭这个学生，这学期他有一个变化是开始积极主动学习了，"他上学期几乎不学习，这学期竟然主动问我问题"！别人可能觉得他可能是暂时装的，过一阵子就显出原型，但我看到的是他对升学的渴望，想要上一个公办大专的渴望，我其实最想对他说，做自己吧，为了自己的未来拼一把。

**AI 先输出了一封信念（速度优先），然后立即逆转方向——从"先给结论"切换为"先诊断问题"。**

在未使用任何系统提示词、数据包的情况下，AI 基于对老师素材的分析，识别出信的三个核心问题：

| 问题 | 诊断 |
|---|---|
| 信的脊柱不清晰 | 写了四个方向（对比、渴望、挑战、自由），但用户最想说的是"做自己"——信没有锚定一个点 |
| 宏观框架偏了 | 把"做自己"抬高到存在主义（"你首先是你自己，然后才是那个努力的张瀚铭"），这不是老师要的——他要的是"你不是别人说的那样" |
| 老师最想说的话被稀释了 | "为了自己的未来拼一把"——这句最核心的话被放在最后，作为可选收尾 |

这三条诊断不是泛泛的评价，而是追溯到信中的具体语句。这就是后来 F2「提取可追溯事件」和 F3「初轮洞察」的雏形。

**其次，AI 给出了信的修正锚点**：

```text
你不需要向任何人证明。
```

并围绕这个锚点重新生成了修正版信，核心变化：

| 原版问题 | 修正版处理 |
|---|---|
| 脊柱不清晰 | 锚点「不需要证明」贯穿全信 |
| "做自己"被抬高到存在主义 | 落到证据层：别人说装的，老师看到的是渴望 |
| "拼一把"被放末尾 | 去掉命令感，变成对已有力量的确认 |
| 缺少可追溯事件 | 明确引用"上学期不开口 vs 这学期主动问" |

这个锚点后来成为一封信 Partner 核心模型「看见 × 命名 × 锚定 × 展开」里最关键的一个环节。

**信后诊断结束后，AI 给出了这封具体信之外的方法论——三条决策原则：**

| 原则 | 内容 | 为什么重要 |
|---|---|---|
| 当老师说「做自己」 | 立刻问：做自己 vs 不做自己之间的差别是什么？这个差别具体表现为哪个行为？ | 「做自己」是标语。标语的问题是听起来都对，但没法落笔。你不追问，信就只能说「做自己吧，加油！」——这是贺卡，不是信。 |
| 当老师说「我看到的是……别人觉得……」 | 立刻问：你看到的和他自己认为的，是一回事吗？ | 信的真正力量在这里。老师说「我看到的是渴望」，学生可能只知道自己想上大专。这两者之间有一条沟——信的任务是帮他看清自己没说清的东西。 |
| 当老师说「拼一把」 | 立刻问：拼一把的前提是什么？ | 学生如果已经在拼，你再说「拼一把」，他听到的是「你还不够」。正确方向是告诉他：你已经在拼了，这种力量不是别人说的装的，是你自己的。 |

这三条原则后来被转化为系统提示词里 F3 洞察生成的调用规则和 PACK_INSIGHT 的素材交叉规则。

**最后，AI 把整个诊断过程结构化为一套可复用的分析框架：**

```text
一封信的四个问题：

□ 脊柱问题：这封信有没有一个核心判断？
  → 张瀚铭：脊柱是「你不需要向任何人证明」。原版写了四个方向，脊柱被稀释。

□ 证据问题：核心判断有没有追溯回老师说的真实事件？
  → 张瀚铭：有——上学期不开口 vs 这学期主动问。但如果老师没说这些具体细节，脊柱就没证据。

□ 语气问题：信的语气是「见证」还是「评判」？
  → 张瀚铭：「你不需要向任何人证明」是见证；「拼一把」「做自己」在不配证据时就是评判。

□ 名字问题：读这封信的人，能不能从第一句就知道这封信是写给我的？
  → 张瀚铭：如果能写进「放学后追到办公室问数学最后一道大题」这种只有他做过的事，名字感就有了。
```

这四问框架后来被完整保留为一封信 Partner 核心模型「看见 × 命名 × 锚定 × 展开」的基础：脊柱问题对应锚定，证据问题对应看见，语气问题对应命名，名字问题对应展开。

#### 案例 2：毛俊杰——下滑但原因不是懒

**老师原文**：
> 毛俊杰，上学期成绩非常好，但是这学期由于谈恋爱，所以导致成绩一落千丈，别人可能觉得他终于不装现出原型了，但是我看到的是，他作为一名单亲家庭背后的情感需求没有人关注，我其实最想跟他说，恋爱只是暂时的，现在你应该好好学习，不要让恋爱影响后面的发展

**补充素材**（母亲谈话记录）：
> 我和他爸爸离婚，其实不是我的错，就是她爸爸可能有一点问题。然后呢就导致现在她跟我，没有她爸爸的关注，所以导致她现在特别的孤独。

AI 按张瀚铭案例总结出的四个问题框架进行诊断。这个案例比张瀚铭复杂——它包含**两条信息源**（老师的印象 + 母亲的谈话记录），而且老师的原始措辞里存在方向性问题（「恋爱只是暂时的，你应该好好学习」）。

AI 提取了四个可追溯事件：

| 事件 | 内容 | 来源 |
|---|---|---|
| A | 上学期成绩非常好 | 老师初始印象 |
| B | 这学期谈恋爱，成绩一落千丈 | 老师初始印象 |
| C | 单亲家庭 | 老师初始印象 |
| D | 母亲说：离婚不是她的错，是父亲那边有问题。孩子跟她，没有父亲的关注，所以现在特别孤独。 | 谈话记录 |

在事件 D 加入后，AI 发现原判断「谈恋爱导致成绩下滑」被颠覆了——真正的原因是孤独。于是重写了三条洞察：

| 洞察 | 核心判断 |
|---|---|
| 第一条 | 成绩下滑不是「谈恋爱」，是「填孤独」——谈恋爱不是原因，是症状。原因在孤独。 |
| 第二条 | 母亲说「不是我的错」——这个家每个人都在自责。母亲在解释，不是投诉。 |
| 第三条 | 信的方向要重定——不是「你该学习」，是「你有人在乎」。 |

在锚点生成前，AI 专门指出了措辞问题——「你应该好好学习」和「恋爱只是暂时的」这两句必须重写，并给出了转换规则：

| 原句 | 问题 | 建议替代 |
|---|---|---|
| 「恋爱只是暂时的」 | 否定他正在投入的关系——他听到的是「你不该被爱」 | 「我不是来让你放弃什么的」 |
| 「你应该好好学习」 | 「你应该」是命令，不是连接 | 「上学期那种力量还在」 |

然后生成锚点：

```text
你只是太累了。
```

并展开解释了为什么这个锚点比「你应该学习」更好：

```text
「你应该学习」把问题定义成「你做错了」→ 他需要改正。
「你只是太累了」把问题重新定义成「你扛太久了」→ 他需要被接住。
```

然后按五段结构生成了完整信件。在输出信之前，AI 做了逐段自检——每一段都追溯回四个事件中的一个或多个，禁止任何编造：

| 段落 | 信息来源 | 是否有编造 |
|---|---|---|
| 开篇（成绩下来了） | 事件 B | 无 |
| 母亲谈话内容 | 事件 D 原文 | 无 |
| 上学期成绩好 + 孤独交叉 | 事件 A + 事件 D | 无 |
| 别人说现原形 | 老师初始印象 | 无 |
| 「你只是太累了」 | 锚点核心句 | 无 |
| 母亲不是抱怨 | 事件 D 语气判断 | 无 |
| 「那种力量还在」 | 事件 A + 老师判断 | 无 |
| 「我不会说你应该学习」 | F4 确认的方向 | 无 |
| 「你母亲也会在」 | 事件 D | 无 |
| 「上学期能那么好不是偶然」 | 事件 A | 无 |

**全信零编造，零「你应该」。**

### 关键转折点：在张瀚铭案例中发现的「先给答案再逆转」模式

回顾整个 P0 走查，最关键的转折发生在张瀚铭案例的开始阶段。AI 没有按照「分析问题→设计方案→输出交付」的线性流程走。它的实际路径是：

```text
速度优先：先输出一封信念（约 400 字）
    ↓
立即逆转：诊断这封信本身的六个问题
    ↓
给出修正：基于诊断重新生成第二封信
    ↓
提炼规则：从诊断中提取三条决策原则和四个通用问题
    ↓
用新规则：把四问框架套到毛俊杰案例进行验证
```

这个「先做→再诊断→再修正→再提炼→再用」的循环，就是后来「先跑案例再建系统」的构建方法论原型。

### 阶段 2：P1 数据包结构设计（对话轮次 13-15）

在案例 2 跑通后，进入正式的系统设计阶段。核心决策：从张瀚铭和毛俊杰两个真实案例的对话记录中，倒推这个 Partner 需要哪些数据包、每个包放什么、包之间怎么调用。

**核心设计决策 1：需要几个包？**

```text
T Partner：1 系统提示词 + 1 总包 + 5 要素包 = 7 文档
一封信 Partner：1 系统提示词 + 1 总包 + 3 能力包 = 5 文档
```

为什么一封信只需要 3 个能力包？因为 P0 走查发现，核心风险点就三个——**洞察不准、锚点不狠、语气不对**。每个配一个专项包。

**核心设计决策 2：三层架构的职责边界**

```text
系统提示词：状态机 + 边界 + 硬禁止 → 控制行为
总包（PACK_FLOW）：流程各环节的通用话术支架 → 支撑交互
能力包（INSIGHT/ANCHOR/TONE）：专项能力的内容与规则 → 保证质量
```

**核心设计决策 3：两个案例的发现如何分配到数据包**

| 案例发现 | 进入哪个包 | 具体内容 |
|---|---|---|
| 张瀚铭：洞察不能只是复述事实 | PACK_INSIGHT | 描述 vs 洞察检查：「成绩好→下滑」是描述，「成绩好和成绩差都在填同一个洞」是洞察 |
| 毛俊杰：谈话记录进入后洞察根基因改变 | PACK_INSIGHT | 素材交叉规则：单源素材不得做「表层 vs 底层洞察」 |
| 张瀚铭：「你不需要向任何人证明」是脊柱 | PACK_ANCHOR | 锚点 = 信的脊柱，每一段回应它 |
| 毛俊杰：「你应该学习」→「你只是太累了」 | PACK_TONE | 「你应该」→「我注意到」转换规则表 |
| 两个案例都有的「别人觉得……」 | PACK_TONE | 回应外部质疑规则：最多 1 段、3 句、不能成为信的主角 |

**全信零编造，零「你应该」。**

### 阶段 4：部署与验收测试（对话轮次 21-22）

#### 部署

选择扣子（Coze 国内版）作为部署平台。五个文档分别处理：
- 系统提示词直接粘贴到 Bot 的系统指令区
- 四个 PACK 文件上传到知识库

#### 第一次验收（V1.0）——暴露 3 个问题

用张瀚铭原始输入测试 V1.0，发现三个问题：

| 问题 | 现象 | 根因 |
|---|---|---|
| F6 感官细节编造 | 信中出现了「耳朵还有点红」「攥着笔的手指捏得很紧」「主动坐在前排听课」——老师从未说过这些细节 | 系统提示词写了「逐段自检信息来源」——这是原则性约束，模型可以跳过 |
| 锚点自查格式不标准 | 用了「专属性」「可落地性」等非标准维度名称，没有按 PACK_ANCHOR 的四维标准（具体性/唯一性/洞察性/语气）逐条输出 | 系统提示词写了「用 PACK_ANCHOR 四维标准」但没有强制输出格式 |
| 语气类型自创 | 用了「共情肯定型」——这个名称不在 PACK_TONE 的四种类型（坚定+温暖/理解+重新定义/看见/接住）里 | 系统提示词写了「匹配语气类型」但没有穷举可选项 |

#### 根因分析——一个重要判断

三个问题的根因不在平台（Coze），不在模型——在提示词。具体地说：**模型对「原则性约束」的遵循程度，远低于对「可执行禁令」的遵循程度。**

```text
原则级（最弱）："逐段自检信息来源" ← 模型可以自检，也可以跳过。模糊。
禁令级（中等）："不得描写任何感官细节" ← 模型知道不能做。
检查动作级（最强）："逐段扫描：有表情吗？有动作吗？有场景吗？有就删除" ← 模型被要求执行一个动作。
```

#### 第一次迭代（V1.0 → V1.1）——修复 3 个问题

在系统提示词中新增了 3 条硬禁止：

| 禁止项 | 内容 |
|---|---|

### 阶段 5：复盘与规律提炼（对话轮次 23-24）

在 V1.0→V1.1 迭代完成后，进行了一次迭代复盘和一次完整对话复盘。从这两次复盘中提炼出四条可迁移规律：

#### 规律 1：从案例倒推系统，不从框架推导系统

```text
不要先设计「这个 Partner 应该有哪些能力包」。
先跑 2-3 个真实案例，记录：
- 什么环节最容易出错
- 什么判断最需要支撑
- 什么输出最容易被模型搞砸
然后从记录里倒推需要哪些包、每个包放什么。
```

#### 规律 2：约束分三级——原则、禁令、检查动作

```text
能写成检查动作的，不写成禁令。
能写成禁令的，不写成原则。
```

#### 规律 3：每个产出型 Partner 都需要定义「写作模式」

```text
默认写作模式：生动、共情、修辞、完整
要求写作模式：克制、追溯、见证、只写素材里有的

两者的冲突不是在某个环节发生的——是在每次输出时都在发生。
所以不是在禁止清单里打补丁，而是在系统提示词开头声明写作模式。
```

#### 规律 4：部署测试不是最后一步，是第二步

```text
传统流程：设计 → 设计更多 → 感觉差不多了 → 部署测试 → 发现问题太多改不完
应该的流程：设计最小可用版本 → 立刻部署测试 → 从测试里拿真实问题 → 驱动下一轮设计
```

#### V1.1 暴露的核心规律：模型善意违规的三种模式

| 模型的"善意" | 它做了什么 | 为什么违规 |
|---|---|---|
| 让信更生动 | V1.0 补了"耳朵红""攥笔""坐前排" | 补感官细节——已堵 |
| 让学生感觉被理解 | V1.1 写了"你可能在想……" | 替学生编内心独白——刚暴露 |
| 让学生感觉被肯定 | V1.1 写了"比浑浑噩噩的同学强" | 替老师评价其他学生——刚暴露 |

**规律：模型不是恶意违规，而是「善意地做多了」。每次修补只堵住某个具体表现，而没有堵住这一类动机。需要从「禁令清单」升级到「分类框架」——明确什么能写（可追溯事件、老师的观察与判断、对学生的命名、老师能给的承诺）、什么不能写（未覆盖的感官细节、任何人的内心独白、对其他人的评价比较）。**

## 第三部分：关键决策与转折点复盘

### 3.1 为什么不是「先设计再验证」

传统的 Partner 构建方式是「假设需求 → 设计系统 → 找案例验证 → 发现不对 → 改系统」。一封信 Partner 的构建完全反过来：先用原始对话把两个案例跑通，再从对话记录里倒推系统需要什么。

**这个顺序差异的后果**：PACK_INSIGHT 的五种洞察类型，全部来自两个案例的实际产出；PACK_ANCHOR 的四维自查，全部来自锚点质量的实际判断；PACK_TONE 的「你应该→我注意到」转换规则，直接来自毛俊杰案例中「恋爱只是暂时的」这个真实翻车点。

**这意味着这套数据包里几乎没有「我猜你会需要」的内容，都是「我见过你确实需要」的内容。**

### 3.2 为什么 F4 被设为闸门

F4（老师校准）被设为整个流程的闸门——has_insight_calibrated 为 false 时，系统不得进入 F5（锚点生成）和 F6（信件生成）。

这个设计不是凭空想象的。它来自两个直接教训：

- 张瀚铭案例：如果跳过校准直接写信，就会编造「放学后追到办公室问数学最后一道大题」这样的细节——因为 AI 不知道哪些细节老师其实没说过
- 毛俊杰案例：如果跳过校准直接写信，就会保留「恋爱只是暂时的，你应该好好学习」这个方向——而不发现真正的锚点是「你只是太累了」

**F4 是整个人机协同机制里，人类判断力最密集、也最不可替代的一个节点。** 这就是为什么校准提问必须是「有没有不太对的」而非「对吗」——前者邀请质疑，后者邀请敷衍。

### 3.3 为什么选择了扣子（Coze）而不是 YAI

用户在对话中表示无法部署到 YAI。选择的替代平台是扣子（Coze 国内版）。

决策逻辑：
- 扣子支持系统提示词直接粘贴到 Bot 系统指令区
- 支持知识库上传 .md 文件
- 国内直接访问，无需特殊网络环境
- 免费额度大方
- 从注册到部署到验收，全流程约 10 分钟可走完

**这个选择的长期影响**：扣子的知识库检索机制与 YAI 可能不同——如果后续发现 Bot 没有按预期调用某个 PACK，可能需要调整系统提示词中知识库的调用方式。

### 3.4 V1.1 修正的三处修改为什么都落在系统提示词

V1.0 的三个问题（感官细节编造、锚点自查格式不标准、语气类型自创）的修正全部落在系统提示词层面。PACK_TONE 只修了一处（类型库加禁止清单）。PACK_INSIGHT、PACK_ANCHOR、PACK_FLOW 完全没动。

**这说明三层架构的职责边界是清晰的**：
- 规则在系统提示词——改了行为
- 内容在能力包——没发现内容错误
- 话术在总包——F1-F7 流程没有结构性问题

## 第四部分：可以复用的方法论

### 4.1 构建方法论：从案例到系统的四步法

```text
Step 1：P0 走查
  跑 2-3 个真实案例，不用任何系统提示词或数据包。
  让 AI 和用户进行「原始对话」，观察：
  - AI 在哪个环节最容易翻车
  - 哪些判断最需要外部支撑
  - 哪些输出最容易被模型的写作习惯搞砸
  从对话记录里提取可追溯事件列表、洞察类型、常见误区。

Step 2：P1 数据包结构设计
  用 P0 走查的发现倒推需要哪些数据包。
  判断标准：核心风险点 = 一个能力包。
  设计三层架构：系统提示词（行为）、总包（交互）、能力包（质量）。
  给每个包定义职责边界——包之间不互相替代。

Step 3：五文档全量输出
  一个一个输出文档。系统提示词优先。
  每个能力包里的内容都追溯到 P0 走查的真实案例。
  不写「我觉得会需要」的内容，只写「我见过确实需要」的内容。

Step 4：部署与迭代
  最小可用版本 → 立刻部署 → 验收测试 → 从真实问题驱动迭代。
  不是「设计完再测」，是「能跑就测，测完再修」。
```

### 4.2 数据包设计准则

| 准则 | 含义 | 一封信 Partner 的体现 |
|---|---|---|
| 从案例倒推 | 不假设需要什么包，从真实对话里找 | PACK_INSIGHT 的五种洞察类型全部来自两个案例的实际产出 |
| 风险驱动 | 核心风险点 = 一个能力包 | 三个风险点 → 三个能力包 |
| 职责隔离 | 包之间不互相替代 | V1.1 三处修正全部在系统提示词，能力包只修了一处 |
| 内容可追溯 | 每条内容都来自真实案例 | PACK_TONE 的转换规则直接来自毛俊杰案例的「恋爱只是暂时的」 |

### 4.3 提示词工程的三级约束模型

这是 V1.0→V1.1 迭代中发现的最核心规律：

```text
Level 1：原则级约束（最弱）
  例："逐段自检信息来源"
  问题：模型可以自检，也可以跳过。模糊。
  只在模型本身已经倾向于做这件事时有效。

Level 2：禁令级约束（中等）
  例："不得描写任何感官细节，包括但不限于：表情、动作、衣着、场景"
  优势：模型明确知道不能做什么。
  局限：只堵住了具体表现，没堵住动机。下次模型可能换一种方式违规。

Level 3：检查动作级约束（最强）
  例："逐段扫描：有表情吗？有动作吗？有场景吗？有就删除"
  优势：模型被要求执行一个具体动作，绕不过去。
  成本：提示词变长。

使用原则：
  能写成检查动作的，不写成禁令。
  能写成禁令的，不写成原则。
  如果某种违规反复出现且变体多 → 考虑升级到分类框架（如"区分四种可写内容"）。
```

### 4.4 「写作模式」声明——每个产出型 Partner 都需要

这是 V1.1 验收后发现的最重要缺失：

```text
模型的默认写作模式 ≠ Partner 要求的写作模式

默认写作模式：生动、共情、修辞、完整、"让读者感觉好"
要求写作模式：克制、追溯、见证、只写素材里有的、"让学生感觉被准确看见"

这两种模式不是在某个环节冲突——是在每次输出时都在冲突。
所以不是在禁止清单里逐条打补丁（禁止表情、禁止动作、禁止内心独白...），
而是在系统提示词开头声明写作模式本身。
```

### 4.5 五段信件结构模板

这来自两个案例的锚点展开验证：

```text
【开篇】一个具体场景
  → 规则：第一句必须让读信的人知道"这封信是写给我的，不是模板"
  → 张瀚铭：「你开始问我问题了」
  → 毛俊杰：「你母亲跟我说了一件事」

【展开】证据 + 洞察
  → 规则：每段展开都有素材支撑，不空洞

【命名】帮他说清他可能说不清的状态
  → 规则：一个词或一句话
  → 张瀚铭：「你找到了自己想去的地方」
  → 毛俊杰：「你不是变差，你只是太累了」

【信念】他值得相信什么——不是"你应该做什么"
  → 规则：不要求学生改变行为，只告诉他一个真相

【收束】一个承诺或一个画面
  → 规则：不喊口号，不给压力
  → 张瀚铭：「下学期你继续问我，我继续答」
  → 毛俊杰：「下次觉得孤独，除了那段关系，还可以来找我」
```

## 第六部分：关键对话片段实录

### 片段 1：速度优先 → 立即逆转（P0 走查 · 张瀚铭案例）

这是整个项目最关键的一个动作。AI 没有按「分析→设计→交付」走，而是「先给答案→诊断这封信的问题→修正→提炼规则」。

这个模式后来成为整个构建方法论的原型：先跑案例，再从案例里倒推系统。

### 片段 2：锚点质量自查的诞生（P0 走查 · 张瀚铭案例）

AI 不是在信写完后泛泛检查，而是给了一个具体的检查维度：
- 这封信有没有一个核心判断？
- 核心判断有没有追溯回老师说的真实事件？
- 信的语气是"见证"还是"评判"？
- 读这封信的人能不能从第一句就知道是写给我的？

这四个问题后来被转化为 PACK_ANCHOR 的四维自查标准（具体性/唯一性/洞察性/语气）。

### 片段 3：V1.0→V1.1 根因判断

验收出问题时，AI 的第一反应是分析根因——不是「扣子的问题」或「模型的问题」，而是「约束的强制等级不够」。这个判断节省了大量无用功。

### 片段 4：模型善意违规的发现（V1.1 验收后复盘）

V1.1 修复了 V1.0 的三个问题，但暴露了两个新问题：「你可能在想……」和「比浑浑噩噩的同学强」。这不是感官细节禁令的漏网之鱼——这是另一种东西。AI 分析出：模型的「写作善意」有三个方向——让信更生动（补感官细节）、让学生感觉被理解（补内心独白）、让学生感觉被肯定（拉踩其他学生）。每次修补只堵住了某个具体表现，而没有堵住这一类动机。

**这个分析后来成为 V2.0 重构的核心论据——从「禁令清单」升级到「分类框架」。**

## 第七部分：团队分享要点

### 7.1 这个案例可以证明什么

1. **好系统不是设计出来的，是跑出来的。** 一封信 Partner 的核心能力——洞察生成、锚点质量自查、语气匹配——没有一个是凭空设计的。全部来自两个真实案例的对话记录。如果先画架构图再填内容，PACK_INSIGHT 的素材交叉规则（单源素材不得做"表层vs底层洞察"）大概率不会出现——因为它只存在于毛俊杰那个具体场景里。

2. **「先跑案例再建系统」是更可靠的构建方法。** 两个案例跑完，P0 走查只用了 12 轮对话，就已经拿到了 5 种洞察类型、四维自查标准、「你应该→我注意到」转换规则。这些不是「我觉得会需要」的内容，是「我见过确实需要」的内容。

3. **约束需要分三级。** 原则级约束（"逐段自检信息来源"）对模型基本无效。禁令级（"不得描写感官细节"）有效但只能堵具体表现。检查动作级（"逐段扫描：有表情吗？有就删除"）最有效。V1.0→V1.1 的迭代，本质上就是把一批原则级约束升级为禁令级和检查动作级。

4. **部署测试不是最后一步，是第二步。** V1.0 只跑了两个案例，PACK_TONE 有 50% 的内容未经验证。但部署测试后拿到的三个真实问题，比任何假设分析都值钱。如果一直在设计阶段打磨而不测试，这三个问题会在真实使用时集中爆发。

### 7.2 可以复用的构建流程

```text
Step 1：P0 走查（2-3 个真实案例，不用任何系统）
  → 产出：可追溯事件列表、洞察类型、常见误区、核心风险点

Step 2：P1 数据包结构设计（从 P0 发现倒推）
  → 产出：包的数量、每个包的职责、包之间的调用关系

Step 3：五文档输出（系统提示词优先）
  → 产出：可部署的系统提示词 + 能力包 + 总包

Step 4：部署 + 验收 + 迭代（最小可用版本即部署）
  → 产出：已验证的系统 + 修正后的文档 + 可迁移规律
```

### 7.3 一句话总结

