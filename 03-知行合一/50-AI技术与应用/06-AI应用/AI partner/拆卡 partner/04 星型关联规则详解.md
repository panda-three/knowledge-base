# 四、星型关联规则详解

---

## 一、什么是星型关联

```
❌ 网状关联（你不需要做的）：

   A ←→ B ←→ C ←→ D ←→ E
   ↕    ↕    ↕    ↕    ↕
   每张卡关联五六张，维护成本爆炸

✅ 星型关联（你只需要做的）：

   B ↗
   C → [枢纽卡A] ← D
   E ↘        ↙ F
   
   子卡只关联枢纽卡。枢纽卡关联所有子卡。
   跨主题只在枢纽卡之间。
```

**核心原理：** AI 做 RAG 检索时，不需要每张卡互相认识。检索到子卡 → 跳枢纽 → 分发到其他子卡。星型结构刚好满足，维护成本是网状的十分之一。

---

## 二、三种卡片的关联规则

### 规则一：枢纽卡的 `related`

**写什么：** 所有子卡 + 跨主题关联的枢纽卡。

**判断方法：** 打开你的主题文件夹，列出所有卡片。枢纽卡的 related = 文件夹里所有其他卡片名 + 其他主题里和这张卡有底层关联的枢纽卡。

**示例——灵感闪现主题的枢纽卡：**

```yaml
# SOUL工作流模型.md（枢纽卡）
related:
  # ↓ 本主题所有子卡
  - "[[2×2创造力矩阵]]"
  - "[[五层应用场景全景]]"
  - "[[SOUL卡牌矩阵]]"
  - "[[Truman演示案例·SOUL全流程]]"
  - "[[灵感闪现×AI使用原则]]"
  - "[[三次飞跃修炼路径]]"
  - "[[六段位修炼地图]]"
  - "[[灵感闪现×刻意练习1+4]]"
  - "[[四个L6级洞察]]"
  - "[[Truman个人进化史]]"
  # ↓ 跨主题——底层框架相同的枢纽卡
  - "[[清单体笔记]]"              # 灵感闪现深度依赖清单体笔记
  - "[[十五字核心框架]]"           # 「充分做加法，专业做减法」是同源框架
```

**枢纽卡 related 自查：**

```
[ ] 文件夹里所有其他卡都在 related 里了吗？
[ ] 有没有漏掉某张子卡？
[ ] 跨主题关联的依据是「底层框架相同」，不是「内容有点像」吗？
```

---

### 规则二：子卡的 `related`

**默认写法：只写枢纽卡。**

**示例——灵感闪现主题的子卡：**

```yaml
# 2×2创造力矩阵.md（子卡）
related:
  - "[[SOUL工作流模型]]"

# SOUL卡牌矩阵.md（子卡）
related:
  - "[[SOUL工作流模型]]"

# Truman个人进化史.md（子卡）
related:
  - "[[SOUL工作流模型]]"
```

**绝大多数子卡只需要这一条。** 不是偷懒，是设计原则——少就是多。每条多余的关联都是维护负债。

---

### 规则三：子卡关联的例外（R14）

**什么时候子卡之间加双向链接？**

判断标准只有一句话：**「用户打开 A 卡，有没有可能接下来最想看的是 B 卡？」**

**是 → 加双向链接。不是 → 不加。**

**实际案例：**

```
✅ 加双向链接：
三次飞跃修炼路径.md  ←→  六段位修炼地图.md

原因：这两张卡是同一条修炼路径的两张地图。
      用户看完「三次飞跃」的状态描述，最想看的下一步
      就是「我现在在第几段位」。

✅ 加双向链接：
Truman演示案例·SOUL全流程.md  ←→  SOUL卡牌矩阵.md

原因：用户看完「Truman怎么完整跑一遍SOUL」，
      最想看的下一步是「我能用哪张牌」。

❌ 不加：
Truman个人进化史.md  ←→  六段位修炼地图.md

原因：个人进化史是建立信念的叙事。
      用户看完不会立刻想「我在第几段位」。
      它们没有强操作关联。
```

**实操规则：** 如果你犹豫「要不要加」，答案就是**不加**。宁可少一条关联，不要多一条不准确的。

### 规则四：跨主题关联（R15）

**只在枢纽卡之间进行。子卡不跨主题关联。**

**判断依据：** 底层框架相同，不是内容有点相似。

**触发词（当 Truman 在不同课程里说了同一句话/同一个框架）：**

- 「底层一致」
- 「同一个框架」
- 「Truman 反复强调」
- 「在不同课程里出现过」
- 「本质上是同一件事」

**当前知识库中的跨主题关联：**

| 枢纽卡A | 枢纽卡B | 关联依据 |
|---|---|---|
| `SOUL工作流模型` | `清单体笔记` | 灵感闪现深度依赖清单体笔记能力 |
| `SOUL工作流模型` | `十五字核心框架` | 「充分做加法，专业做减法」是同源框架 |
| `十五字核心框架` | `SOUL工作流模型` | 同上，双向 |
| `一堂成长三角形·1+4五要素` | `IPO·科学学习` | 刻意练习依赖 IPO 输入 |
| `一堂成长三角形·1+4五要素` | `知识管理必修课` | 刻意练习产出需要知识管理沉淀 |
| `一堂成长三角形·1+4五要素` | `深度复盘第一课` | 复盘是及时反馈的核心手段 |
| `四步基本功·ABCD分层递进` | `一堂成长三角形·1+4五要素` | 项目管理是刻意练习的实践场 |

## 四、新建卡片时的关联操作流程

```
第1步：确定这张卡是枢纽卡还是子卡
  → 「只能带走一张」= 枢纽卡
  → 其他 = 子卡

第2步：如果是子卡
  → related 只写枢纽卡名（一条）
  → 检查：有没有另一张子卡和它有强操作关联？
    有 → 加双向链接
    没有 → 完成

第3步：如果是枢纽卡
  → related 列出本主题所有子卡
  → 检查：有没有其他主题的枢纽卡和它有底层框架相同的关联？
    有 → 加跨主题关联（双向）
    没有 → 完成

第4步：更新关联到的对端卡片
  → 子卡关联枢纽 → 枢纽卡不需要改（它已经关联了所有子卡）
  → 两张子卡双向链接 → 两张都要加
  → 跨主题关联 → 两张枢纽卡都要加
```

## 五、常见错误

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 子卡关联了多张卡 | 破坏星型结构，维护成本高 | 子卡默认只关联枢纽卡 |
| 枢纽卡漏了某张子卡 | AI 检索时子卡找不到入口 | 每次新增子卡后检查枢纽卡的 related |
| 跨主题关联放在子卡上 | 跨主题应该只在枢纽卡之间 | 移到枢纽卡上 |
| 因为「内容有点像」就加关联 | 关联不是因为相似，是因为底层框架一致 | 用 R15 的触发词判断 |
| 双向链接只写了一边 | 关联断裂 | 检查对端卡片是否也加了 |
| 加了不存在的卡片名 | AI 检索时跳转失败 | 确认 Obsidian 里真有那张卡，且名字完全相同 |

## 六、关联健康度自检

每新增一个主题或每新增 5 张卡后，做一次：

```
[ ] 每个主题文件夹，有且只有一张枢纽卡吗？
[ ] 枢纽卡的 related 列出了所有子卡吗？（打开文件夹，逐张核对）
[ ] 每张子卡的 related 第一条是枢纽卡吗？
[ ] 有例外关联的子卡，双向链接都写了吗？
[ ] 有跨主题关联的枢纽卡，双向链接都写了吗？
[ ] 有没有关联了不存在或改名了的卡片？
[ ] 有没有子卡关联了跨主题的卡？（应该移到枢纽卡上）
```
